## 1. 执行结论

不把“未完成事项”当作一个总项目一次性清空。建议按四种工作分流，并用小批次收口：

1. **近期代码批**：先修 `G-6-L1` 成品口径错位，再做同源投入配给仲裁 `L1′`，随后开始 `G-2` 全商品供给州府桶骨架。三者无须等待旧粮价裁决；共享目录/结算入口的改动按批串行，避免相互覆盖。
2. **死代码与废弃项**：对 §9.2 的 11 个登记项逐项做“证据复核 → 保留/接线/删除/延后”处置。清单中的“疑似未引用”不等于“可删”；音频、肖像、自动生成目录、打包导入和 SQLite 性能项分别设验收门。
3. **决策门**：只在决策真正阻塞的批次前请用户裁定。当前最直接影响主线的是 **H（粮食载体）**；**A（旧粮价价格域）**影响 P0 放行和后续价格工作，但不阻塞 G-2 供给骨架。其余决策按对应专题到达时再定，不把它们包装成当前工程阻塞。
4. **长期路线**：粮食市场交易、工坊市场采购、产业链扩充、P1–P6 纵向经济路线依次通过守恒、空间归属、真实支付/运输与长局质量门；未通过时不扩大商品或玩法范围。

**推荐的工作决策**：接下来代码落地以 `G-6-L1 → L1′ → G-2` 为主线；与此同时可只读复核 9.2 的处置证据。通过 L1′ 与 G-2 骨架验收后，再进入粮食载体裁定及 G-3；不因“全商品”目标跳过 POP 挂载律或直接开启 G-4。

#### ✅ 裁定（2026-10-04 DSH，用户授权「以史实和游戏性为先」自行裁决并留理由）

**裁定：甲** —— 粮迁入 `goods[治所][米/麦]`，`pops[].grain` 降为**只读派生视图**。

**理由一（史实）**：宋代官府粮秣本来就是**走市场采购**的。计划所引曾雄生《宋代的城市与农业》
载元丰七年诏「荐新米麦之属，皆取于市……其所无者，乃索之杂买务」，而杂买务「掌和市百物，
凡宫禁、官府所需，以时供纳」。把粮排除在市场之外，与史实相反。

**理由二（游戏性）**：只有甲能让粮与其余商品共用同一条 `goods[治所][dim]` 通道。选乙则
`.grain` 与 `.goods` 成为**两个载体**，市场访问层须同时懂两者 —— 「口径单点」
（`AGENTS.md` §3-2）被打折，且「运没运到」对粮食不可观测，
这正是本次已在建材上修掉、却会在粮上复发的同一缺陷。

**理由三（不选丙）**：丙与用户明确的产品目标「所有商品都参与经济流转」直接冲突，
属静默改变目标，不可默认。

**关键前提（甲的放行条件）**：派生视图**不产生第二本账** —— `.grain` 只由 `goods` 求和派生，
**任何写入必须落 `goods`**，否则违反 POP 挂载律「禁与 POP 平行的账本」的本意。

**同步动作**：① 改 `AGENTS.md` §3-1 措辞，允许 `grain` 作为 `goods` 的派生视图；
② 旧档 `grain:int` 迁移为 `goods[州府][米/麦]`；③ 迁移前后 POP/商人/太仓分别对账，读路径不得双写。

**裁决记录人**：DSH · 2026-10-04 · 依据用户授权「有争议的地方以史实和游戏性为先，留下裁决理由就行」。

**G-3 放行**：H 有明确裁定；迁移前后 POP、商人、国库/太仓分别对账；旧存档可加载并保持读数；新旧读路径无双写；迁移失败有安全回滚。

### 阶段 3 · 工坊市场采购与价格域（G-4 → G-5）

G-4 曾因料款/工钱共用资金口、判定与采购分叉、顺序相关失败而回退。本次不得从“改掉太仓直扣”直接扩成全链路大改。

1. 先把“能否购买”的判定和实际采购收敛到同一纯查询/撮合入口；拆分料款与工钱预算，明确出资 POP、卖方、商品、成交地和在途批次。
2. 分别接本地成交与跨府成交。每笔成交只扣一次买方钱、只扣一次卖方货；在途未到不可消费；无货/无钱/无路径要有不同拒绝原因。
3. 再将工坊消耗、产出和副产物纳入明确持有人与地点；工坊无料按规则减产/停产，不得免费生产。
4. G-4 稳定后才扩 G-5 州府级供需同域价格。将“旧粮价 A”与“新市场价格”分开管理，明确每个商品维只有一个生效价格口径。

**G-4 放行**：钱、货、在途三套数量/价值变化分别可对账；遍历顺序不改变撮合结果；无货停产、无预算不成交、未到货不消费；重复结算不会重复付款或发货。

**G-5 放行**：供需和价格在同一州府域；调一府供需只影响有传播规则的区域；运费由实际路线/距离口径计算；与旧粮价并行期间没有同一粮食双重定价。

### 6.9 放行门机制的价值：静态扫描会漏，长局对账才暴露（2026-10-04）

### 6.19 G-4 开工诊断：失败根因是**资金池共用**，不是撮合算法

**现状实测**（`settlement_econ:1641-1651`）：工坊投料是**白拿**——

```

state.change_granary(-int(round(g)))      # 从太仓直接扣，无付款方
```

⇒ **无买方、无成交价** ⇒ 与「G-4 真成交 + 真实在途」的目标差两层。

**为什么「收窄版 B」当初整体回退**（计划已记录的三条症状）：

1. **料款与工钱共用同一笔钱** —— 工坊没有独立资金池，付了料款就没钱发工钱；
2. 判定与采购口径分叉；
3. 失败集合随用例顺序漂移。

🔴 **第 1 条是根因**，且**不是算法问题**：
`material_market.buy_material` 的钱腿走 `buyer_pop.wealth`，
而工坊的 `artisan` POP 正是买方 ⇒ **付料款即从工匠身上扣钱**，
而工钱也从工匠 wealth 出 ⇒ **同一笔钱被两条腿争抢**（计划 §三 的原话）。

**因此 G-4 不能只换撮合函数**，必须先解决**营运资金隔离**。
两个可行方向（**需用户裁定**，属设计边界非实现细节）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲** | 工坊设**独立营运资金**（如 `ws["capital"]`），料款从资本出、工钱从资本出，资本按月补充 | 需新增台账与补充规则；改动面大但守恒清晰 |
| **乙** | 工钱**不从工匠 wealth 出**，改由作坊「产出后折钱」支付（延迟结算） | 经济含义变更较大；与「工钱即所得」的体感冲突 |

⏸ **本轮未擅自实施** —— 这属产品/经济口径决策，按授权范围（「有争议以史实和游戏性为先」）
**记录理由、不自决**，因为两个方案对长局金钱量级影响不可预估，需先跑影响面校准。

### 6.21 V3 做法实施结果：**第二次失败，已回退**；根因锁定（2026-10-04）

用户指定「按 P社《维多利亚3》的做法」。V3 的经济链是：

资本所有者与劳动者是两个**独立阶层**，故料款与工钱永不争抢同一笔钱。

## 本作无「资本家」阶层

六类 POP = `农 / 士绅 / 商人 / 官僚 / 兵 / 工匠`。取**商人**为坊主：

## 🔴 根因（第一版失败处，非我最初判断的「凭空注入」）

⚠️ 这不是调参能解决的：**收款方由供给链的位置决定**，不是由我选的。

## V3 真正的前提（本项目尚不具备）

V3 里工厂的投入品来自**市场中的其他厂商/商人**，钱付给**卖方**；
而本作的料在**政府仓**，政府既是卖方又是唯一的收银台。

⇒ 要落地 V3 做法，必须先满足其一：

| 方案 | 做法 | 代价 |
|---|---|---|
| **甲** | 供给链改为**商人持料**（`supply_goods_to_seats` 落商人 goods 桶），工坊向**本路商人**买料付款 | 改动供给链；G-2 已把料铺进州府桶，但**收归商人**这一步未做 |
| **乙** | 料款付给**国库但同时等额扣减**（政府补贴产业，净支出） | 国库仍净流出，可控；但「采购」名不副实，实为**官营手工业** |

⏸ **均未实施** —— 属供给链架构决策，超出单点改动范围。

## 本次一并确认的第二处造钱（已在回退中消除）

「按整路总需求给每坊记资本」：`_need_pref` 是**整条路**的总需求，
却被加给该路**每一座**工坊 ⇒ **扣一次、记 N 次**（6 坊即 5 倍虚增）。
⚠️ 这类「池子按需汇总、再按件分摊」的写法极易重复计入，**分摊必须按各坊自身份额**。

## 结论

V3 的**阶层分离思想是对的、可落地**；但本作的**物料供给链位置**（政府仓）
使「付给市场卖方」无法直接成立。**先定供给链归属，再谈工坊采买** —— 顺序反了必然造钱或撑爆国库。

### 6.24 POP 须区分**派系与阶层**两层（2026-10-04 用户纠正，连带修正持有者解析）

用户指出「**pop 要区分派系和阶层**」。这一条**推翻了我 §6.23 的一层映射**。

## 为什么必须分两层

我在 §6.23 把「盐铁 → 官营」当成一个类别处理，但**「官营」不是阶层属性，是派系属性**。
同一个阶层可以处在不同派系中，**钱的去处因此完全不同**：

| 情形 | 阶层 | 派系 | 实际持有者 |
|---|---|---|---|
| 盐、铁 | —（官营） | **官** | **国库**（不是 POP） |
| 丝、麻 | **农** | 民营（自产） | 农户 |
| 丝、麻 | **农** | **官营佃种** | 官仓 |
| 果、木、石 | **士绅** | **庄园** | 士绅 |

同为「农」，民营自产与官营佃种，**付款对象分别是农户与国库** ——
若压成一维（只有阶层），就会**付错人**，等于凭空造钱或抽错税。

## 两层解析

```
持有者 = 解析(维, 阶层, 派系)
#维：      物料维（丝/麻/果/木/石/盐/铁…）
#阶层：    POP_CLASSES = 农/士绅/商人/官僚/兵/工匠（经济身份）
#派系：    官营 / 民营 / 庄园 / 官市 / 蕃市 …（权力归属与经营属性）
#返回值：  POP 键 或 非 POP 载体（国库 / 官仓）
```

## 对 POP 本体的要求（这才是本节的正题）

现 `POP_CLASSES` 六类**只有阶层，没有派系**。要支撑上面的解析，POP 载体需增派系字段：

| 字段 | 含义 | 取值 |
|---|---|---|
| `cls` | 阶层 | 现有六类 |
| `faction` | 派系 | 官营 / 民营 / 庄园 … |
| 聚合镜像 | 路级只读镜像 | **派维合成**（各派系 Σ）|

⚠️ **必须遵守 POP 挂载律**：`faction` 是**子池键**（与 `hidden`/`size` 同级），
不是与 POP 平行的账本；下沉州府、路由 `sync_route_pops` 聚合，**不得就地造第二个载体**。

## 状态

⏸ **未实施**。这一条比 §6.23 的映射表更基础 —— **先有派系，再谈持有者解析**。
实施顺序：① POP 增派系子池（含下沉与镜像聚合）→ ② 维×阶层×派系 → 持有者映射（单点）
→ ③ 供给链接通 → ④ 工坊按持有者付款。
