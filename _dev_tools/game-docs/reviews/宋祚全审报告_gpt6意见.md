## 4. 【优先级错配】

### 4.1 把文件拆分列为“必修”，而把存档/守恒风险列为一般建议

建议排序：

- **必修**：守恒断言、存档 round-trip/迁移、诏令公式边界、AI provider/model 契约、缺失值契约；

### 4.2 `numeric.py` 不应以“减少重复”直接进入必修

**报告位置**：§4 必修第 2 项。

`_num`、`_finite`、`_clamp` 并不一定拥有相同语义。尤其当前已经出现：

- 缺失值；
- 非有限值；
- 内部保守判定；
- 对外“未定义”；
- 业务默认值。

盲目抽公共 helper 可能把不同业务语义强行统一，反而制造新的错误。应先建立明确 API：

```text
parse_number
finite_or_undefined
clamp_effect_multiplier
required_number
```

每个函数定义 `None`、NaN、无穷、非法字符串和默认值策略，再决定是否抽公共模块。

`GameState.__init__` 587 行主要是可维护性问题；`load_game` 复杂度 116 则直接影响：

因此应把 `load_game` 提到必修或至少“高优先级应修”，并且先补行为测试再拆。

## 5. 【规模建议复核】

### 5.1 `situations.py` / `situation_settle.py` 拆分

**报告位置**：§1.6 高优先级第一项；§4 必修第 1 项。

**风险评级：报告标为低，实际应为中。**

原因：

- 报告没有给出两个文件的实际符号分布；
- `Record`、DSL、效果契约、intent、readout、settlement 之间很可能存在类型和序列化依赖；
- `test_situation_settle.py`、`test_readouts_endpoint.py`、前端 situation registry 可能依赖当前 import 路径；
- 记录对象字段变化会影响存档兼容。

更优做法：

1. 先只移动纯类型和无副作用函数；
2. 保留原模块 re-export，避免破坏现有 import；
3. 对公开构造函数、Record 字段和序列化结果做快照测试；
4. 验证 situation settlement、readout endpoint、前端字段三条路径；
5. 连续两个回合做状态等价比较。

验收至少包括：

```text
拆分前后同一输入的 Record 等价
结算顺序不变
序列化 JSON 等价
旧 import 路径仍可用或有明确迁移
pytest + tsc
```

### 5.2 `numeric.py` 公共抽取

**风险评级：报告标为低，实际为低到中。**

如果只是抽取完全相同且语义明确的 helper，风险低；但当前报告没有证明这些函数的默认值和异常行为相同。

建议：

- 先生成函数行为矩阵；
- 只收敛真正同语义的函数；
- 保留业务层命名包装；
- 对 NaN、None、字符串、无穷、负数和边界值逐项测试；
- 不以“重复组数量下降”作为唯一验收指标。

### 5.3 `settlement_steps.py` 按批次拆分

**风险评级：中高，判断基本合理。**

报告正确提到 `_STEPS` 镜像和 AST 比对，但同步范围还不完整，至少还要包含：

- 12 步的顺序；
- 每步是否执行一次；
- 事务边界；
- POP/国库/粮食写入；
- 结算失败时回滚；
- 月报和 readout 输出；
- 存档后下一回合继续结算；
- monkeypatch 或动态注册的测试。

更优方案是先把每一步提取为相同签名的函数，保留一个中央 `_STEPS` 注册表；不要先按文件移动再重新设计执行器。

### 5.4 `load_game` 拆分

**风险评级：报告标为中，实际应为中高。**

它涉及存档格式和迁移，不应只按“读档 / 迁移 / 各域载入”机械拆函数。建议先定义：

```text
raw decode
schema validation
version migration
domain hydration
invariant validation
commit/return
```

并保证任何一步失败都不会返回半初始化对象。测试必须同步覆盖新旧存档 fixture、损坏存档、未知字段和 round-trip。

### 5.5 `content/data.py`、`ai/client.py` 拆分

**风险评级：报告标低到中，需拆开判断。**

- `content/data.py`：如果是纯常量，可低风险拆分，但要保留导出面并验证数据加载顺序。
- `ai/client.py`：import 风险只是次要问题，真正风险是 provider、计量、重试、fallback 和契约行为。文件拆分前应先补 contract tests。

### 5.6 疑似死代码

报告建议“文档标注状态”是合理的，但需要定义三种状态：

```text
active
intentionally_unwired
deprecated
```

每个条目必须有引用搜索、运行时入口检查和负责人/后续接线位置。不能仅凭“当前无引用”判定可删除。

## 6. 【可执行性】

**结论：部分可执行，但不能按当前版本直接交给开发者。**

### 已具备的部分

§3 的五个行为问题基本具备：

- 位置；
- 现象；
- 修法；
- 测试名称；
- 部分边界条件。

这些可以作为修复记录或回归记录继续使用。

### 缺失的部分

#### A. §7 不是开发任务模板

报告 §7 只有三个“请你决定”的问题，没有做到每项：

```text
位置
问题
影响
修改方案
不修改的风险
验收断言
依赖和同步文件
```

因此 §4 的规模建议仍是方向性意见，不是可直接执行的任务单。

#### B. 规模任务缺少精确符号和迁移边界

例如：

> “抽 `situation_dsl.py` / `situation_record.py`”

没有列出：

- 要移动的类、函数和常量；
- 保留在哪个模块的兼容导出；
- 哪些 import 必须修改；
- 哪些测试是镜像；
- 序列化字段是否改变；
- 是否允许改变异常类型。

#### C. 验收大多是静态或全量通过

“pytest 全量通过”不能替代机制断言。每项至少要有一个可观察的业务不变量，例如：

```text
POP 总人口前后守恒
国库 + 地方合法账户总额前后守恒
军队加成不超过 30%
民心 + 识字率弱影响不超过 15%
fallback 使用精确模型名
缺失字段序列化为 undefined
save/load/save 状态等价
```

#### D. “只审不改”与报告内容需澄清边界

报告说规模类问题“只审不改”，但同时已经：

- 修了 5 个行为缺陷；
- 删除了一个别名；
- 修改并新增测试；
- 新增了 skill。

这不一定违反 skill，因为可能是“规模问题只审不改”，但报告应明确：

> 行为缺陷已修复；规模/架构建议未执行。

否则开发者会误以为整份报告中的修法都已经落地。
