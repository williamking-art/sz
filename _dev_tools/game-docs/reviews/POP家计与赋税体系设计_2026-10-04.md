## 一、问题的由来

G-4「工坊改市场采买」开工后连续两次失败，暴露的真问题不在算法：

| 现象 | 实测根因 |
|---|---|

⇒ 「付给持有者」的前提是：**先有持有者**。而持有者体系当前**不存在**。

## 二、载体层：POP 须区分**派系**与**阶层**

### 2.1 现有结构不足

`POP_CLASSES = ("农", "士绅", "商人", "官僚", "兵", "工匠")` —— **只有阶层，没有派系**。

### 2.2 为什么必须有派系

「盐铁归官营」**不是阶层属性，是派系属性**。同为「农」，处境不同：

| 情形 | 阶层 | 派系 | 付款对象 |
|---|---|---|---|
| 盐、铁 | —（官营） | **官** | **国库** |
| 丝、麻 | 农 | 民营（自产） | **POP**（农户） |
| 丝、麻 | 农 | **官营佃种** | **国库**（官仓） |
| 果、木、石 | 士绅 | 庄园 | POP 或 内帑 |

压成一维就会**付错人**（等于凭空造钱或抽错税）。

### 2.3 字段设计

| 字段 | 含义 | 取值 |
|---|---|---|
| `cls` | 阶层 | 现有六类 |
| `faction` | 派系 | 官营 / 民营 / 庄园 / 官市 / 蕃市 … |
| 路级镜像 | 只读聚合 | **派维合成**（各派系 Σ） |

> 🔴 **POP 挂载律**：`faction` 是**子池键**（与 `hidden`/`size` 同级），
> **不是与 POP 平行的账本**。须下沉州府、由 `sync_route_pops` 聚合，不得另造载体。

## 三、持有者解析：三类载体

### 3.1 史实依据

- **山林川泽之利归官**，皇室另经**内诸司**（内诸库/内园/御苑）掌控园林矿产珍异，百姓采伐须**纳课**；
- **榷盐、铁冶官营** —— 「专卖」即国家专营，**不在商人手中**；
- 「男耕女织」：蚕桑纺麻为**农户家庭手工业**。

### 3.2 三类载体

| # | 载体 | 代码落点 |
|---|---|---|
| 1 | **POP 私有** | `pops[阶层][派系].goods[治所][维]` |
| 2 | **国库** | `state.treasury` ＋ `resources[维]["stock"]`（官仓） |
| 3 | **内帑（皇室）** | `state.imperial_treasury`（已有酒课/肉折钱先例） |

> 🔴 国库与内帑是**两个钱袋，付给谁不可混** —— 混即凭空造钱或抽错税。

### 3.3 商人的位置（被收窄）

商人是**流通者，不是持有者**。他只经手 **`yields < 0`**（本路不产、须外输入）的部分。

### 3.4 解析签名（单点）

```python
resolve_holder(维, 阶层, 派系) -> POP键 | 'treasury' | 'imperial_treasury'
# 产出端与付款端共用本函数，不允许分叉（口径单点 §3-2）
```

### 3.5 产表实测（`PREFECTURE_INFO[路]["yields"]`，京畿路）

`{茶 0, 丝 1_000_000, 麻 500_000, 蔗 0, 果 500_000, 木 200_000, 石 300_000, 铁 0, 盐 −100_000}`

负值 = 该路不产、须外输入。

## 四、度量层：家计

### 4.1 定名

取宋代习称**家计**（苏轼「家计萧然」；宋有五等版籍分贫富等第）。
它不是「生活水平 SoL」的译名，而是**更基础的财力标尺** —— SoL 是它的一种读法。

### 4.2 定义（单点）

```
家计 = Σ[ wealth + 存粮折价 + 生业应收 ] − Σ[ 口粮 + 租 + 税 + 役 ]    单位：贯
```

> 🔴 **缺失 ≠ 0**：任一分项不可读 ⇒ `家计 = None`（不可计算），**不是 0**。
> 回落 0 会把「没数据」判成「赤贫」进而误降阶层 —— 这是最危险的失真。

> 🔴 **粮折价必须用基准价**（`MATERIAL_PRICE_BASE`），**不用当月市价** ——
> 否则家计随物价自激，等第自己乱跳（涨→家计降→降等→需求减→跌→反之）。

### 4.3 一个数值，三重读法（同源，不得分叉）

| 读法 | 公式 | 用途 |
|---|---|---|
| **阶层（等第）划分** | `家计 ≥ 阈值ᵢ` ⇒ 第 i 等 | **等第由家计定义**，不是并列的第二口径 |
| **贫富** | `家计` 绝对值 + 序位 | 群体间比贫富，跨路可比 |
| **生活水平** | `家计 / 必需支出` 倍数 | 同一家计，口粮占比不同 ⇒ 实际生活水平不同 |

> 三者必须**出自同一次计算**。否则会出现「家计升高却生活水平下降」的矛盾读数 —— 那就是口径分叉。

### 4.4 五等版籍

| 等第 | 判据 | 宋代对应 |
|---|---|---|
| 上户 | 家计 ≥ 阈值₄ | 富室、士绅、大商 |
| 中户 | 阈值₃ ≤ 家计 < 阈值₄ | 中等民户 |
| 下户 | 阈值₂ ≤ 家计 < 阈值₃ | 平民、自耕 |
| 贫民 | 阈值₁ ≤ 家计 < 阈值₂ | 佃农、贫农 |
| 无业/逃户 | 家计 < 阈值₁ 或无籍 | 流民、客户 |

> 🔴 **等第 ≠ 身份**：士绅可贫、官僚可穷。**家计定等第，身份定类别**，
> 台账两列分记，不得互相推导。

## 五、赋税层：三税三基

### 5.1 分税定基（宋制）

| 税 | 计税基础 | 等第作用 | 史实依据 |
|---|---|---|---|
| **赋役**（免役钱） | **五等版籍** | ✅ 正相关 | 募役法：五等主户等第越高，输免役钱越多 |
| **田赋** | **占田亩数** | ❌ 无关 | 主户输田赋；**客户不纳租**，只纳身丁钱 |
| **商税** | **交易额 × 税率** | ❌ 无关 | 税关从税(2%)/倍税(3%)等，税率随**货物种类**而异 |

### 5.2 关键后果

**家计等第只喂「赋役」一税。**
若套到田赋、商税上，等于把「按土地」「按交易」错改成「按家财」：

1. **史实错** —— 客户无田不纳租，改按家计就成了无田也要缴田赋；
2. **机制坏** —— 税基与纳税能力脱钩，垦荒与商品激励被打乱，汲取链结构崩。

### 5.3 台账

```
等第(家计五等)    → 赋役(免役钱/力役)        # 由家计派生
占田(亩)          → 田赋                      # 独立口径，不读等第
交易额 × 货物税率 → 商税                      # 独立口径，不读等第
身份(农/士绅/…)    → 税率特权                  # 如士绅免役，与家计无关
```

### 5.4 硬约束

1. **三税各自单点**，不得共用一个税率函数；
2. **等第只入赋役**，田赋/商税路径**不得读取等第字段**；
3. **客户不纳田赋**（只纳身丁），不得按家计折算成「无田亦须纳租」；
4. **税率按货物种类**，不按等第；
5. 缺失 ⇒ 该税 `None`，**不得回落 0、不得用另一税基顶替**。

## 六、跃迁层：科举与家计正交

V3 的阶层流动**几乎全由 SoL 驱动**（连续链）；本作是**汲取链**，且有 V3 没有的**科举** ——
一次考试即可**农 → 官僚**，与 SoL 无关。

| 通道 | 管辖 | 性质 |
|---|---|---|
| **家计** | **等第升降** | 连续、缓变 |
| **科举** | **身份跃迁** | 离散、一步 |

⇒ 科举中第**不改等第**（可能中第而家计仍贫）；家计再高也**不能变官僚**。**互不越权。**

### 6.1 三条硬约束

1. **科举通道不得被 SoL 稀释**：中第不受 SoL 阈值限制，也不被 SoL 降层回退；
2. **两通道可区分可审计**：`move_pop_people` 须记 `cause ∈ {sol_up, sol_down, 科举, 役使…}`
   —— 否则台账无法解释「这个农为什么成了官僚」；
3. **SoL/家计不得成为汲取链旁路**：升层**不得**自动免除当期租税役。
   宋代免税属**恩荫**，须**单独立项、显式记账**，不得混进自动逻辑 ——
   否则「富起来」等于「免税」，汲取链直接崩。


## 九、本轮的两次失败（教训留存）

| 失败 | 根因 | 教训 |
|---|---|---|
| 开办资本 2M×107 坊凭空注入 | 新增钱袋不在守恒口径 `M_ALL` 内 | **新增钱袋必须在守恒体系内出资**，否则是印钞机 |
| 料款付国库 ⇒ 国库撑爆 | 收款方由**供给链位置**决定 | 收款方不是实现者选的；**先定归属再谈付款** |

> 后续提交带上了未验证的破损，是后台任务 `exit code=1` 才暴露。

## 十一、附录 · 多 Agent 协同协议（2026-10-04）

本会话发生过 **3 次并发文件冲突**（`game_state.py`、`pop_bridge.py`、本文档）
与 **1 次记忆库覆盖**（`phase` 单键被 Codex 会话覆盖）。故定此协议。

### 11.1 键位布局

```
agents        共享：agent 注册表 + 文件归属 + 协议
phase_<名>     独占：各 agent 自己的当前阶段（**不再共用 phase**）
decisions     共享：待裁定项登记（含 blocks 依赖）
tasks         共享：任务板（含 claimedBy 认领）
worklog       共享：追加式日志（**唯一绝对可靠的记录**，追加语义不丢条目）
phase         保留：Codex 会话在用，不动
```

> ⚠️ 实测：`phase:DSH` 被服务端规范化为 **`phase_DSH`**（冒号 → 下划线）。

### 11.2 三条硬规矩

1. **先认领再动手**：`state_get('tasks')` 看 `claimedBy`，非空且非自己就不碰；
2. **改共享文件先声明**：`log_append` 一行「我要改 X」，避免两边同时写；
3. **决策不进 phase**：一律登记 `decisions`，phase 只写「我现在在做什么」。

### 11.3 文件归属（当前）

| 路径 | 主写 |
|---|---|

`state_set` 是**覆盖**、`context_save` 是**快照** —— 都会丢。
本轮 `phase` 被覆盖后，我的设计内容**只因 Codex 读了仓库文档才得以保留**；
