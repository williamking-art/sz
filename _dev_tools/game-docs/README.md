# `game-docs/` · 游戏文档

本目录保存机制说明、设计分析、规格、审查记录与开发知识库。请按文档用途读取：归档审查稿记录曾经的发现，不自动代表当前代码状态。

## 文档分层

| 子目录 | 用途 | 判定规则 |
|---|---|---|
| [`docs/`](docs/README.md) | 已确认的机制口径和开发说明 | 机制“当前如何工作”的首选文档；代码变更后同步维护。 |
| [`specs/`](specs/README.md) | 专题需求、设计、任务状态与验收证据 | 目标及实施情况；任务状态需有代码路径和验证依据。 |
| [`analysis/`](analysis/README.md) | 设计探索、平衡分析和项目审查 | 过程材料；结论被采纳后回写 `docs/`，未采纳不作为机制事实。 |
| [`reviews/`](reviews/README.md) | 外部/专项审查与交接记录 | 留档追溯；问题是否修复须复核当前代码和任务状态。 |
| [`archive/`](archive/README.md) | 旧计划、历史审查与已过期材料 | 仅作历史查阅；原始事实不追改，最新处置写入现行文档/审校台账。 |
| `kb/` | 文档/源码检索工具及生成的知识库 | 生成数据库不是机制文档或唯一事实源。 |

## 维护规则

1. 机制实现发生变化时同步更新对应 `docs/` 和模块 README。
2. 规格状态区分代码存在、生产接线、测试覆盖、平衡验收，不用一个“完成”概括不同层次。
3. 新增文档或目录后同步更新所属目录 README；分析稿成为正式口径后合并到 `docs/`。
4. 文档、注释和归档结论不能代替代码调用链核查。
5. `archive/` 与 `reviews/` 的历史记录只补索引/更正说明，不回写成“当前事实”；现行状态以 `docs/` + 对应 `specs/*/tasks.md` 为单一入口。
