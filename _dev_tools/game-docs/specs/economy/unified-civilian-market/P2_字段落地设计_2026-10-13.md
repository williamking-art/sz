## 一、目标字段与来源（逐项给"值从哪来、谁写、缺了怎么办"）

| 字段 | 值的来源（**既有单点**） | 谁写 | 缺时 |
|---|---|---|---|
| `owner` | **复用 M66 词表**：`local:<路>` / `pop:<路>:<阶层>` / `state_treasury` / `imperial` | 迁移（新局+读档共用入口，**只填缺失**） | `undefined` + reason |
| `operator` | 首期＝**与 `owner` 同值**（官营/民营尚无独立经营者模型）⇒ **须口径裁定**；否则留 `undefined` | 同上（可选） | `undefined` |
| `completed_month` | 仅 `civil_building` 有建成月（既有字段）；其余**不臆造** | 不新增 | `undefined` |
| `operation_mode` | 由 `owner` 前缀**派生**（`local:`→官营；`pop:…:商人`→民营雇工；`pop:…`其它→家庭兼业？）⇒ **须口径** | 派生（只读） | `undefined` |
| `jobs_capacity` | `JOBS_PER_LEVEL` × 等级（**已有**） | 只读 | 可算 |
| `jobs_filled` | `allocate_employment_detail`（**已有纯函数**，M78） | 首期**只读**；若要落成状态 ⇒ 另批（改数值） | 可算 |
| `recipe` / `io_stock` / `income_to` | 配方在**作坊**；库存**不按主体分栏**；利润归主待 M71 口径 | —— | `undefined` |

**口径原则**：能**派生**的绝不写进 state（避免第二份真相）；只有**无法派生且需持久化**的（`owner`）才落字段。

## 二、schema 与迁移方案（**不改 `buildings` 现有形态**）

* 现状：`prefectures[路].seats[治所].buildings = {建筑名: 等级}`（标量；M38 已州府化）。
* 🔴 **保形态**（照 M38 手法）：**不把标量改成 dict**（会被 20+ 处读取炸）；改为**并列新增**一个
  `seats[治所].building_meta = {建筑名: {owner, operator?, ...}}`，`buildings` **一字不动**；
  读侧一律「先查 `building_meta`，缺 ⇒ `undefined`」。
* **迁移入口**：`migrations.assign_building_owners(state)`（与 `assign_workshop_owners` 同型）：
  幂等、**只填缺失**、判不出归属则**跳过并计数**（不臆造）；`game_init.init_building_owners` +
  `load_game`（**失败不拒档**）。
* **归属规则（建议，须裁定）**：`水利`/`常平仓` ⇒ `local:<路>`（官府兴办）；其余建筑类型
  **逐类型给依据**才登记，否则留 `undefined`（**不按人口/等级摊派**）。

## 三、桥接与影响面

* 本方案的字段**不被任何结算读取** ⇒ 首期**零数值变化**（A/B 应为恒等）。
* 若将来 `jobs_filled` 要**落成状态**（把 M78 的只读算法写入），则必须：① 走桥（`building_bridge` 范式）；
  ② **同种子 A/B 标定**（岗位/就业影响人口流动、产出、财政）；③ 全量回归 + 长局对照。
* 影响面读数：`entity_projection` 的 `defined_ratio`（`owner` 由 0 → 若干）、`readout_hub.p2_readiness`。

## 四、验收断言（写死）

- [ ] `buildings` **形态不变**（标量仍是标量；20+ 读取点零改动）
- [ ] 迁移**幂等**：新局/读档共用入口；重复调用 `assigned=0`
- [ ] **只填缺失**、判不出归属**跳过并计数**（不臆造）
- [ ] 首期 **A/B 同种子恒等**（新字段不被结算读取）
- [ ] `entity_projection` 就绪度随之上升，且未登记类型仍 `undefined`
- [ ] `load_game` 迁移失败**不拒档**（warning 留痕）

## 五、风险与回滚

* 风险：新增 `building_meta` 若被误当作"建筑账本"使用 ⇒ 违反「不新增与 POP 平行的账本」——
  **本设计明确它不是账本**（只是**归属/元数据**，不含存量与金额）。
* 回滚：删 `building_meta` 与两处迁移调用即可（`buildings` 未被触碰）。

## 五·补：`blueprint`（蓝图版本）**取证**（M100，2026-10-13）

规格要求「蓝图版本」。取证结论：**容器存在、但未持久化到建筑条目**。

| 事实 | 证据 |
|---|---|
| 静态蓝图表存在，**键即中文名** | `settlement_tech` 注释：「`BUILDING_STD` 政府建筑：其键即中文名（水利/常平仓/官营作坊/官署/军营/学校）」 |
| **动态蓝图注册表**存在 | `state.dynamic_blueprints = {dyn:xxxx: 蓝图dict}`（`game_state`；`core/blueprint_dynamic.register_dynamic_blueprint` / `resolve_dynamic_blueprint`） |
| 工程档案**带 blueprint_key** | `proj["blueprint_key"]`（`settlement_tech` 落成登记处） |
| 落成时**知道** key，却**只写等级** | 落成写 `prefectures[route]["buildings"]`（标量或 `{"lv","built_month"}`）——**不含 blueprint_key** |

**两条可行路径**（均未实施）：
1. **只读派生（零 state 改动）**：按**建筑名**反查静态表 ⇒ 可报 `key = 名`、`version = None`（版本未登记）。
   ⚠️ 风险：把"键当版本"会误导 ⇒ 若要落地，须把 `blueprint` 语义**明确为 `{key, version}`** 且 `version` 缺失时仍 `undefined`。
2. **持久化（改 state）**：落成登记时把 `blueprint_key` 一并写入建筑条目（`{"lv","built_month","blueprint"}`）——
   需 ① 幂等迁移回填旧档（**无法回填**：旧档没有 key ⇒ 只能对**新建**建筑生效）
   ② 桥接（沿用既有 `building_set`/`building_bridge` 范式）③ **A/B 同种子标定**（本项不应改数值，但落成登记属于结算路径，须证恒等）。

🔴 **本批不做**（避免"把键当版本"或以改 state 的方式绕开口径）。
