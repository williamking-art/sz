## 1. 结论（先说答案）

1. **当前不存在粮双源**：`new_game` 后连跑 18 月，**702 个 POP 全量扫描，米桶数 = 0**；
   粮仍由 legacy `pops[].grain` 承载（569 个非零）。
2. **原因是 G-3 迁移未接线**：`core/foundation/ledger/grain_ledger.py` 只提供纯函数
   （`grain_of` / `has_grain_bucket` / `GRAIN_MIGRATION_DIM="米"`），**全库没有任何迁移调用点**。
3. **真正风险不是"现在分叉"，而是"将来做一半"**：`grain_add/grain_set` 共 **46 处**调用，
   **44 处未传 `state`**。一旦有人只迁一部分 POP（或新增代码用 `pop_goods_add(..., "米")`），
   就会出现「一半有桶、一半没有」，而 `grain_get` 优先读桶 ⇒ 静默分叉。
4. 所以门的判据取**全体一致性**：**0% 或 100%，禁止中间态**；不是"桶数必须为 0"。

## 4. 为什么不顺手改那 44 处

- 迁移未实施时，不传 `state` 与传 `state` **行为相同**（都写 legacy）⇒ 改动零收益、零验证价值；
- 真正要改的时机是**迁移那一批**：届时所有写入必须统一落桶，44 处要一起改并逐处对账；
- 现在改反而会制造"看起来已迁移"的假象（口径已经半迁、账本没迁）。
