# 奏报机制现状整理（2026-10-19）

> 目的：把“谁能上奏、怎么上奏、哪些呈现、哪些只是背景板”按真实代码理清。
> 本文是**现状整理 + 设计口径建议**，不改 UI、不写生产代码。

## 0. 一句话结论

现有奏报是：**每回合 AI/模板生成最多 3 条 → 覆盖 `state.memorials` → 前端准奏/留中 → 准奏生成 `edict_drafts` 诏草**。

机构（通进银台司/都进奏院/登闻鼓院）**数据已落地**，但目前主要作为**提示词身份与来源标签**，还没有真正的“上奏资格门 + 路由 + 呈报/沉淀”分层。

## 1. 真实调用链

```
回合开始
  → commands._memorial_posture(state)
      → TianDaoFacade.scan_memorial_seeds(state, limit=3)   # 事实签，只进提示词
  → ai_client.generate_memorials(posture, count=3)
      → 失败/无 key → ai.narrative_fallback.fallback_memorials(...)
  → state.memorials = _memos                                 # 每回合覆盖
  → 前端 GovernanceHub：state.memorials
      → accept_memorial(index)  → 生成 edict_drafts 诏草
      → dismiss_memorial(index) → 留中，只记 memory/short_term_log
```

关键点：
- `scan_memorial_seeds` **不是直接呈现**，它是给大模型拟折的“事实签”；
- `state.memorials` 每回合被**整体覆盖**（`commands.py:600/641`），不是追加归档；
- `accept_memorial`/`dismiss_memorial` 用**数组下标**，不是 `memorial_id`；
- 后端 handler 也只传 `index`（`game/backend/client.py:251-254`）。

## 2. 三个队列必须分开

| 队列 | 内容 | 入口/呈现 | 是否落地 |
|---|---|---|---|
| `state.memorials` | 待批奏折（每回合最多 3） | `GovernanceHub` 奏折区；准奏/留中 | 准奏→诏草；留中→只记录 |
| `state.ai_pending_actions` | AI/大臣提议（财政/军令等） | `PendingActionsPanel`；批红/驳回 | 批红才走 applier/执行 |
| `state.edict_drafts` | 已准奏/会签中的诏草 | 诏草会签；`issue_edict_from_review` | 下诏→`pending_decrees` |

注意：`ai_pending_actions` 的 409 守卫会阻止颁诏（`issue_decree`/`issue_free_decree`），但它和 `memorials` 是两个队列，不能混为一谈。

## 3. 谁能上奏（现状）

### 3.1 实际写入者

- **AI 提示词身份**：`game/ai/prompts/memorial.md` 第一句是“你是北宋朝廷的通进银台司……为陛下具折呈奏”。
- **模板兜底**：`fallback_memorials` 给 3 条，`source_tag` 分别为：
  - `通进银台司进呈`
  - `都进奏院急递`
  - `登闻鼓院直奏`
- **事实签**：`scan_memorial_seeds` 只取**中枢在任主官**作为 `target_minister`：
  - 财政：户部/三司/尚书省/中书省主官；
  - 军事：枢密院/兵部主官；
  - 政务：中书省/尚书省主官。
- **人物字段**：模板里有 `official: {name, role}`、`guarantor`，但**没有校验**是否在册/在任/有上奏权。

### 3.2 机构已落地，但没做资格门

`content/ministers/data.py` 已有：

| 机构 | belong | scope | 事权 | 在任 holder |
|---|---|---|---|---|
| 通进银台司 | 皇帝 | 天下奏章进纳/封驳进退/内外章表总汇 | `奏章进纳` | 丰稷（知通进银台司事） |
| 都进奏院 | 门下省 | 各路驻京机构/地方情状邸报通传 | `邸报通达` | 唐恪（都进奏院提辖官） |
| 登闻鼓院 | 皇帝 | 庶民击鼓进诉/直达天听申冤 | `民隐通达`、`登闻进诉` | 陈师锡（判登闻鼓院） |
| 门下省 | 皇帝 | 封驳/审议 | `诏令封驳`、`政令审议` | 李清臣（门下侍郎） |
| 中书省 | 皇帝 | 决策/除授 | `朝政决策`、`人事除授`、`官制` | 曾布（中书侍郎） |
| 御史台 | 皇帝 | 监察/弹劾 | `监察百官` | — |
| 谏院 | 皇帝 | 谏诤/言路 | `言路` | — |

`AUTHORITY_MATTERS` 也已登记：`奏章进纳`→通进银台司、`邸报通达`→都进奏院、`民隐通达`→登闻鼓院。

**但**：`generate_memorials`/`accept_memorial` 没有调用 `permission_model.has_permission(actor, "奏章进纳"/"邸报通达"/"民隐通达")`；机构目前只是**来源标签/提示词身份**。

### 3.3 地方官员奏折（现状：基本没有接线）

地方官数据已落地：
- `circuit_officials`：帅司/漕司/宪司/仓司/首府长官/通判六职；
- `prefect_officials`：知州/知府、通判。

| 地方职位 | 能奏什么 | 应走渠道 |
|---|---|---|
| 帅司（经略安抚使/安抚使） | 军报、边防、盗贼、兵变 | 枢密院/都进奏院（急递） |
| 漕司（都转运使/转运使） | 财赋、漕运、上供、地方府库 | 户部/通进银台司 |
| 宪司（提点刑狱） | 刑狱、冤案、监察、按察 | 刑部/御史台/通进银台司 |
| 仓司（提举常平） | 常平、水利、赈济、粮价 | 户部/通进银台司 |
| 知州/知府 | 民政、灾伤、盗贼、地方情状 | 都进奏院/通进银台司 |
| 通判 | 监察同署、副署异议、地方隐情 | 都进奏院/御史台 |

**现状**：
- `scan_memorial_seeds` 只取**中枢在任主官**（户部/中书/枢密），**没有取 `circuit_officials` / `prefect_officials`**；
- `state.memorials` 仍只有 AI/模板 3 条，地方官没有独立上奏入口；
- 没有“地方官在任 + 职务领域”资格判断，也没有“都进奏院/通进银台司转呈”的路由。

**建议口径**：
- 地方官上奏资格 = **在任 + 职务领域**（帅司军、漕司财、宪司刑、仓司仓、知州民政、通判监察）；
- 路由：地方 → 都进奏院（`邸报通达`）→ 通进银台司（`奏章进纳`）→ 御前；
- 频率：常规月报/季报走背景档；灾伤/兵变/盗贼/边警等**急报**才进 `state.memorials`；
- 延迟：按 `transport`/驿传距离计算，不瞬达；
- 通判可单独上“副署异议/监察”折，不被知州完全过滤。

### 3.4 军报（现状：只有泛 military 折，没有军报通道）

军务数据：
- `枢密院`：`调兵`、`边防`、`军务机要`；
- `兵部`：`武官铨选`、`军籍`、`军需后勤`；
- 三衙：禁军/京城防务/北边防务/内地屯驻；
- `army_units`：士气、训练、欠饷、驻地、兵额；
- `settlement_military`：欠饷→逃亡、士气/训练衰减、裁汰、募兵成本。

**现状**：
- `generate_memorials` 只有泛 `kind="military"`，内容是模板/大模型泛写；
- `scan_memorial_seeds` 的军事事实签只从**流民数量**推，没读 `army_units` 的士气/欠饷/边防；
- `issue_military_order` 是**军令**（增募/调赴/换帅等），不是**军报**；
- 没有 `priority="urgent"`、没有“急递/走马承受”、没有“军报 vs 军令”的区分。

**建议口径**：

| 军报类型 | 来源 | 渠道/事权 |
|---|---|---|
| 边报/敌情 | 帅司、边将、走马承受 | 枢密院 `边防`/`军务机要`，急递 |
| 兵额/欠饷/士气 | 三衙、兵部、帅司 | 枢密院/兵部，常规或急报 |
| 城防/粮道/军需 | 帅司、漕司、兵部 | 枢密院/兵部/户部 |
| 调兵请求 | 帅司、边将 | 枢密院 `调兵`，急报 |

- `channel_matter` 用 `边防`/`军务机要`/`调兵`；不新增军事事权；
- `priority="urgent"` 的军报才进 `state.memorials` 前排；常规军报进 `monthly_gazette`/背景档；
- 军报只报事实与请求，**不直接调兵**；调兵仍走 `issue_military_order`/批红；
- 军报延迟走驿传/急递，不瞬达；边报可因道路阻断而延迟或丢失（可诊断，不静默）。

### 3.5 事故逐级处理链：县/乡里（地点）→ 州府 → 路省 → 中央

**现状（关键校正）**：
- 游戏**没有顶层县席位表**：`jinshi_to_county` 是知县蓄水池/履历；
- **但县的编制/县治/县官已写进 MemoryGraph**：
  - `core/county_registry.py`：`ensure_county_establishment` 写 `county` 实体，attrs 带 `posts/quotas/parent_seat_id/route/tier`；
  - `jinshi_to_county` 已调用它，并建立 `官员 --governs--> 县`、`县 --belongs_to--> 父州府`；
  - 事故链可用 `county_officials(mem, locality)` 从记忆库取县官；
- 真正有完整席位表的是 **136 州府**（`prefect_officials`）与**路级监司**（`circuit_officials`）；
- 因此：县官**有则用**（记忆库实体），无则州府通判/幕职/巡检代行；不能凭空生成县官，也不能假设事故只发生在州府。

**设计口径**：县/乡/镇/渡口是**事故地点粒度**，不是行政层；事故挂在父级州府下，由州府代行县务，处理不了再逐级上报。

```
地点（县/乡/镇/渡口，locality）
  → 州府（知州/知府 + 通判；无县官时由通判/幕职/巡检代行）
  → 路省（帅司/漕司/宪司/仓司）
  → 中央（中书/门下/六部/枢密）
  → 御前（仅摘要+建议；急报可越级）
```

| 层级 | 是否有实体 | 处理者 | 限制 |
|---|---|---|---|
| 县/乡里 | 🔶 MemoryGraph `county` 实体（编制/父州府） | 有县官 `governs` 关系 → 县官；否则州府通判/幕职/巡检代行 | 县官从记忆库取；无则代办 +1 回合延迟、能力折扣；**不得凭空生成县官** |
| 州府 | ✅ `prefect_officials` | 知州/知府 + 通判 | 本地府库/粮仓/兵力 |
| 路省 | ✅ `circuit_officials` | 帅/漕/宪/仓 | 跨州调度、监司职权 |
| 中央 | ✅ 中枢机构 | 中书/门下/六部/枢密 | 政策/钱粮/人事/军令 |

事故单字段：

```python
{
  "incident_id": "inc_<hash>",
  "kind": "flood|famine|bandit|revolt|border|fire|epidemic|judicial|...",
  "locality": "X县/某乡/某镇/某渡口",     # 事故地点，不是行政层
  "parent_seat_id": "路|治所",             # 父级州府（真实席位）
  "route": "路名",
  "severity": 0.0,
  "status": "reported|assigned|handling|resolved|escalated|failed",
  "level": "locality|prefecture|circuit|central",
  "handled_by": "姓名/机构",
  "acting_official": "通判/幕职/巡检/知县（可空）",
  "escalation_path": [{"level": "...", "actor": "...", "turn": 0, "reason": "..."}],
  "raw_report_ids": ["rep_..."],
  "summary": "...", "recommendation": "...", "unresolved": [...],
  "created_turn": 0, "due_turn": 0
}
```

存储：
- 不新增顶层 `state.*`；县制写 MemoryGraph（`county` 实体 + `posts/quotas` + `governs`/`belongs_to`）；事故挂在 `prefectures[parent_seat_id]["incidents"]` 子键；
- `incidents` 按 `incident_id` 幂等；读档随 `prefectures` 往返；
- **已落地（2026-10-19）**：`core/incident.py` 的 `create_incident` / `settle_incidents`；存 `prefectures[路]["seats"][seat]["incidents"]`；县官从 MemoryGraph `county_officials` 取，无则州府通判/幕职代行；`_settle_officialdom` 每回合调用；central 只到 `awaiting_decision`（不直接生成奏折）。
- 事故的 `severity` 可汇总进父级 `unrest`/`refugees` 等既有读数，但不得另开人口/钱粮账本。

处理规则：
- 地点层：有知县（池中指派）→ 知县处理；无县官 → 州府通判/幕职/巡检代行，`+1` 回合延迟与能力折扣；
- 州府：知州/知府 + 通判；本地资源不足 → `escalated` 到路省；
- 路省：按监司职权处理/跨州调度；仍不足 → 中央；
- 中央：六部/枢密/中书按事权处理；需皇帝决策 → 摘要进御前；
- 急报（兵变/边警/大灾/盗贼）可越级直送路省或中央/御前；
- 同一 `incident_id` 不重复升级/扣资源。

示例：
- **X 县水灾**：无县官 → 州府通判/幕职代行（+1 回合、能力折扣）；州府府库/常平不足 → 仓司/漕司；仍不足 → 户部/中书；需免赋/拨帑/问责 → 御前摘要。
- **某乡盗贼**：州府捕盗；跨州 → 宪司/帅司；酿成兵变 → 枢密院/御前。
- **边警**：帅司/边将 → 枢密院急报 → 御前，不等州府常规流程。

### 3.5.1 这是“奏折之前”的处理层

- 事故先由县（若记忆库有县官）/州府/路省处理；**不是所有事故都变奏折**；
- 只有处理不了、需要钱粮/人事/政策/军令/问责的，才整理成御前摘要；
- 已解决的事故只进 `monthly_gazette`/背景档，不占御前奏折；
- 原始报告 `raw_reports` 全量留档；御前只看 `summary + recommendation`；
- 奏折是“处理后的摘要”，不是事故的第一现场。

### 3.5.2 党禁在奏折前的作用

党禁首先作用于**地方官/监司/机构的事故处理与执行**，不是先作用于奏折：

- 被禁派系的地方官/监司被罢黜或限制任用 → 事故处理能力下降、代办 +1 回合、升级更频繁；
- 执行党禁的部门可能**压案/拖延/给偏向建议**（`suppressed_by_faction`/`delayed`），但 `raw_reports` 原件仍留档；
- **禁而不绝**：正式职位 capture 下降，但门生/吏员/地方网络仍在，事故执行可能被非正式网络影响；
- 党禁本身**不直接生成奏折**；只有事故升级/需决策时才生成御前摘要；
- 天道 verdict 影响执行/反噬，但不改写 `legal/procedure/fact_finding`；
- 党禁状态/`grievance`/`cohesion` 只在后台与奏报档位体现，不通过 UI 精确展示。

示例：
- **X 县水灾 + 党禁**：知县/通判被罢黜 → 州府代办（+1 回合、能力折扣）→ 府库不足 → 仓司/漕司 → 户部/中书 → 御前摘要；若党禁过激，台谏/士林事件进入反噬。
- **边警 + 军功集团党禁**：帅司/边将缺员 → 枢密院急报 → 御前；党禁不能替代调兵军令。

**已落地（2026-10-19）**：
- `core/faction_ban.py`：`start_faction_ban` / `lift_faction_ban` / `settle_faction_bans` / `is_faction_banned` / `is_official_banned`；状态写 `state.factions[faction]["ban"]`，不新增顶层 state；
- 事故单 `_county_actor` / `_prefecture_actor` / `_circuit_actor` 会**跳过被禁官员**；无可用承办官则按 `escalation_path` 升级；
- `_settle_officialdom` 每回合先 `settle_faction_bans` 再 `settle_incidents`；
- 一次性 `_event_delta` 与到期 +5 只一次；不直接写 satisfaction/cohesion；
- **未接**：`grievance/cohesion` target 修正、UI、御前摘要层。

## 3.6 御前奏折是“摘要+建议”，不是原件

用户口径：**上报的奏折理论上全部到御前，但实际大部分由各部门处理，整理后并给出建议后才到御前。**

设计成两层：

| 层 | 内容 | 是否直接呈现 |
|---|---|---|
| 原始奏报 `raw_reports` | 县/州府/路省/军报原件、事实、请求 | ❌ 不直接进 UI |
| 处理回执 `handled_reports` | 某部门已办/未办、摘要、建议、升级原因 | 部分进背景档 |
| 御前摘要 `state.memorials` | 需要皇帝决策的“摘要 + 建议 + 分歧” | ✅ 奏折区 |

**已落地（2026-10-19）**：
- `incident.settle_incidents` 到 `central/awaiting_decision` 时生成 `state.memorials` 摘要折；
- 折带 `memorial_id="mem_inc_<incident_id>"`、`incident_id`、`raw_report_ids`、`recommendation`、`priority`；
- `generate_memorials` 每回合覆盖时**保留带 `incident_id` 的摘要折**，不被新 AI 折冲掉；
- 同 `incident_id` 只生成一次。

规则：
- 所有原始奏报都留档（`memorial_id`/`report_id` 可追溯），不因“没到御前”而消失；
- 部门能处理的：记 `resolved`，只进 `monthly_gazette`/背景档，不占御前奏折；
- 部门处理不了/需要钱粮/人事/政策/军令的：整理成 `summary + recommendation` 进 `state.memorials`；
- 急报/边报/皇帝点名要看的：**越级直送御前**，但仍保留原始报告；
- 部门可以压案/拖延/给偏向建议（`suppressed_by_faction`/`delayed`），但原始报告仍在；皇帝可通过召对/勾校追问，不靠新 UI。

示例：
- X 县水灾：县（若有）→ 州府动用本地府库/常平；不足 → 路省仓司/漕司；仍不足 → 户部/中书；需免赋/拨帑/问责 → 御前摘要。
- 边警：帅司/边将 → 枢密院急报 → 御前，不等常规州府流程。
- 盗贼：县/州府捕盗；跨州 → 宪司/帅司；酿成兵变 → 枢密院/御前。

验收：
1. 事故不能跳过层级（急报除外）；每级有 `handled_by`/`escalation_path`；事故可发生在任意 `locality`，但必须挂到真实 `parent_seat_id`；
2. 原始报告全量留档，御前只看摘要+建议；
3. 下层已解决的事故不占御前奏折，只进邸报/背景档；
4. 需决策的事故进 `state.memorials` 时带 `incident_id`/`raw_report_ids`/`recommendation`；
5. 压案/拖延/偏向建议有痕迹，原件不丢；
6. 同一 `incident_id` 幂等，不重复升级/扣资源；
7. 不新增 UI；皇帝通过奏折/召对/邸报追问。
8. 无县官时不得凭空生成县官：`acting_official` 只能是通判/幕职/巡检/知县池已指派者，且带 `+1` 回合延迟与能力折扣。
9. 事故存储只在 `prefectures[parent_seat_id]["incidents"]`，不新增顶层 `state.*`。
10. 县制/县官只在 MemoryGraph：`county` 实体带 `posts/quotas/parent_seat_id`；县官用 `governs` 关系；读档往返保留。

## 4. 怎么上奏（当前 schema）

`generate_memorials` 白名单只接受：

```python
kind ∈ {invention, governance, military, personnel, finance}
title, body
# invention 额外：name, effect_dim, effect_tier
```

模板额外字段：`source_tag`、`official`、`guarantor`、`_fallback`。

**没有**：`memorial_id`、`submitted_by`、`channel`、`channel_matter`、`target`、`accusers`、`evidence_refs`、`created_turn`、`status`。

## 5. 哪些呈现、哪些背景板

### 呈现给玩家

- `state.memorials`：`GovernanceHub` 奏折列表，准奏/留中；
- `state.ai_pending_actions`：`PendingActionsPanel` 朱批待阅；
- `state.edict_drafts`：会签/下诏。

### 背景板（不直接呈现为奏折）

- `scan_memorial_seeds`：只作为提示词事实签；
- `summarize_monthly_omen`：月报叙事；
- `short_term_log` / `memory`：召回与日志；
- `official_stats` / `faction_voice` / `permission_capture`：读数；
- `central_orgs` 的 scope/authority：制度背景，不是奏折正文；
- `monthly_gazette` / `briefing`：邸报/简报，另一条叙事通道。

## 6. 缺口与风险

1. **无上奏资格门**：任何 AI/模板生成的折子都能进 `state.memorials`，不校验 `奏章进纳/邸报通达/民隐通达`。
2. **无路由**：通进/进奏/登闻只作为 `source_tag`，没有按渠道决定“谁呈、呈给谁、是否留中/封驳”。
3. **无 `memorial_id`**：准奏/留中用 index；前端 busy 只能防连点，后端无幂等。
4. **每回合覆盖**：未批奏折下回合被覆盖，没有归档/积压；`central_orgs.backlog` 也未接。
5. **人物不校验**：`official/guarantor` 可能是死者/罢黜者/无此官；未走 `MINISTERS`/holder 校验。
6. **无弹章字段**：`kind` 白名单没有 `impeachment`；`accusers/target/evidence_refs` 无法承载 M3a。
7. **`ai_pending_actions` 与 `memorials` 易混**：一个 409 守卫、一个奏折批红，玩家可能以为“批了奏折就办了事”。
8. **背景板未沉淀**：事实签/天象/机构读数没有转成“可查的奏报档”，也没有“谁压了哪条”的记录。
9. **地方官没有上奏入口**：`circuit_officials`/`prefect_officials` 未进入 `scan_memorial_seeds` 或 `memorials`。
10. **军报没有独立通道**：只有泛 `military` 折；未读 `army_units` 士气/欠饷/边防；军报与军令未分离。
11. **无优先级/延迟**：急报、边报、常规月报混在 3 条里；没有驿传距离延迟，也没有“急报挤占常规折”的规则。
12. **事故单已落 M1（2026-10-19）**：`core/incident.py` 已有 `create_incident`/`settle_incidents`/`escalation_path`，存 `prefectures[路]["seats"][seat]["incidents"]`；**尚未接**党禁对地方官处理能力的影响、御前摘要层。
13. **原件与摘要未分层**：没有 `raw_reports`/`handled_reports` 全量留档，御前只能看到 AI 生成折，无法追溯“谁办的/谁压的”。

## 7. 建议口径（设计，不实现）

### 7.1 上奏资格

- 通进银台司：持 `奏章进纳` 的在任者，可汇总/进纳天下章奏；
- 都进奏院：持 `邸报通达` 的在任者，可上地方邸报/情状；
- 登闻鼓院：持 `民隐通达` 的在任者，可转呈庶民直诉；
- 台谏：持 `监察百官`/`言路` 的在任者，可上弹章/谏章；
- 中枢大臣：按本职位事权上奏（户部财政、枢密院军事等）；
- 路/州主官：经都进奏院/通进银台司转呈，不直接入御前。

### 7.2 路由

```
地方/庶民 → 都进奏院（邸报）或 登闻鼓院（直诉）
        → 通进银台司（汇总/进纳）
        → 门下省（封驳/审议）
        → 御前（state.memorials）
```

台谏弹章走 `御史台/谏院`，不经过“民隐”渠道；财政/军事实体奏报走对应机构。

### 7.3 呈现分层

- **御前奏折**：`state.memorials`，只放“需要皇帝朱批”的；
- **待批提议**：`ai_pending_actions`，只放“AI/大臣提议、需批红”的；
- **背景档**：`scan_memorial_seeds`/`summarize_monthly_omen`/`short_term_log`，不直接进奏折列表；
- **邸报/简报**：`monthly_gazette`/`briefing`，只读叙事，不进批红队列。

### 7.5 UI 边界

- **不新增 UI、不改现有面板**；

## 8. 与党禁/弹劾的接口

- 弹章：`kind="impeachment"` + `accusers/target/evidence_refs` → `accept_memorial` 只开案，不直接罢官；
- 党禁：不新增 UI；执行/民情/士林反应通过奏折、召对、机构奏报进入御前；
- 天道：`scan_memorial_seeds` 仍是事实签来源，`summarize_monthly_omen` 只做月报，不直接生成弹章证据；
- 所有队列仍用 `memorial_id`/`behavior_id`/`event_id` 做幂等。
