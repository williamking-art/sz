# 阶段 1 产出：模块依赖图与循环依赖（实测）

> 2026-10-06 · 承架构方案 §8 阶段 1「稳定入口与依赖图」。
> **本文件是实测结果，并更正阶段 0 的错误结论。**

## 🔴 更正：阶段 0 报告「循环依赖 = 0」**是错的**

```
SCC count = 2
  [18] asset_context, blueprint_dynamic, commands, commands_decree, construction,
       events, focus_mechanic, game_state, longterm_task, plan_commit, save_load,
       settlement, settlement_decree, settlement_econ, settlement_granary,
       settlement_imperial, settlement_military, settlement_steps, settlement_tech
  [ 2] faction_basis, faction_metrics
```

**根因**：阶段 0 的扫描脚本把「模块级 import」当成**有向无环图**处理，
但**函数内延迟导入**（`from core.X import Y` 写在函数体内）同样形成真实依赖边，
而阶段 0 用了**不同的匹配逻辑**（只认 `ast.ImportFrom.module` 以 `core.` 开头，
漏了 `import core.X` 形式与部分条件分支），导致边集不完整 ⇒ 假 0。

## 五、现存反向边与替代接口（§8 阶段 1 第 3 项）

| 源模块 | 反向依赖（更高层）| 替代接口方向 |
|---|---|---|
| `save_load` | `blueprint_dynamic` `longterm_task` `plan_commit` `settlement_imperial` | 存档应只依赖**状态 schema**，业务装配交 `foundation/state` 注册 |
| `commands_decree` | `settlement` `settlement_steps` | 政令用例应调**政令服务**，不直接碰结算编排 |
| `asset_context` | `settlement_steps` | 读数应从**读数服务**取 |
| `construction` | `blueprint_dynamic` | 建造应调**蓝图注册表**接口 |
| `focus_mechanic` | `settlement_steps` | 同 `asset_context` |
| `game_state` | `settlement_imperial` | 🔴 违反 §6-4「基础状态避免导入业务包」，须**函数内延迟装配** |
| `settlement_imperial` | `events` | 结算步应只发**领域事件**，不反向调编排 |
| `settlement_steps` | `settlement` | 同上，编排只应由 `settlement` 持有 |

**合计 12 条反向边**，全部集中在 18 模块环内。

⇒ **阶段 3（结算域）的前置条件**是先把这些边改成接口调用，
否则移动文件只会把环从一个位置搬到另一个位置。
