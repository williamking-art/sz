# G-3 粮与粮仓设计稿 v2（2026-10-18）

> 状态：**设计稿 v2，未实施**。取代同日 v1（v1 把「粮」做成固定成员类目，方向做窄了）。

## 0. 用户口径（本轮澄清，作为设计前提）

> 「因为粮食也是商品，而米面麦也是粮食，而面又是中间产物，还能继续精加工，这一条是连贯的；
> 只不过因为朝廷、民间都会屯粮，现在是要解决这个问题；粟/菽就不必再细分了；
> 但我个人认为，粮仓就是粮的仓库，不管是米面麦，还是红薯、玉米，都应该能存。」

拆成四条设计约束：

1. **粮是商品**：它和盐、铁、布一样走 goods 通道，不是特殊字段；
2. **粮是开放集合**（属性判定，不是白名单）：米/麦/面/稻/粟… 只要 kind=粮 就算粮；
3. **面是中间产物**：麦→面→（饼/点心…）是可继续的加工链，所以「粮」不能是一个闭合成员表；
4. **核心要解决的是「屯粮」**：朝廷（太仓/常平）与民间（POP 自储）都要能存，
   **仓就是仓**——同一座粮仓里可以混存米/面/麦等任何粮类商品，共享容量。

⚠️ 史实纪律：玉米、红薯是明清作物，**宋境不立此维**；它们只是「机制上必须能存」的举例。

## 1. v1 错在哪（记录以免重犯）

| v1 做法 | 问题 |
|---|---|
| 把「粮」做成 `GOODS_CLASSES` 的**固定成员表**（米/麦/面） | 面是加工中间产物，将来还会出饼干/酒曲；加一种粮就要改类目定义 |
| 把「面」标成 `active=False`（未立维） | 面不是"没资格"，是"链上还没有人生产它" |
| 只谈 `pops[].grain → goods[米]` | 用户真正的诉求是**仓容与屯粮**，不是换个字段存哪 |

**保留**：`grain_of` 走 `class_total` 的写法方向（读口单点）；但成员判定要改为**属性**。

## 2. 数据模型（三张表，全部在 content 层）

### 2.1 商品属性表 `COMMODITY_KINDS`

```text
COMMODITY_KINDS = {
    "米": "粮", "麦": "粮", "面": "粮",          # 粮类；面为中间产物
    "稻": "粮",                                   # 未脱壳，可入粮仓
    "盐": "原料", "铁": "原料", "木": "原料",
    "布": "成品", "绸": "成品",
    "兵刃器械": "军需", ...
}
```

- **判定单点**：`is_grain(dim) <- COMMODITY_KINDS[dim] == "粮"`；
- **开放**：新增一种粮 = 在表里加一行，**不动任何代码**；
- 未登记维 ⇒ 按「非粮」处理并告警（缺失 ≠ 默认是粮）。

### 2.2 加工链表 `PROCESS_CHAINS`（面只是其中一环）

```text
PROCESS_CHAINS = {
    "面":  {"inputs": {"麦": 1.0}, "rate": 0.80, "kind": "粮"},   # 麦→面（rate 待史料核校）
    "酒":  {"inputs": {"米": 1.0}, "rate": 0.30, "kind": "成品"},
    # 将来：饼/点心/酒曲…只需加一行
}
```

- 面既是「粮」（能进粮仓），又是「中间产物」（能继续加工）——**两个属性不冲突**；
- 换算率**没有史料依据就留空**，引擎不做隐式换算。

### 2.3 仓 `GRANARY`（本轮真正的主题）

**统一抽象**：一座粮仓 = `{dim: qty}` + `cap`（容量，单位石）。

| 归属 | 载体 | 说明 |
|---|---|---|
| 民间 | `pops[cls]["granary"] = {米: x, 麦: y, ...}` | 替代现在的标量 `pops[cls]["grain"]` |
| 朝廷 | `state.granaries[路][仓名] = {米: x, ..., cap: N}` | 太仓/常平仓/转运仓各自一座 |
| 派生 | `grain_of(pop)` = Σ `granary` 中 kind=粮 的项 | 旧读数与旧规则全部走它 |

**关键约束**：

1. **容量共享**：仓内所有粮共享一个 `cap`（石）；混存米麦面不额外占容量；
2. **准入判定**：只有 `kind=粮` 的商品能进粮仓；非粮（盐/铁）不得入 → 写入即报错（不是静默丢弃）；
3. **溢出规则**：满仓时**不静默丢粮**——返回实际入仓量，调用方按返回值记产出（沿用 `_write_warehouse` 的既有纪律）；
4. **腐损按维**：陈化率可按维不同（米/麦/面各不相同），但计损后总量仍守恒；
5. **单一真账**：仓就是账，`pops[].grain` 彻底改为派生只读。

## 3. 屯粮（用户痛点）怎么落

现在"粮只有一个标量"，所以**屯粮无从谈起**：既看不到囤了什么，也无法表达"囤米还是囤面"。
改后：

| 诉求 | 落地方式 |
|---|---|
| 朝廷屯粮 | 太仓/常平仓 = 带容量与分维库存的实体；丰籴歉粜按仓位与库存操作 |
| 民间屯粮 | POP `granary` 分维库存 + 留存率；饥荒时先吃自家仓 |
| 混存 | 同一仓内米/面/麦并列，共享 cap |
| 调运 | 仓→仓按维搬运，**每笔可追踪**（这正是"运没运到"能观测的前提） |
| 加工 | 面从麦磨出，入同一座粮仓；下游（饼/酒）继续消耗面 |

### B. 损耗口径改为「天道裁决档位 × 程序查表」

现状（读码）：`settlement_granary.py:136` `sparrow = int(state.granary * SPARROW_RAT * outflow_mult)`

正确形态（符合「AI 只出档位、数值由程序算」）：

| 角色 | 职责 |
|---|---|
| 天道 | 裁决本月**仓储条件**档位：`无 / 轻 / 中 / 重`（鼠患、霉变、兵燹、仓吏贪墨叠加） |

档位倍率（程序常量，非 AI 给数）：`无=0.0 / 轻=0.5 / 中=1.0 / 重=1.8`。

## P3 理清：三层仓的真实结构与改法（2026-10-18）

### 一、现状实测（new_game 后）

| 层 | 治所数 | 有仓的治所 | 库存合计 | 说明 |
|---|---|---|---|---|
| 州府（治所） | **117** | **20** | 6,010 万石 | 只有每路的**治所**有仓，其余 97 个州府**无仓** |
| 路 | 20 | — | — | **没有独立路仓**；20 座治所仓事实上就是路级枢纽 |
| 中央（太仓） | 1 | 1 | 1,500 万石（容量 2,000 万） | `state.granary` / `granary_cap` |

关键发现：**现有 20 座仓"位置在州府、语义是路仓"**——它们恰好每路一座、集中在治所，
且漕运代码就是逐路从 `p["storage"]` 抽粮直送太仓（`state.prefectures[route]["storage"]`）。

⇒ 所以 P3 **不是从零建三层**，而是：
1. **承认**现有 20 座为**路级转运仓**；
2. **补 97 座州府仓**（117 − 20）；
3. 在州→路之间**加一段上解**（今天没有这一段，田赋直接进"路仓"）。

### 二、目标结构（单点：`granary3tier.py`）

```text
州府仓  state.prefectures[路]["seats"][治所]["storage"]        117 座（已有 20，补 97）
路级仓  state.prefectures[路]["route_granary"]                  20 座（新字段，承自现有 20 座库存）
中央仓  state.granary / state.granary_cap                        1 座（不动）
```

三个访问入口（单点，禁止绕过）：`granary_get/set/add(layer, route, seat, dim)`，
内部按层路由到上述载体；`granary_report(state)` 出三层盘点。

### 三、容量口径（Jev 已裁 + 本轮补充）

| 层 | 容量 | 依据 |
|---|---|---|
| 州府仓 | 该州府人口 × 人均石数（常量 `GRANARY_POP_PER_CAPITA`） | Jev 0.623（人口口径，可解释、随人口伸缩） |
| 路级仓 | Σ该路州府仓容量 × 0.5 | 转运枢纽只周转不囤积 |
| 中央仓 | 沿用 `GRANARY_START_CAP`（可经工程扩建） | 既有 |

### 四、三段搬运（P3b/P3c 才动，P3a 不动）

```text
[田赋/产出] → 州府仓 --上解(效率 A)--> 路级仓 --漕运(效率 B, 途耗 CANAL_LOSS_BASE)--> 中央仓 → 支出(P2c 闸门)
```

- **上解效率 A**：新增常量（如 0.15/月，逐州按余粮比例上解，不掏空州仓）；
- **漕运效率 B**：沿用现有 `canal_eff = CANAL_MONTHLY_RATE × (1 − block/100) × inflow_mult`；
- **途耗**：州→路按 0（短途）、路→中央按 `CANAL_LOSS_BASE + 贪腐×权重`（既有）。

### 五、守恒断言（P3a 就要能跑）

| 断言 | 形式 |
|---|---|
| 层内守恒 | 迁移前后：`Σ州仓 + Σ路仓 + 中央` 不增不减（迁移只是搬家） |
| 逐段搬运守恒 | 每次搬运：`Δ源 + Δ目标 + 途耗 == 0` |
| 全局守恒 | `期末三层合计 == 期初 + 产出 − 消费 − 损耗 − 途耗` |
| 容量约束 | 任何一层 `库存 ≤ 容量`，溢出时**返回实际入仓量**（不静默丢） |
| 幂等 | 迁移连跑两次结果逐字节相同 |

### 八、这轮为什么不直接动手

## P3 修正（2026-10-18 用户提问：「现在不是有货运的交通路径吗，粮银钱不能用吗」）

### 查证结果：交通层早就有了，而且已被强制用于跨路

| 设施 | 位置 | 能力 |
|---|---|---|
| 交通边 + 在途批次 | `core/transport.py` | `route_days(frm,to)`（按经纬算天数，未登记路线返回 None，**不瞬移**）；`dispatch(state, frm, to, dim, qty)` 立刻扣源、建批次、`arrive_month` 才入账；`arrive_due(state)` 到期入账；`in_transit()` / `transit_report()` 可查在途 |

| 中央太仓 | `state.granary`（标量） | ❌ |

⇒ **粮要先变成 `goods[米]` 这类商品维，transport 才搬得动** —— 这就是 G-3 迁移。

银/铜/官铸铜钱**已在 `GOODS_DIMS` 里**（可 dispatch）；但国库 `state.treasury`（贯）是另一本账，
要搬"国库银钱"需单独裁定" treasury 是否落 goods"，不在本轮。

## P4 理清：钱能押运，交子才有意义（2026-10-18 用户指示）

> 「钱也要能押运，这样交子的存在就有意义了」

### 一、现状（实测/读码）

| 项 | 现状 | 位置 |
|---|---|---|
| 国库 / 内帑 / 地方府库 | 三个标量，调拨**瞬时**（`local_treasury += money`） | `settlement_common.py:212/313` |
| 民间持币 | `pops[].wealth`（铜钱+交子按 `copper_share` 拆分） | `money.py` M0 口径 |
| 白银 | `state.silver_stock`（存量） | 同上 |
| 交子 | **有完整参数**：issued/reserve/trust/circulating/redeem_rate/discount/run_pressure/tax_acceptance/credit_ceiling；界制 36 回合、换界 5% 工墨费销毁；发行上限 = 准备金 × 皇威 × 税收接受度 × 信用上限 | `content/data.py` 交子块、`money.py` |

**关键事实**：交子目前**只影响货币供给与通胀**，与"运输"毫无关系——因为没有运输成本，
纸券省不下任何东西，交子就退化成一个利率旋钮。这正是用户指出的"没意义"。

### 二、逻辑链（为什么押运是交子意义的前提）

```text
钱能运（有运费 + 时效 + 途耗 + 被劫风险）
      ⇒ 异地支付出现三种方式，各有代价：
         ① 运现钱：到得慢、路上有损耗/被劫、占运力
         ② 交子汇兑（便换）：A 地存钱→持券→B 地取钱，省运费省时间，但依赖兑付信用
         ③ 官发交子（交子务）：加税收接受度与界制约束
      ⇒ 商民按「运费+途耗+误期损失」与「手续费+折价+挤兑风险」比价
      ⇒ 运输越难（路远/盗匪/漕淤），交子越受欢迎；信用越差，越退回运现钱
```

这就是交子的存在意义：**它是运输成本的替代品**，而不是一个独立的货币开关。

### 三、设计要点

#### 3.1 钱作为 cargo

- `cargo = {kind: "money", dim: "coins"|"silver", qty, unit: "贯/两"}`；
- 持有方适配器：`state.treasury` / `state.imperial_treasury` / `seat.local_treasury` / `pops[].wealth`；
- 运力占用：贯 → 重量 → 船/车（沿用 `logistics_coupler` 的 barge 池）；
- 成本三件套：**运费**（里程 × 重量）、**时效**（`route_days`）、**风险**（途耗/被劫，见 3.4）；
- 押运：复用 `hire_escort_guard`（保费 1%–3%，降低被劫概率）——钱和货共用同一套押运。

#### 3.2 交子两种用途（对应宋代史实）

| 用途 | 机制 | 收益 | 代价 |
|---|---|---|---|
| **存款凭证** | 交子铺收钱发券，异地/异时兑付 | 免于携钱 | 铺户信用 |
| **汇兑便换** | A 地纳钱 → B 地取钱（官营便换或交子务） | 替代运钱，省运费与途耗 | 手续费、兑付能力 |

机制上只需两个新动作：`issue_draft(state, from_seat, to_seat, amount)`、`redeem_draft(state, draft)`；
兑付失败 ⇒ 复用现有 `discount`（折价）与 `run_pressure`（挤兑）字段，不新增账本。

#### 3.3 守恒与口径（关键，别破坏 M0–M3）

| 动作 | 货币口径变化 | 断言 |
|---|---|---|
| 运现钱 | 持有者不变、位置变 ⇒ **M0 不变**（在途仍属原持有方） | `Σ源 + 在途 + 到账 == 常数` |
| 交子发行 | 发行方负债，不计入 M_ALL（既有口径）；流通额 = issued × trust/100 | 发行 ≤ 准备金 × 皇威 × 税收接受度 × 信用上限 |
| 汇兑 | 不动 M0，只改持有者（A 的钱 → 铺户准备金；B 取现 → 准备金 → B） | 准备金不足 ⇒ 兑付失败，不得凭空造钱 |
| 换界 | 5% 工墨费销毁（既有销币通道） | 销毁量 = 在发额 × 5%，记 `redeemed_total` |

#### 3.4 途耗/被劫：不臆造

钱在路上被劫/损耗**没有史料比例可依**，故：
- 默认 **0**（不凭空消失）；
- 只有**天道档位/事件**（盗匪、兵乱、漕淤）才产生损失，走既有"档位→程序查表"模式；
- 押运（镖局）降低被劫**概率**，不改变"无故不损耗"原则。

### 四、分步实施

| 步 | 内容 | 行为变更 |
|---|---|---|
| **P4a** | transport 支持 `cargo.kind = money`（treasury/local_treasury/POP wealth 适配器）+ 运费/时效/押运 + 守恒门 | 无（新接口不被调用） |
| **P4b** | 国库→地方拨付改走 `dispatch`（在途，到账才可用） | 有：拨款不再瞬时 |
| **P4c** | 交子汇兑：`issue_draft` / `redeem_draft` + 手续费 + 兑付失败→折价/挤兑 | 有：交子开始替代运钱 |
| **P4d** | 宏观联动：运钱需求 ↔ 交子流通（进物价/信用读数与面板） | 无（只读） |

### 五、需要你拍的一点（其余我自定）

**P4b 是否允许"国库拨款在途"**：
- 允许 ⇒ 拨款次月才到账（真实，但玩家下赈济令后可能"钱还没到"）；
- 不允许 ⇒ 只有**大额/远距离**拨款走押运，小额仍即时（避免操作摩擦）。

## P4b 理清：钱粮远端调拨的真正前置是「路由」（2026-10-18）

### 一、实测发现（比预想严重）

`core/transport.route_days()` **只认相邻州府**（`ADJACENT_KM = 200km` 阈值内），
超过即返回 `None` = **不通**，且模块注释明确「不做全图任意互通」。

实测：从京师开封府出发，

| 路 | route_days |
|---|---|
| 京畿路 | 0 |
| 京西路 / 河北路 | 1 月 |
| **两浙路 / 江南东西路 / 广南 / 成都府…** | **None（不通）** |

⇒ **当前交通网只能"相邻两州府"直运**；`dispatch_money`（P4a）因此对绝大多数跨路调拨会直接
返回 `route_undefined`。我把 P4b 写成"改拨付调用点"，前置条件其实不成立。

### 二、规模实测（说明为什么必须解决）

| 账户 | 期初 |
|---|---|
| 国库 | **500 万贯** |
| 内帑 | 100 万贯 |
| 地方府库合计 | **1,644 万贯**（两浙 195 万 / 江南西 144 万 / 江南东 135 万）|

而钱是重货：按「1 文铜钱 ≈ 4g、1 贯 = 1000 文」估算，**1 贯 ≈ 4kg**（**估算，非史料**），
50 万贯 ≈ **2,000 吨**——远超单船单队，**大额调拨物理上必须靠银或交子**。
这恰好就是交子的位置：不是"可选便利"，而是**大宗远运的唯一解**。

### 三、修正后的三步（顺序不可颠倒）

| 步 | 内容 | 产出 |
|---|---|---|
| **P4a'（新增前置）** | **邻接图最短路**：`route_path(frm,to) → {path, days, km}`；不可达 ⇒ `None`。只读、纯函数、零行为变更 | 任意两治所可判"怎么走、几天到；走不通就明说" |
| **P4b** | **多段押运**：一批钱/粮沿 `path` 逐段 dispatch，到中转治所续发（在途链）；中转仓暂存与续发规则 | 全国调拨真正可走，且每段可查 |
| **P4c** | **交子便换**：大额远运的替代路径（`issue_draft/redeem_draft`），与运钱比价 | 交子有存在意义 |

### 四、路由层设计（P4a'，最小可行）

- 图：节点 = 117 治所；边 = 距离 ≤ `ADJACENT_KM` 的相邻对（与 `is_adjacent` 同源，不另造）；
- 权重：边权 = 距离 km（耗时 = `km / KM_PER_MONTH` 取整，与既有口径一致）；
- 算法：Dijkstra（117 节点，毫秒级；结果按 (frm,to) 缓存）；
- **不臆造**：不可达返回 `None`（例如海外/孤岛/边疆无驿路），绝不"按直线距离凑"；
- 读数：`route_path` 返回 `{reachable, path, days, km, hops}`；`None` 与"0 天"严格区分。

### 五、对既有代码的影响

| 项 | 影响 |
|---|---|
| `transport.route_days` | **不改**（保持"只判相邻"，有 6 处调用方依赖该语义）；新增 `route_path` 与之并列 |
| `dispatch` / `dispatch_money` | 增加"沿路径多段"的上层封装（`dispatch_along`），单段接口不变 |
| 测试 | 现有 3535+ 用例不动；新增路由门（连通性/不可达/天数量级/缓存一致性） |

### 六、待验证的风险

1. **连通性**：117 席 × 200km 邻接图是否连通（若分裂成几个孤岛，远端调拨仍不可行）——本轮先测，
   若断裂则需在**史料/地理**上补边，不得为凑连通性硬连；
2. 多段续发会放大批次数量（一段一批），需给"在途批次上限"与合并规则；
3. 交子便换要与货币口径（M0/M1）对齐，不能凭空增发。

## P7 理清：AI 接线的一致性（生产者 ↔ 消费者）

### 一、三类不一致（按成本/影响分级）

| 类型 | 实例 | 现状 | 成本 | 影响 |
|---|---|---|---|---|
| **有生产者、无消费者** | `_finance_ai` / `finance_decide` | `AGENT_DEFS` 里 `wired: False`，`route_agents` 三处守卫跳过 ⇒ **当前不唤醒、零 token** | 现 0；但配置仍在 `token_meter` 推演列表里，**改回 True 就白烧** | 误导后来者；「财政天道」名存实亡 |
| **有消费者、无生产者** | `_reform_ai` / `reform_decide` | 结算侧 `settlement.py:329` 读该槽位，但**契约方法不存在** ⇒ 永久本地兜底 | 0 | 天道挂点空转，「变法受天道影响」是假的 |
| **产销皆无** | `_invest_ai` / `invest_decide` | `estate_mechanic.invest()` **无调用方** + 契约未接线 | 0 | 整条投资子系统未落地，却在生产代码里留假挂点 |

### 二、为什么会这样（历史成因，记录以免重犯）

1. 2026-09-27 审查 P2-35 批量接线时，先给结算侧加了 `getattr(state, "_*_ai")` 消费点，
   契约/入口有的后补、有的没补 ⇒ 出现「半边接线」；
2. `_finance_ai` 更严重：**生产者（唤醒+LLM 调用）先写、消费者后没写**，一度每回合真烧 token，
   于是被打上 `wired: False` **停用**（治标），但配置与 `token_meter` 条目没删 ⇒ 留下"看起来能开"的雷；
3. `_invest_ai` 的入口 `invest()` 从一开始就没有调用方，属于**先建接口后没接功能**。

### 三、治理方案（分级，按性价比排序）

| 项 | 方案 | 理由 |
|---|---|---|
| **A. 加一致性门**（先做） | 静态扫描：每个 `settle_attr` 必须「有生产者 ⇔ 有消费者」；不一致且未登记在 `PENDING_CONTRACTS` ⇒ 门红 | 一次性根绝「半边接线」，成本最低、收益最高 |
| **B. `_finance_ai` 处置** | **先彻底断开**（从 `AGENT_DEFS` 与 `token_meter` 移除，说明留在 PENDING）；将来要「财政天道」时，**先设计落点再一起接** | 避免"改回 True 就白烧"；财政档位落点（税率/支出/铸币）属口径变更，应单独裁定 |
| **C. `_reform_ai`** | 补 `reform_decide` 契约（档位：变法力度/阻力反馈），或在文档显式标「未接线·本地兜底」并进门白名单 | 让"天道影响变法"名副其实 |
| **D. `_invest_ai`** | 登记为「未落地子系统」，从生产挂点移除或标 TODO；等投资功能真正做时再接线 | 不留假挂点 |

### 四、一致性门设计（A，可直接实施）

```text
扫描 game/application/agent_router.py：
  AGENT_DEFS: name -> {method, settle_attr, wired}
  PENDING_CONTRACTS: [(attr, method, note)]
检查 1：每个 settle_attr 在 game/core/** 至少被 getattr 一次（有消费者）
检查 2：每个被读的 _*_ai 槽位，要么在 AGENT_DEFS（有生产者），要么在 PENDING_CONTRACTS（已登记）
检查 3：AGENT_DEFS 中 wired=False 的项必须出现在 PENDING_CONTRACTS
检查 4：PENDING 中「有生产者无消费者」的项必须与 token_meter 一致（要么都留、要么都删）
任一不满足 ⇒ 门红，输出「哪个槽位、缺哪一半、应补契约还是该删」
```

### 五、成本量化（当前）

- `_finance_ai`：`wired=False` ⇒ **当前 0 次调用 / 0 token**；
- 若被改回 `wired=True`：按唤醒条件（`treasury < 0` 或财政关键词）会在财政恶化的回合**每回合调用一次**，
  属"长期白烧"，且 `token_meter` 已把它算进「推演」配额（更隐蔽）；
- 对应地，`transport_decide`（P5d 新增）**必须在设计消费语义之后才加入 AGENT_DEFS**，
  否则会复制同一个坑。

### 六、结论

**先做 A（一致性门），再做 B（断开 `_finance_ai`）**；
C/D 各自独立排期，不急。运输系统的 `transport_decide` 按「先设计消费者、再加生产者」接入。

## P5a 落地：多跳路由（2026-10-18）

新增 `core/transport.py::route_path(frm,to)`（Dijkstra，边权 km，与 `is_adjacent` 同源同阈值）：

| 情形 | 返回 |
|---|---|
| 未知治所 | `None`（读不出） |
| 同点 | `{reachable:True, path:[点], km:0, days:0, hops:0}` |
| 相邻 | 与既有 `route_days` **天数一致**（门已钉） |
| 远端 | 多跳路径 + 总里程 + `ceil(km/1000)` 天，**每跳 ≤200km** |
| 不连通 | **显式 `reachable:False`**（不是 None、不回落 0、不臆造直线） |

### 连通性实测（136 治所）

| 项 | 实测 |
|---|---|
| 连通分量 | **3 个**：133 / 2 / 1 |
| 分裂原因 | `广南西路\|琼州` + `广南西路\|雷州` 成 2 点孤岛；`广南西路\|邕州` 孤立 |
| 主体可达 | 133 席互通；例：台州→熙州 **15 席 / 2,148km / 3 月 / 14 跳** |

⇒ 主体地图连通，**海南/邕州需要海运或驿路补边**——正好落在 P5b 的 `sea` 模式，
**不硬连**（无史料不臆造地理）。

### 门（7 条，全绿）

相邻天数==route_days · 远端多跳且每跳 ≤ 阈值 · 里程/天数一致 · 未知⇒None · 同点⇒0 · 对称+缓存一致 · 不连通显式 False · 连通性报告自洽。
