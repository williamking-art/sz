## 0. 裁决总纲

### 0.1 五条不可退让的红线

1. **权限挂在职位上**：在任职位即有该职位事权；免职/空缺即失去；兼职取并集。部门只是职位集合与默认归属。
2. **皇权可以覆盖程序，但不能凭空创造事权/资源/军队/职位**。直行必须仍校验目标合法与物理约束，并留下「绕过了什么」的记录。
3. **三关状态不得互相冒充**：`returned` 不等于 `blocked`，`resisted` 不等于 `returned`，`failed/claimed` 不等于 `executed`。
4. **默认中性**：旧调用不显式携带新字段时，旧行为逐位不变；新逻辑只从明确的显式入口进入。
5. **一切政治后果可追溯**：必须能追到 `decree_id`、`case_id` 或 `event_id`；同一 id 不得重复施加。

### 0.2 本轮裁决摘要

| 优先级 | 裁决 | 一句话 |
|---|---|---|
| **P0** | 接受 Lead 提出的 **A′** | `institution.check_authority` 保留为参数型旧口径；新增 `authority_gate` 做 actor 判权；`decree_confirm`、`issue_decree`、`settle_reform`、调兵检查迁到新门；`apply_reform` 暂留旧门并标 `legacy_authority` |
| **P1** | 财政入口分批 | 第一批只做 **`free_effect.didang` actor 判权** 与 **`repay_local_arrears` 的国库/度支调度门**；其余财政入口列清单后分批 |
| **P2** | M2a 最小诏令三关 | 只做 `issue_decree` 显式事权路径；先支持 `官吏铨选`、`度支调度` 两键；实现 `resisted` 三期与幂等；`partially_executed` 延到 M2b |
| **P3** | M3a 最小弹劾闭环 | 先做 **路/州主官** 一条链：弹章→立案→证据审查→建议→圣旨处置→人事实体落地；不做中枢官批量、不做公式化的派系影响 |

### 0.3 已核对到的关键代码事实

- `institution.check_authority` 生产调用点只有 2 个：`core/decree_confirm.py:679`、`core/domains/administration/institution.py:282`（`apply_reform` 内）。
- `institution.require_matter` 当前 **0 生产调用点**；人事入口已经改走 `permission_model.personnel_authority`。
- 旧 `resolve_executor` 仍有 4 个业务调用点需要迁移：`commands_decree.py::_decree_authority_check`、`settlement.py::settle_reform`、`commands.py::issue_military_order`、`decree_confirm.py` 的 `enforce_troops` 检查。
- `decree_confirm` 的 `can_act` 只校验官员 Agent 在朝 + 通用 authority 数值，不校验具体事权；具体事权必须由新的 actor 判权门补上。
- `settlement_decree.py::_settle_decrees` 现有执行仍是 `random.random() < rate`，不是 `state.turn + TianDaoEngine.dice`；M2 新路径必须改确定性掷点，旧路径不动。
- `free_effect._apply_free_effect` 当前先做成本预检，再调用 `_apply_effect_to_state`，最后 `_pay_cost`。若只在 `_apply_effect_to_state` 内拒绝，**成本仍可能被扣**。P1a 必须把权限预检放到成本扣除之前。

## 1. P0：M1b-3d 旧口径迁移

### P0-1 结论：接受 A′，拒绝 B/C

**结论**

1. `institution.check_authority` **不改成 actor 判权**，保留为**参数型旧口径门面**，只服务 `apply_reform`/旧测试兼容。
2. `institution.require_matter` 保留但标记 **deprecated / 0 新调用**；新代码不得再调用。
3. 新增 `game/core/authority_gate.py`，作为**玩家诏令/确认/改革/调兵**的 actor 判权唯一门面：
   - `check_matter_authority(state, executor, matter) -> (ok, label_or_reason)`
   - `check_decree_authority(state, key, executor) -> (ok, label_or_reason)`（`key` 先用 `institution._matter_of(key)` 映射到事权）
4. 迁移业务调用点：
   - `core/decree_confirm.py::confirm_decree` 第 679 行：改调 `authority_gate.check_decree_authority(state, _auth_key, aid)`。
   - `core/commands_decree.py::_decree_authority_check`：对 `primary_matter`/`co_matters` 逐项调用 `check_matter_authority`，不再用 `resolve_executor` 返回的机构事权集合。
   - `core/settlement.py::settle_reform`：改调 `check_matter_authority(state, executor, "官吏铨选")`。
   - `core/commands.py::issue_military_order`：改调 `check_matter_authority(state, executor, "调兵")`。
   - `core/decree_confirm.py` 的 `enforce_troops` 分支：改调 `check_matter_authority(state, aid, "调兵")`。
5. `apply_reform` 暂不迁移，继续调用旧 `check_authority(state, key, executor)`；这是**参数型旧门**，不是无校验。

**理由**

- `test_domains_administration_b19::test_new_home_is_a_leaf` 禁止 `institution.py` import `core.*`，所以不能把 `permission_model` 塞进 `institution.py`。
- `test_domains_administration_b19::test_authority_gating_unchanged` 明确把 `check_authority(s, "didang_loan_rate", "枢密院") is False`、`{"post":"抵当所提举"} is True` 当作旧口径钉死；直接改写会制造无谓回归。
- `decree_confirm` 的 `aid` 本来就是**受命人/actor**，不是部门；它最该走 actor 判权。
- 方案 B（迁出 `apply_reform`）改动大、会触碰 B19 冻结面；方案 C（放宽叶子规则）会削弱架构测试，均不采纳。

### P0-2 旧调用兼容与 `legacy_authority` 标记

**结论**

- `apply_reform`/`free_effect` 中尚未迁移的**参数型**路径，继续使用 `institution.check_authority`，但必须显式标为旧口径：
  - 代码注释与 docstring 标 `legacy_authority: department/post parameter gate`；
  - `apply_reform` 对受事权约束的参数，在日志行加固定后缀 `（legacy_authority）`；无 `authority` 字段的参数不加。
- `free_effect` 的长期制度条目（`state.longterm_effects[*]`）若仍走旧门，记 `authority_mode="legacy_department"`；迁到 actor 门后记 `authority_mode="actor_position"`。这是**已有容器内的字段**，不新增顶层 `state.*`。
- 不新增 `state.legacy_authority` 一类全局字段；默认中性要求旧存档、旧哈希不因一个纯标记而变。
- 迁移期为 P0→P1c。退出条件：生产代码中除 `apply_reform` 自身外，不再有 `institution.resolve_executor/check_authority/require_matter` 调用；之后再把 `apply_reform` 改为 actor-aware 包装并删除旧门面。

**理由**

- 旧门并不是永远放行，而是机构/职位参数门；直接删掉会破坏 B19 与旧调用方。
- 标记必须落在日志/既有条目上，不能落成新存档字段；否则默认中性验收失真。

### P0-4 验收测试

新增 `_dev_tools/game-dev/tests/test_authority_gate.py`，至少覆盖：

1. **在任主官**：王古持「官营放贷」，`check_matter_authority(s,"王古","官营放贷")` 通过。
2. **非主官但在任**：把户部侍郎填入「李四」，`resolve_actor` 得李四，按当前「机构默认事权」规则通过；若该 post 显式配置 `matter_keys`，只按显式集合判定。
3. **空缺职位**：户部侍郎为空，`check_matter_authority(s, {"post":"户部侍郎"}, ...)` 拒绝。
4. **同机构非任职人**：不是 holder 的人拒绝。
5. **跨机构**：户部 actor 判「官吏铨选」拒绝；吏部 actor 判「官营放贷」拒绝。
6. **免职即失权**：清空 holder 后原 actor 立即拒绝；重新任命后恢复。
7. **组织解析**：`{"org":"户部"}` 解析到当前第一在任 holder；全空机构拒绝，不得把机构本身当 actor。
8. **无状态污染**：拒绝路径前后 `state` 深比较相等。
9. **fail-closed**：monkeypatch `authority_gate.check_decree_authority` 抛异常，`confirm_decree` 返回 `STATUS_UNDEFINED`/`authority_check_error` 或 `STATUS_UNAUTHORIZED`，`authorized=False`、`withheld=True`。
10. **高皇威不豁免**：`state.prestige=100`，非法 actor 仍拒绝。
11. **旧门不变**：B19 的 `check_authority` didang 两断言原样通过；`apply_reform` 旧日志仍含 `→` 或 `拒绝`。
12. **新叶子边界**：`institution.py` 仍不 import `core.*`；`authority_gate.py` 不写 `state`。

### P0-5 不做什么

- 不把 `institution.py` 迁出、不重命名 `check_authority`、不删除 `require_matter`。
- 不让 `authority_gate` 读取派系 satisfaction/influence/capture 来决定合法性。
- 不让皇威直行通过 `authority_gate` 的非法事权检查；皇威只能覆盖执行侧权限/程序，不能创造事权。
- 不在 P0 改 `free_effect` 的财政成本扣款顺序；那是 P1a。

## 2. P1：M1b-2b 财政入口清单

### P1-0 口径

1. 财政权限**按动作映射**，禁止一个财政通吃。
2. 底层账本 API（`local_treasury_set/add`、`GameState.change_treasury`、`transfer_money`）**不加**权限门；它们是单点写通道，权限门在**玩家/AI 可触发的政治入口**。
3. 月度内部结算步骤（`settlement_finance._settle_*`）不加权限门；它们执行的是既有预算/制度结果。
4. 默认中性：新入口未显式携带 `executor` 时，旧调用保留并记 `legacy_unchecked_fiscal`；显式携带则严格判权。严格开关可复用 `state.authority_strict`，但必须补持久化，否则读档会复位（见风险审查）。
5. `propose_inner_transfer`/`confirm_inner_transfer` 是**皇帝私帑**路径，不是户部事权；不加户部权限门，但仍应受玩家入口与额度校验。

### P1-2 第一批 P1a：只做 F1 + F2

#### F1：`free_effect.didang_*` actor 判权

**结论**：在 `free_effect` 层对 `effects.institution` 中受事权约束的参数做 **actor preflight**，通过后再走 `apply_reform`；权限失败时整单拒绝、**不扣 cost**。

**理由**：`apply_reform` 已有旧门，但旧门允许机构名直接代表权限；玩家/AI 入口应绑定到在任 actor。且 `_pay_cost` 在 `_apply_effect_to_state` 之后执行，必须提前拒绝，否则越权但扣钱。

**精确改动点**
- `core/authority_gate.py` 提供 `check_decree_authority(state, key, executor)`，用 `institution._matter_of(key)` 取 `INSTITUTION_PARAM_SPEC[key]["authority"]`，再走 `permission_model.resolve_actor + has_permission`。
- `core/free_effect.py::_apply_free_effect`：
  - 在 `validate_free_effect` 之后、`_cost_affordable`/`_money_effects_feasible` 之前调用 `_authority_precheck(state, effects, executor)`；
  - 任一受限参数不通过 → 返回 `[自由动作] 事权拒绝：...（未落地、未扣成本）`，`return`；
  - 长期条目写 `authority_mode="actor_position"`；**缺失 executor 或 executor 不是 holder 时整单拒绝**，不得进入 `apply_reform`，也不得用 `legacy_unchecked_fiscal` 放行受限参数。
- `core/free_effect.py::_settle_free_effects`：每月再次 preflight；权限失效 → 不调用 `_apply_effect_to_state`、不调用 `_pay_cost`，条目留队并记 `last_error="authority_denied"`。
- `core/domains/administration/institution.py` 不改行为；其旧门继续兜底。

**验收测试**
1. 王古 + `didang_loan_rate` + `cost.treasury=100000`：利率改变、成本扣一次。
2. 李清臣/户部外臣 + 同契约：利率不变、国库不变、无长期条目、返回含「事权拒绝」。
3. 户部侍郎空缺时 `{"post":"户部侍郎"}` 拒绝；填李四后按当前机构默认规则通过。
4. `mode=ongoing` 创建立项后把 holder 清空，下一月不生效、不扣成本、`last_error` 可读。
5. 旧 `apply_reform` 直接调用与 B19 不变。
6. 权限拒绝路径 `state` 深比较除诊断计数外无业务字段变化；F1 拒绝**不增加** `legacy_unchecked_fiscal`。

**不做什么**
- 不在 P1a 改 `institution.check_authority` 本身。
- 不在 P1a 给 `treasury`/`commerce_tax` 加门（P1b）。
- 不把 `executor=None` 自动解析为「户部」后放行；必须显式 actor/机构，机构由 `resolve_actor` 落到 holder，全空则拒绝。

#### F2：`repay_local_arrears` 的国库/度支调度门

**结论**：`source="treasury"` 时，新增可选 `executor=None, strict=None`；有 executor 则必须为持 `度支调度` 的在任 actor；无 executor 时，兼容模式保留并计 `legacy_unchecked_fiscal`，严格模式拒绝。`source="coffer"` 属地方府库盈余，P1a 不加中央事权门。

**精确改动点**
- `core/settlement_finance.py::repay_local_arrears` 签名追加 `executor=None, strict=None`。
- 在 `LOCAL_REPAY_ENABLED` 检查后、任何 `transfer_money` 前做权限预检。

**不做什么**

## 3. P2：M2 诏令三关

### P2-1 结论：M2a 最小范围

**结论**：第一批只接 `issue_decree` 的**显式事权路径**，支持两个事权键：

```
M2A_MATTERS = {"官吏铨选", "度支调度"}
```

- 旧调用（无 `primary_matter`/`co_matters`）：**完全不进入 M2a**，保留 `legacy_unchecked=True`，不写 `legal/procedure_state/exec_state` 新字段。
- 显式路径：必须有 `primary_matter` + `executor` + 可解析的 actor；`co_matters` 允许但 M2a 按**同一执行主体、整诏原子执行**处理；M2a 不产生 `partially_executed`。
- 其他事权键：M2a 仍只做 M1b-1 的合法性校验，不进入新的执行状态机；待 M2b 扩大。
- M2a 只实现 `resisted` 三期和整诏幂等；`partially_executed` 放 M2b（见 P2-5）。
- 出入口仍只有 `issue_decree`；`issue_free_decree`/`issue_kouyu`/`issue_edict_from_review` 的财政门在 P1b 做，不另造诏令入口。

**理由**：先把「合法但会拖延」「程序封驳」「执行失败不伪装完成」三条验证清楚；同时避免在没有 `matter_effects` 分区时做出假的部分执行。

### P2-2 `issue_decree` 字段兼容

**结论**：保留现有全部字段与返回值；只在显式路径追加以下字段（全部落在 `pending_decrees[*]` 的 decree dict 内，不新增顶层 `state.*`）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `decree_id` | str | 显式路径**颁诏时即补**；旧路径仍在结算时补 |
| `legal` | bool | 关口一结果；不依赖程序态 |
| `legal_reason` | str | 不合法原因 |
| `executor_actor` | str\|None | 由 executor 解析出的具体承办人 |
| `procedure_state` | str | `not_required/pending_review/passed/returned/bypassed` |
| `procedure_reason` | str | 程序结果原因 |
| `procedure_reviewer` | str\|None | 行使封驳/审议的 actor；必须是 `诏令封驳` 持有人 |
| `procedure_reviewed_turn` | int\|None | 程序裁决回合 |
| `exec_state` | str | `not_entered/ready/resisted/partially_executed/blocked` |
| `exec_reason` | str | 执行原因 |
| `matter_exec` | dict | `{matter: {status, executor, attempts, last_turn, due_turn, error}}` |
| `resist_period` | int | 0..3；M2a 整诏级；M2b 逐事权级 |
| `due_turn` | int\|None | 到期重评回合；禁止墙钟 |
| `completed_turn` | int\|None | 终态回合 |
| `refusal_fact` | dict\|None | 拒收事实，不自动定罪 |

字段兼容规则：

1. 旧调用不写上述字段；序列化哈希应保持旧基线（允许已有 `legacy_unchecked` 字段）。
2. `direct=True` 且显式：`procedure_state="bypassed"`；仍必须 `legal=True`、`executor_actor` 有权限；结算仍需确认与执行。
3. `is_zhongzhi`/`is_direct` 的既有扣皇威/台谏积怨逻辑不动；不重复扣。
4. `addressees`：显式路径若无 `addressees`，自动补 `[executor_actor]`；若已有 `addressees` 但不含 `executor_actor`，颁诏时拒绝（防止承办人不是受命人）。
5. 现有 `effects` 仍走 `_apply_decree_effect`；M2a 不拆 effects；M2b 才引入 `matter_effects`。

### P2-3 三关与状态转移

**关口一（legal）**

- 继续用 `authority_gate.check_matter_authority` 对 `primary_matter` 与所有 `co_matters` **逻辑与**；任一不合法：拒绝入队，不扣 prestige、不占 bandwidth、不消耗御笔次数。
- `legal` 只取决于皇帝主权/诏令形式/承办适法性；**不看** procedure/exec。
- 结算前再次核验 `executor_actor` 是否仍在任并有权限；失效 → `exec_state="not_entered"` + `OUTCOME_FAILED`，不得把人事变动后的旧权限当作仍有效。

**关口二（procedure）**

- 初始态：
  - `direct=True` → `bypassed`；
  - `intent ∈ {调停,站队,打压}` 或 `decree.procedure_required=True` → `pending_review`；
  - 其它显式普通诏 → `not_required`。
- `pending_review` 的 reviewer：
  - 显式 `procedure_reviewer`；否则 `permission_holders(state,"诏令封驳")` 的第一个（确定性排序）；
  - reviewer 必须实际持 `诏令封驳`；无 reviewer/无资格 → 保持 `pending_review`，`exec_state="not_entered"`，留在队列。
- `returned` 只能由持 `诏令封驳` 的 reviewer 产生；判定证据只允许**显式事实字段**：
  - reviewer ∈ `decree.veto_ministers`，或 reviewer 派系 ∈ `decree.oppose_factions` → `returned`；
  - 否则 `passed`。
- 禁止用 `institution_distribution`、`permission_capture`、satisfaction、影响力、随机数产生 `returned`。
- `returned` 的诏：`exec_state="not_entered"`，台账 `outcome="vetoed"`，从 pending 移除；可重新拟诏，但同一 `decree_id` 不重复施加政治后果。

**关口三（execution）**

- 只有 `procedure_state ∈ {not_required, passed, bypassed}` 才进入。
- 先走既有 `confirm_decree`（受命人复述）；映射：
  - `STATUS_CONFIRMED` → 继续；
  - `STATUS_UNDEFINED` → 留在 pending，不执行、不落终态台账；
  - `STATUS_MISMATCH`/`STATUS_UNAUTHORIZED` → `exec_state="not_entered"`，落 `OUTCOME_FAILED`，不施加效果；
  - `STATUS_VETO` 且 actor 持 `诏令封驳` → `procedure_state="returned"`、`exec_state="not_entered"`、`OUTCOME_VETOED`；
  - `STATUS_VETO` 且 actor 不持 `诏令封驳` → 生成 `refusal_fact`（`reason_code="unknown"` 或 `authority_conflict`），`exec_state="not_entered"`，**不得**写成 `returned`/`blocked`，不得自动定罪；M2a 可落 `OUTCOME_FAILED` 结束。
- 执行掷点：新路径禁止 `random.random()`；使用
  `seed = int(sha1(f"{decree_id}|{matter}|{state.turn}|{resist_period}|{executor_actor}").hexdigest()[:16],16)`
  `roll = 0.5 + TianDaoEngine.dice(seed, entropy=0.5)`，`success = roll < rate`。
- 成功：`_apply_decree_effect` 只调用一次；所有 `matter_exec` 置 `executed`；`exec_state="ready"`；台账 `executed`。
- 失败且 `resist_period < 3`：`exec_state="resisted"`，`resist_period += 1`，`due_turn=state.turn+1`，留 pending；**不写台账终态、不重复扣初始政治代价、不重复施加 `_event_delta`**。
- 失败且 `resist_period == 3`：`exec_state="blocked"`，`matter_exec[*].status="failed"`，台账 `OUTCOME_FAILED` + `detail="resisted_expired"`，生成**一次** `event_id`；从 pending 移除。
- 若 `due_turn > state.turn`：直接留在 pending，不重评、不掷点。

### P2-4 `resisted` 三期

| 期 | 触发 | 状态 | 后续 |
|---|---|---|---|
| 1 | 首次执行失败 | `resisted`, `resist_period=1`, `due_turn=T+1` | 留在 pending |
| 2 | 到期重评仍失败 | `resist_period=2`, `due_turn=T+1` | 留在 pending |
| 3 | 到期重评仍失败 | `exec_state=blocked`, matter `failed`, detail `resisted_expired` | 终态台账一次、事件种子一次 |
| 通过 | 任一期成功 | matter `executed`, `exec_state=ready` | 终态台账一次 |

- `resisted` 不是终态，`execution_of` 不写。
- 读档恢复 `exec_state/resist_period/due_turn`；同一 `(decree_id, matter, resist_period)` 不得重复掷点/重复效果。
- 等待期不重新走 `_apply_decree_effect`；初始 `_event_delta`/皇威代价只在颁诏或首次进入执行时一次。

### P2-5 `partially_executed` 边界（M2b）

**结论**：M2a **不产生** `partially_executed`。原因：现有 `effects` 是整诏级字典，没有哪个事权对应哪部分效果的分区；在多事权未分区时写部分执行会制造假账。

M2b 精确方案：

1. 新增可选 `matter_effects = {matter: effects_subset}`；多事权新诏必须提供，且键集合等于 `[primary_matter]+co_matters`。
2. 每个 matter 单独执行、单独 `(decree_id,matter)` 幂等；`_apply_decree_effect` 只接收该 matter 的 effects 子集。
3. 聚合规则（照契约 §4.2）：
   - 只聚合已进入执行的事权；
   - 任一已执行事权 `blocked` → 整诏 `blocked`；
   - 有 executed + 有 resisted/pending → `partially_executed`；
   - 全部 executed → `ready`；
   - 否则 `resisted > partially_executed > ready` 的优先级只在已进入执行集合内使用。
4. 验收：户部部分执行成功、吏部仍在 resisted → `partially_executed`，户部不重复扣；全部完成后才整诏完成。

### P2-6 `STATUS_VETO` / `OUTCOME_VETOED` 收口

**结论**：**不把二者塞进现有四态元组**；新增超集元组，既修正语义又不破坏既有 API/测试。

- `STATUSES` 保持 `(confirmed, mismatch, unauthorized, undefined)`，它是「复述四态」。
- 新增 `CONFIRM_RESULTS = STATUSES + (STATUS_VETO,)`，表示 `confirm_decree` 的**全部可能返回结果**。
- `OUTCOMES` 保持 `(executed, registered_only, failed, claimed)`，它是「正常执行结果」。
- 新增 `LEDGER_OUTCOMES = OUTCOMES + (OUTCOME_VETOED,)`，表示 `decree_exec_ledger` 的**全部合法结果**。
- `_settle_decrees`/`record_execution`/读取台账的校验一律使用 `LEDGER_OUTCOMES`；`confirm_decree` 的 docstring 与状态表改用 `CONFIRM_RESULTS`。
- 现有 `test_four_states_are_reachable_and_distinct`（`set(seen)==set(STATUSES)`）与 `set(OUTCOMES)=={...}` 不会被破坏；新增测试验证超集差集恰为 veto。

**理由**：`veto` 是终态/程序结果，不是「复述四态」之一；硬塞进 `STATUSES` 会让「四态互斥且穷尽」的语义和旧测试同时失真。超集元组是同样明确的单点，且不破坏前端/API 对四态的消费。

## 4. P3：M3 弹劾案件闭环

### P3-1 结论：M3a 最小闭环

**结论**：只做一条可追溯链路，且首批目标限定为**路/州主官**（`circuit_officials` / `prefect_officials` 中的在任者），因为现有 `dismiss_*` 只覆盖这两类；中枢大臣的弹劾后置 M3b。

链路：

```
弹章 memorial(kind=impeachment)
  → accept_memorial 开 case (investigating, due_turn=T+1)
  → 到期 fact_finding（只看证据）
  → institutional recommendation（只看证据+程序，不看派系影响力）
  → awaiting_disposal
  → 玩家圣旨/命令 dispose（pardon/force_dismiss/remand/none）
  → 如罢黜：走 dismiss_circuit_official / dismiss_prefect_official
  → 派系反应经 faction_settle 的受控冲击入口
```

### P3-2 精确字段与模块

- 新模块 `game/core/impeachment.py`。
- 新存档字段 `state.impeachments`（dict，真状态），并在 `game/core/save_load.py` 保存/载入白名单补上；旧档缺省 `{}`。
- `memorials` 增加 `kind="impeachment"`；事实签字段：
  `memorial_id/kind/accuser/target/target_faction/trigger_fact/evidence_refs/severity/created_turn`。
- `case` 字段：
  `case_id/status/fact_finding/evidence_score/institutional_ruling/imperial_disposal/due_turn/created_turn/closed_turn/event_ids`。
- `case_id = "imp_" + hash(memorial_id,target,created_turn)`；`status ∈ {filed, investigating, awaiting_disposal, closed}`。
- `fact_finding ∈ {supported, unsupported, unknown}`；`institutional_ruling ∈ {dismiss, demote, acquit, retry}`；`imperial_disposal ∈ {pardon, force_dismiss, remand, none}`。

### P3-3 证据与裁定映射（M3a 暂定常量）

**证据审查（只看证据）**

- 遍历 `evidence_refs`：只接受能解析到真实 `audit_case` / `inspection` / `memorial` 的引用；任一引用不可解析 → `unknown`，不得猜。
- `evidence_score = clamp(0.6*verified_ratio + 0.4*min(1, severity), 0, 1)`；`verified_ratio` 只数 `verified=True` 的引用。
- `fact_finding`：
  - 有 ≥1 个 verified 且 `evidence_score >= 0.5` → `supported`；
  - 所有引用均可解析但均为 `verified=False` → `unsupported`；
  - 缺引用/不可解析 → `unknown`。
- 派系 satisfaction/influence/capture **不进入** `evidence_score`/`fact_finding`；只允许影响调查 `due_turn`（M3b，M3a 不做）。

**制度建议（只看 fact + severity + 程序）**

| fact_finding | 条件 | institutional_ruling |
|---|---|---|
| `unsupported` | 任意 | `acquit` |
| `unknown` | 证据不足 | `retry`（`due_turn=T+1`，最多 2 次；仍 unknown 则 `acquit` 并记 `evidence_undefined`） |
| `supported` | `evidence_score >= 0.7` 且 `severity >= 0.6` | `dismiss` |
| `supported` | `evidence_score >= 0.4` | `demote` |
| `supported` | 其它 | `acquit`（罪证/严重度不足，不等于事实不存在） |

**玩家处置（不改 fact_finding）**

- `none`：接受建议但不额外动作；`acquit`/`retry` 按建议结束或续查。
- `force_dismiss`：即使建议不是 dismiss，也走 `dismiss_*`；记录 `imperial_bias`、皇威/民望代价、史册 `event_id`；**不得改写 fact_finding**。
- `pardon`：不罢黜；记录皇威/民望代价与 `event_id`。
- `remand`：`due_turn=T+1`，重新审查；不得跳过证据。
- `force_dismiss`/`pardon` 的人事/政治后果必须可追溯，不得直接删 holder。

### P3-4 验收测试

1. 弹章缺 `accuser/target/trigger_fact` → 不生成/不开案。
2. `accept_memorial` 准奏弹章 → `investigating`，**不直接罢官**；`due_turn=T+1`。
3. 留中 → 不开案；记录怠政/民望代价；不是无罪。
4. 证据全 verified → `supported`；证据不可解析 → `unknown`；证据全假 → `unsupported`。
5. 派系影响力改变 → `fact_finding` 与 `evidence_score` 不变。
6. `force_dismiss` → 走 `dismiss_*`，`fact_finding` 原样保留；有 `event_id` 与皇威代价。
7. 同一 `case_id` 重复结算/读档重跑 → 不重复罢官、不重复扣 satisfaction。
8. 目标为中枢官 → M3a 拒绝并提示 M3b 未开启，不静默改 holder。
9. 存档往返：`state.impeachments` 逐字保留。

### P3-5 不做什么

- 不做中枢大臣弹劾、联名弹章、多罪状合并、流放/籍没/永不叙用。
- 不用派系影响力决定证据真假或制度裁定。
- 不准奏即罢黜、不跳过调查/证据审查。
- 不另造奏折系统；沿用 `state.memorials`。
- 不做 AI 自由裁定；AI 只出档位/叙事，事实与裁定由程序表决定。

## 5. P4：M4 党禁 / 动态集团

### P4-1 结论：M4a 只做轻/中党禁

**结论**：先做 `faction_ban` 状态机，轻/中两级；动态集团、重度清算、流放/籍没明确不做。

**级别与参数（暂定，集中配置）**

| 级别 | 时长 | 一次性 satisfaction | 维护态 |
|---|---|---|---|
| 轻 | 6 回合 | -8 | 限制该派除授；不重复扣 satisfaction |
| 中 | 12 回合 | -15 | 指定职位罢黜走人事流程；不重复扣 satisfaction |

### P4-2 精确字段与接口

- 新模块 `game/core/faction_ban.py`。
- 新存档字段 `state.faction_ban`（dict），`save_load` 白名单补上；旧档缺省 `{}`。
- 字段：
  `{faction: {level, status, start_turn, end_turn, target_posts, event_ids, created_decree_id}}`
- API：
  - `start_faction_ban(state, faction, level, decree_id, target_posts=None) -> dict`
  - `is_faction_banned_for_appointment(state, faction) -> bool`
  - `settle_faction_bans(state) -> dict`（`turn_start`/月度固定点）
  - `lift_faction_ban(state, faction, reason) -> dict`

- 维护态每月只检查到期/资格，不再扣 satisfaction。
- 到期自动解除；解除后 +5 一次，亦经事件台账。
- 提前解除：M4a **不做**；M4b 再做（需期间无新弹劾 + 财政/民望达标）。
- 轻/中党禁的罢黜：
  - 目标必须是 `circuit_officials`/`prefect_officials` 在任者；
  - 逐人调用现有人事流程 `issue_personnel_order`/`dismiss_*`，不得直接改 holder；
  - 无人事权限时拒绝，不得静默跳过。
- 授职限制：`issue_personnel_order` 与四个 `appoint_*` 在目标派系处于 ban 时拒绝新任命；`imperial_direct` **不豁免党禁**（皇帝要先解禁或走新的显式破例，M4b 再议）。

### P4-3 验收测试

1. 轻党禁：开始一次 satisfaction -8；之后 5 个月不再扣；第 6 回合到期 +5 一次。
2. 中党禁：-15、12 回合；指定职位罢黜逐人走 `dismiss_*`，不直接删 holder。
3. 同一 `event_id` 读档重跑不重复扣/不重复解除。
4. 被 ban 派系的新任命被拒；解禁后恢复；解禁不是直接改官员。
5. 目标职位非法/空缺/不在任 → 拒绝并留原因，不批量抽样式删除。
6. 存档往返 `state.faction_ban` 逐字保留。
7. 240 回合长跑：无 banned 状态泄漏、无重复惩罚、无 POP/官员守恒破坏。
8. 中枢动态集团：不进入 `faction_registry`、不改 `FACTION_NAME_SET`、不写动态派系存档。

### P4-4 不做什么

- 不做动态新集团（M4b+ 另裁）：不加 `faction_registry`，不改 `save_load` 的 `FACTION_NAME_SET`，不新增派系 POP。
- 不做重度清算、流放、籍没、永不叙用。
- 不每月重复扣 satisfaction/influence。
- 不让党禁状态机直接删除官员或直接改 `central_orgs.holders`。
- 不在 M4a 做提前解除与财政/民望达标自动恢复。

## 7. 对当前已实现部分的风险审查

### 7.1 皇威直行是否架空职位权限

**结论：设计上不架空，当前实现有内部布尔后门与目标校验偏弱两处风险；P0/P1 必须补测试与记录。**

已实现事实：

- `imperial_mandate.can_direct` 要求 `prestige > threshold` 且 `implemented=True`；任免阈值 80，代价 2。
- `personnel_order.issue_personnel_order` 在直行时把 `imperial_direct=True` 传给低层 `appoint_*`/`dismiss_*`；低层据此跳过 `personnel_authority`。
- 低层仍校验：路名/role_key 合法性；prefect seat 存在；目标 holder 存在（罢免时）。
- 因此**当前不会把不存在的事权授给部门**，也不会直接改权限表；它只是皇权对执行侧权限的覆盖。

风险：

1. **低层布尔后门**：`appoint_*`/`dismiss_*` 的 `imperial_direct: bool` 是公开参数。任何内部调用方都可以传 `True` 跳过权限，没有 capability token 或调用栈证明。当前生产调用点只有 `personnel_order`，但这是约定不是强制。
2. **目标合法性偏弱**：`appoint_circuit_official` 对空名字会回退成「待命官员」，并可通过 `ensure_person_identity` 创建新身份；高皇威可以给不存在的目标造一个人。这不符合目标合法/职位存在的强校验。
3. **直行没有记录绕过了哪项事权/程序**：ledger 只有 `mode="imperial_direct"` 和 `prestige_cost`，缺 `bypassed_matters`/`procedure_state="bypassed"`/`target_validation`。
4. **低皇威走流程时**，`personnel_authority(strict=True)` 会重校验；这是正确的；但直行路径没有同等强度的目标/资格记录。
5. **阈值边界**：`can_direct` 是 `prestige > threshold`；80 不直行、81 直行，与设计一致。
6. **皇威代价只在成功时扣**；失败不扣，合理，但需测试失败不改官职且不扣费。

**裁决**

- 保留皇威直行，但 P0/P1 必须：
  1. 把低层 `imperial_direct` 改为**不可由普通业务调用方直接构造的授权凭证**（最小实现：`imperial_mandate.DirectGrant`，由 `can_direct + charge` 通道签发；低层只接受 grant，不接受裸 bool）。若暂不引入对象，至少把四个低层入口改为私有 `_appoint_*_direct`，公开入口不收 `imperial_direct`。
  2. 直行前校验目标非空、身份唯一、职位存在、目标未处于党禁（M4 后）；空名字/重复身份拒绝。
  3. ledger 增加 `bypassed_matters`、`procedure_state="bypassed"`、`target_validated=True`、`source`。
- 这些是 P0/P1 的安全加固，不改变皇威 > 阈值可直行的设计。

### 7.2 `permission_capture` 是否被误当任职分布

**结论：`permission_capture` 不是 `institution_distribution`；当前实现只能叫「有该事权的 holder 的派系人数占比」，不能当机构控制/任职分布使用。**

差异：

| 维度 | `institution_distribution`（M1a） | `permission_capture` |
|---|---|---|
| 对象 | 机构岗位槽位 | 某具体事权的持有人 |
| 分母 | 全编制岗位数（含空缺） | 该事权 holder 人数 |
| 空缺 | 有 `vacant_share` | 无，空 holder 返回 `{}` |
| 兼任 | 次职 0.5/0.5 + discount | 每人 1，不折损 |
| 未登记派系 | `unaffiliated_share` | 直接归未登记 |
| 权重 | 岗位权重/headcount | 人数等权 |
| 定义态 | `defined` | 无 `defined`/`basis` |
| 多事权 | 机构级 | 每个 matter 可能相同（因所有岗位继承机构事权） |

风险：

1. 当前所有无 `post.matter_keys` 的岗位继承机构全部事权，因此户部 6 个财政事权的 `permission_capture` 可能完全相同；用它解读财政控制会过度概括。
2. `permission_capture` 空返回 `{}`，前端若把 `{}` 当 0 会误报无人控制；必须显式 `defined=False`。
3. 它没有 `vacant_share`，不能与 M1a 五项守恒混算。
4. 它是派系人数占比，不是控制力；不能参与 `returned`/`exec_state` 的合法性判定。

**裁决**

- `permission_capture` **保留**，但输出改为显式契约：
  ```
  {
    "matter": str,
    "as_of_turn": int,
    "basis": "permission_holders_headcount",
    "defined": bool,
    "holders_total": int,
    "faction_share": {faction: float},
    "unaffiliated": float,
  }
  ```
- 空 holders：`defined=False, faction_share={}, holders_total=0`，不得用 `{}` 冒充 0/全控。
- UI 文案只能叫「事权持有人派系构成」，不得叫「机构派系分布/控制度」。
- 单测必须对比：户部 `institution_distribution` 有 `vacant_share=1/3`、`concurrent_discount_share=0.5/3`，而 `permission_capture` 不出现这些字段；两者不得互相赋值。
- 若将来要按岗位权重算事权分布，另建 `permission_distribution`，不要改 `permission_capture` 的语义。

### 7.3 其他已实现风险

1. **`authority_strict` 未持久化**：`permission_model.authority_strict` 读 `getattr(state,"authority_strict",False)`，但 `GameState`/`save_load` 未显式保存；读档会复位 False。若把它当迁移开关，必须写入存档（`statistics` 或白名单字段），否则严格模式在旧档中静默失效。
2. **`permission_model` 的机构默认继承**：当前 `_post_matter_keys` 对无 `matter_keys` 的岗位继承机构 `authority/matter_keys`，所以户部侍郎与户部尚书权限相同。这符合当前测试，但不是精细职位权限；若后续要求主官独占，必须给岗位写 `matter_keys` 并补测试，不能靠假设。
3. **`resolve_actor` 对 org 只取第一个在任 holder**：多 holder 机构用 `{"org":...}` 可能绑定到非预期的人；显式 `post`/`holder` 更精确。UI 应尽量传 actor，不传机构。
4. **`decree_confirm` 的 `can_act` 与具体事权分离**：`can_act` 只看 Agent 通用 authority 数值；新门必须继续在 `confirm_decree` 内运行，不能只靠 `can_act`。
5. **`STATUS_VETO`/`OUTCOME_VETOED` 不在 `STATUSES`/`OUTCOMES` 元组**：按 P2-6 用 `CONFIRM_RESULTS`/`LEDGER_OUTCOMES` 超集收口，不破坏旧四态 API。
6. **新路径随机数**：`settlement_decree` 旧路径 `random.random()` 保留，但 M2 新路径必须用 `TianDaoEngine.dice`；禁止把旧随机路径原样复制到新状态机。
7. **存档白名单**：P3/P4 新字段必须同时改 `game/core/save_load.py` 的保存与载入；只改 `GameState` 会读档丢状态。
8. **事件台账**：现有 `_event_delta` 只是 faction dict 上的临时冲击，没有统一 `event_id` 台账。P2a 必须先建 `statistics["political_event_ledger"]` 的受控 helper，P3/P4 复用；否则同一事件只一次无法验收。

**阻断项 1：resisted 三期 off-by-one**

当前 `settle_m2a_decree` 用：

```python
period = int(decree.get("resist_period", 0) or 0)
...
if period < 3:
    decree["resist_period"] = period + 1
    ... pending
# period == 3 才 blocked
```

实测：

```
turn 0: resisted, period=1
turn 1: resisted, period=2
turn 2: resisted, period=3   # 第三次失败仍留队
```

契约 §6/裁决 P2-4 要求：**第三次失败即终态** `blocked/failed/resisted_expired`、写一次台账、生成一次事件。当前要等到第四次失败才终止，且第四回合若掷点成功会错误执行。

要求：第三次失败（`period` 初始为 2 的那次）直接进入终态；`matter_exec.attempts=3`；`due_turn=None`。验收需明确三回合终止，不再用 `for turn in range(4)` 掩盖。

**阻断项 2：M2a 字段构建异常静默降级**

`issue_decree` 的 M2a 字段构建包在：

```python
try:
    if _auth.get("explicit") and is_m2a_decree(decree):
        ...
        _m2a = {...}
except Exception:
    _m2a = {}
```

实测 monkeypatch `decree_gates.is_m2a_decree` 抛异常后，诏令仍返回 `已下诏`，且 `pending_decree` 没有 `procedure_state`，直接退回旧路径。这违反「关键步骤异常不得静默中性/不得伪装成旧路径成功」的硬约束。

要求：显式 M2a 路径的 gate 构建异常必须拒绝颁诏（`authority_check_error`/`fiscal_error` 可读原因）或写 `faction_strife_error + degraded`；不得设置 `_m2a={}` 后继续走旧路径。

- `_fail` 对所有失败都写 `confirm_status=STATUS_UNAUTHORIZED`；`returned`/`veto` 的 `confirm_status` 应单独表达（可用 `STATUS_VETO` 或 `undefined`），不要混成越权。
