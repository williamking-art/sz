# AI 科技维度与蓝图演进 · 开工门台账

> **状态**：C0 设计台账，待评审。只做现状核验、生命周期设计和阶段拆分；**不改代码、AI schema、科技表、蓝图注册器、存档或结算**。C1+ 未授权。
> **目标**：保留 AI 游戏特有的开放度——AI 可提出既有内容库没有的新科技维度/节点、配套蓝图，以及既有蓝图的升级方案；但由程序校验和结算，玩家审批后才能成为有效游戏内容。
> **边界**：「科技维度」在本台账只表示科技树的领域/分支/节点，不自动表示新增资源、POP、钱粮账户或任意结算字段。

## 0. 结论摘要

一句话：**让 AI 的创意空间开放，让改变世界的注册/研究/建设路径受控。** 不用静态菜单限制构想，也不允许 AI 把创意直接写成游戏状态。

现状核验表明本项目并非从零开始：

| 能力 | 当前状态 | 代码/文档依据 |
|---|---|---|
| AI 提议新建筑蓝图 | **已接通基础路径**：声明式 `blueprint_proposal` → 逐项校验 → 当前存档注册 → 可接现有项目链 | `ai/contracts_decree.py::decree_action_plan`；`core/decree_plan.py::validate_action`；`core/plan_commit.py`；`core/blueprint_dynamic.py` |
| 蓝图效果安全 | **已有安全边界**：只允许已注册 `EFFECT_OPERATORS`，拒绝代码、表达式、字段路径和未注册效果 | `core/blueprint_dynamic.py::validate_dynamic_blueprint` |
| 动态蓝图持久化 | **已有**：`GameState.dynamic_blueprints`；随存档保存/读取，读档逐条重验 | `core/game_state.py`；`core/save_load.py`；`decree-action-chain/tasks.md` §7 |
| 动态蓝图升级 | **未实现**：注册器同名拒绝；没有修改/升级/版本替换 API | `core/blueprint_dynamic.py::register_dynamic_blueprint` |
| 科技树 | **静态**：`content/data_tech.py::TECH_NODES` 是代码内固定列表；研究候选/依赖读取该表构成的模块缓存 | `core/domains/economy/regime_tech.py::_tech_nodes_index` |
| 科技维度动态扩展 | **未实现**：无存档级科技节点/领域 proposal registry；现有 `regime_tech` 是政权科技进度，不是 AI 可扩展科技目录 | `regime_tech.py` 与 `TECH_NODES` 全链核验 |
| 科技与 AI 蓝图提案关联 | **未接通**：AI action 有独立 `blueprint_proposal`，没有“科技提案生成/引用蓝图”这一跨对象注册链 | `contracts_decree.py` / `plan_commit.py` |

因此需要补的是：**科技扩展的提案与存档注册、动态科技进入研究流程、既有蓝图的版本化升级，以及科技—蓝图关联**。已经工作的动态蓝图新建流程应当复用，不能重做一套。

## 1. 目标生命周期

```text
AI 开放式构想（自然语言，不限现有档位/目录）
  → 科技扩展提案（新维度/领域/节点/前置/效果构想）
  → 关联新蓝图提案或既有蓝图升级提案（可分开，也可成包）
  → 程序做结构、类型、单位、依赖、operator、安全与兼容校验
  → 玩家审议批准（未批只是提议，不注册、不研究、不建造、不生效）
  → 版本化注册到当前存档；研究/工程分别沿既有流程推进
  → 程序按获批 schema/operator 与实际状态结算效果
  → 反馈来源、阶段、失败原因与因果链
```

关键区分：

1. **创意可以自由，执行结构必须可验证。** AI 可提想法、方案和相对目标；进入引擎需转为声明式、版本化的 proposal。
2. **提出 ≠ 批准 ≠ 注册 ≠ 解锁 ≠ 建成 ≠ 生效。** 这六态不得混成一句“AI 发明成功”。
3. **研究解锁不能代替建筑建设。** 科技维度扩展不自动生成蓝图，蓝图注册不自动建造，项目完工才可触发相应效果。
4. **效果必须有程序实现。** AI 可以提议尚不存在的能力；没有经过审计并注册的 effect operator 时，提案应为待补/不支持，而非编造数值效果。

## 2. 术语和对象边界

| 对象 | 本台账定义 | 不自动意味着 |
|---|---|---|
| 科技维度/领域 | 科技树的可扩展分类/研究方向 | 不自动新增 goods/resource/pop/account 或结算变量 |
| 科技节点 | 某项知识或能力的研究条目：前置、研究成本/时长、效果引用、可选蓝图引用 | 不等于已研究、已部署或效果已生效 |
| 蓝图定义 | 建筑/产业的声明式建造规格：地利、成本、材料、工期、岗位、维护、效果 operator | 不等于已经建成的建筑实例 |
| 蓝图版本 | 同一稳定 `blueprint_id` 下的不可变定义版本 | 不能覆盖已被工程/实例引用的历史版本 |
| 蓝图升级 | 从明确的 `from_version` 到 `to_version` 的独立项目/状态转移 | 不是同名重新注册、也不是即时改写所有旧实例 |
| 建筑实例 | 某治所已建成对象，记录地点、蓝图 id/version、等级、运行状态 | 不等于 proposal 或 registry 条目 |
| 效果 operator | 程序实现并注册的确定性计算构件，含参数 schema、单位、时点、守恒/范围 | AI 不得自行创造可执行代码或任意公式 |

## 3. 科技扩展 proposal 契约（设计草案）

### 3.1 提案结构

建议采用“提案包”：科技扩展可关联零个、一个或多个蓝图提案；不存在强制一科技配一建筑。一个包可含多节点，但审批结果应能逐项区分接受、待补、拒绝。

```json
{
  "proposal_id": "程序生成的稳定 ID",
  "source": {"kind": "ai_innovation", "reference": "原意图/行动引用"},
  "technology_extension": {
    "dimension": {"id": "候选领域 id", "name": "名称", "scope": "适用范围"},
    "nodes": [{"id": "稳定候选 id", "name": "节点名", "prerequisites": [], "research": {}, "effect_refs": []}]
  },
  "blueprint_proposals": [{"kind": "new | upgrade", "blueprint_id": "稳定 id", "from_version": null, "to_version": 1, "definition": {}}],
  "unresolved": [],
  "status": "proposed"
}
```

> 这是设计示意，非已批准 schema。C0 应冻结字段、id 生成、版本、逐项裁决和未知字段策略，但不实现。数值字段要有单位/范围/出处；材料不足时标未定义/待补，不能默认为零、免费或中性效果。

### 3.2 动态节点进入研究树的条件

批准后的动态节点需能与静态 `TECH_NODES` 一起被研究器解析，但静态内容仍为代码发布资产，动态内容单独进入存档注册表。建议统一读模型而非改写静态表：

- 动态 id 全局唯一且版本固定；与静态节点、其他扩展节点撞 id 则拒绝。
- 前置引用必须指向已发布或同一已批准提案中的节点；整张依赖图必须无环。
- 领域、名称、解释、研究成本/时长/输入、适用对象、effect refs 都有 schema 和明确缺失语义。
- 研究时从该政权/国家自己的 tech state 记录进度与 unlocked ids；不把政权研究进度与宋侧 `GameState.tech` 混成一个真账。
- 动态节点解锁只允许启用其显式关联的蓝图/后续节点；不直接写产量、建筑等级、POP 或货币。
- 研究和部署各自有前置：**研究完不等于建筑已部署/建成**。

### 3.3 创新维度≠新增经济账本

本项目 `TECH_NODES` 的 effects 是对既有能力键的修正；AI 提“新科技维度”只能先扩展科技树的知识分类/节点目录。若提案要创造新的经济商品维度、库存、需求、持有人、税基或货币账户，须另开对应经济模型与守恒设计，不可把它塞入 technology registry 随节点一起启用。

## 4. 蓝图新建与升级契约

### 4.1 新蓝图：复用现有路径

1. AI 可自由起草新的建筑/产业蓝图，继续复用 `blueprint_dynamic` 声明式 validator、operator registry、玩家审批、`plan_commit` 与 `construction`。
2. proposal registration 与建造立项要可分别发生；注册成功只表示定义可引用，不表示花钱、建成或生效。
3. 未注册 operator、结构/单位不全、无效地点、缺研究前置等，逐项拒绝或待补并说明原因；不得剔除坏字段后悄悄缩小蓝图再通过。
4. blueprint 定义需注明 `blueprint_id/version`、科技前置、地点条件、成本单位/材料、工期、岗位/容量、维护、产权/出资主体与 effects；缺资源来源或 effect 结算落点，状态为待补/unsupported。

### 4.2 既有蓝图升级：追加版本，不覆盖

当前没有升级 API，C0 只定义语义。建议升级 proposal 至少包括：

| 字段 | 约束 |
|---|---|
| `blueprint_id` | 稳定身份；须存在于当前有效 registry |
| `from_version` | 必须等于被审批/建筑实例所用版本；不一致则冲突拒绝 |
| `to_version` | 全新、单调递增、不可复用的版本 |
| `changes` | 结构化改动：岗位、容量、材料、成本、维护、地利、effect refs 等；不得只交一段自然语言 |
| `instance_scope` | 新造建筑默认用新版本；既有实例是否逐个升级需玩家明确选择，不得全局自动替换 |
| `project_policy` | 在建项目锁定旧版本或经批准显式迁移；须有一致规则 |
| `effect_migration` | 明确旧效果何时结束、新效果何时起效；需原子切换，失败仍留旧版 |

新版本只有经玩家批准、结构校验、operator 校验与存档注册后才可新建/升级工程。蓝图定义不可变；同名覆盖继续拒绝。版本数、旧版保留/归档规则需在 T0 冻结或另行裁定。

## 5. AI 自由与安全边界

| 自由空间（允许提出） | 生效约束（不得绕过） |
|---|---|
| 自由提出新知识领域、研究主题、科技节点、产业和建筑构想 | 节点/领域须经玩家审批并注册；前置、范围、成本、单位、effects 需程序验证 |
| 提议现有算子未覆盖的新能力 | 记录为“待实现 operator”；实现/审计/回归前不得注册为有效数值效果 |
| 提议新蓝图，或对现有蓝图升级 | 声明式字段；蓝图升级必须版本化，不得同名覆盖 |
| 用自然语言说明取舍、提出多种方案、发现新的经营机会 | 建议不等于命令或批准；只有玩家选择后才进入注册/研究/工程链 |
| 在知识、材料或历史信息不全时提出探索性假设 | 置信度/来源/未知项显式标注；未知不自动变成真实事实或默认数值 |

AI **不可以直接提供并写入**：最终产量、POP/劳动力、库存、钱粮、建筑等级、生产率乘数或任意结算公式；不可以输出可执行代码、脚本、字段路径或未经注册的 operator。程序按当前 state 和批准参数计算结果，报告差异与失败原因。

> 自由度的核心是**提案空间开放**，不是状态写权限开放；通过类型化 proposal、安全 registry、玩家审批及确定性执行来保留创造性而不牺牲账本。

## 6. 存档与所有权边界

- 静态定义（代码）与动态批准内容（存档）分开；AI 原始提案、待审提案、已批准定义、研究进度、建筑实例/工程分别有状态与 owner。
- 建议批准的动态科技扩展、蓝图版本存于当前存档的 versioned registry；工程/建筑引用稳定 id + 精确版本快照，避免升级代码后旧项目被静默改义。
- 状态归属：宋侧科技沿 `GameState.tech`；外部政权沿 `ex["tech"]`；二者可共享定义读取规则，但进度/库银/解锁状态不能共用一个可写对象。若统一扩展则需显式给每个 scope 定 owner。
- 旧档没有动态科技扩展字段时幂等初始化空 registry；现有静态研究进度、动态蓝图、建筑、项目和资金逐字段不变。坏动态项逐条隔离/记原因，不能因一个 proposal 搞坏整档。

**边界提示**：`decree-action-chain` 与本台账交叉引用——它已允许 AI 为营建 action 提议新蓝图，并已有注册/立项链；本台账新增关注点是**科技维度提案、科技—蓝图关联和旧蓝图升级**。科技构件只可引用已登记 operator，不重做行动链或其蓝图 schema。
- schema 升级需明确旧版迁移和高版本拒绝；注册、研究、立项、升级操作需幂等，重试不重复扣费或建造。

## 7. 阶段门与验收

> C0 通过**只批准设计契约**；不能解释为获准 prototype/implementation。T1–T3 仍须单独申请。

| 门 | 内容 | 验收断言 |
|---|---|---|
| **T0（本台账）模型/schema** | 确定提案对象、领域/节点注册、蓝图升级版本、玩家批准、存档 owner、AI/程序边界 | 当前与缺口有代码/文档证据；无“注册=完工”；无静态表与动态表双源；已列待裁项和非目标 |
| **T1（另行授权）proposal dry-run** | AI 自然语言提案→结构化科技/蓝图 proposal→校验报告；不写 state | 多种创新提案可表达；非法 operator、循环依赖、单位缺失、版本冲突逐项拒绝/待补；state 存档零变化 |
| **T2（另行授权）审批与动态研究** | 玩家批准后存档注册节点/维度，研究器从静态＋批准动态视图读取 | 未批不入表；重复提交幂等；缺前置/资金不足不研究完成、不部署、不产生效果；宋/政权 tech state 彼此隔离 |
| **T3（另行授权）新建/升级蓝图** | 蓝图提案、建造/升级工程、完成后 operator 运行 | 注册不等于建成；升级只对显式实例生效；失败原子回滚；旧版在建工程按快照继续；钱粮/材料守恒与来源链完整 |

### T0 的 C0 验收断言

1. 静态 `TECH_NODES` 与动态科技 registry 分属两个明确来源；研究读取合并视图，不能写回静态表。
2. “科技维度”限科技分类/研究方向，不暗含 goods、POP、account 或新结算字段。
3. AI 开放 proposal 可表达不在现有目录中的构想；它不改变 state。玩家未批准前 registry、研究进度、可建清单、钱粮、建筑和 effects 全部不变。
4. 科技节点 prerequisites 是可验证 DAG；引用未知节点、循环或重复 id/version 必须拒绝。
5. 动态蓝图新建复用现有 registry；升级用新版本/项目策略，不同名覆盖；明确当前升级 API 缺失。
6. operator 必须程序注册；未知 operator/数值/单位/结算落点缺失时 proposal 待补/unsupported，不执行。
7. 研究完成、蓝图可建、工程完工、效果生效保持不同状态；前一状态不得伪装成后一状态。
8. 静态和 dynamic defs、宋和外部政权的研究状态 owner 分离；旧档 round-trip 与逐项隔离策略明确。

## 8. 前置、并行和冻结范围

### 可复用前置

- `decree_action_plan` 已提供多动作 proposal 和 `blueprint_proposal` 字段；`decree_plan` 已有 operator registry 与 action 校验。
- `blueprint_dynamic` 已完成新蓝图安全 schema、当前档注册、效果翻译、同名拒绝与 round-trip；新方案要在其上扩展，而非另造蓝图通路。
- 现有 project/construction 流负责资金、材料、地点、工期和完工；科技研究推进静态表已有实现。

### 本轮明确不做

- 不改 `TECH_NODES`、`BUILDING_BLUEPRINTS`、`TECH_NODE_DEPLOY`、AI prompt/schema/validator、`blueprint_dynamic`、save/load、settlement 或项目状态。
- 不定义/新增具体科技、科技效果数值、新 operator、蓝图条目或升级规则的实施版本。
- 不让 AI 自动批准，不把科技解锁当作自动建成/升级，不将新维度解释成新商品/账本。
- 不重做既有动态蓝图/圣旨计划流程；只为未来科技提案和蓝图升级识别接口缺口。

### 留待后续裁定（不是本轮偷偷默认）

1. 玩家是否必须批准所有动态科技/蓝图，还是可为特定 AI/机构授予范围有限的自动批准权？**建议默认逐项玩家批准**。
2. 科技扩展的持有人 scope：仅宋侧、各政权各自可选、还是设计全局共享但进度状态各自独立？**建议定义共享 schema、独立 per-polity progress**，但宋侧/外邦是否均可创新需裁定。
3. 动态科技维度最多增什么？**建议只先增领域标签/节点，不开放新数值字段或 operator 自动注册**。
4. 动态节点研究输入/成本/时长/效果的 schema、研究资金主体及外邦技术传播路径需具体数值/史料或玩法裁定。
5. 蓝图升级已建实例的生效策略：逐个升级项目、版本并存、旧项目快照；不能默认全局立即替换。
6. 版本上限、退役/迁移、跨档案兼容及旧 dynamic blueprint 改版政策需后续定义。
