## 一、结论摘要

1. **主流水线结构健康，账本镜像完整**：`_STEPS` 镜像 33 项 ↔ 实际 31 次 `_settle_*` 调用
   ＋2 个非同名前缀步（`_simulate_external` / `_evaluate_timeline_breaks`），**函数对象逐一同一**
   （非仅名字相同），无漏账步。每回结算 **16.53 ms**（31 步实测，12 回合均值，预热后）。
2. **发现 1 处行为回归（必修）**：三段式重构后 `advance_two_phase` **丢失了 AI 可用性预检**
   （同文件的 `settle_turn` 有、它没有）→「AI 未配置」被降级为**后台** `AI_CONTRACT_FAILED`
   （错误码误导），且**民间情况先弹、随后被回滚**。
3. **发现 1 处失败语义缺陷（必修级，已实证）**：后台结算失败时，回滚把 `rich_ready=True` 与
   `rich_report`/`rich_civilian`/`_last_settle_log` **一并还原成上一回合的值**，在
   `_restore_state`（实测 5.63 ms）期间形成「就绪 ＋ 无错误 ＋ 富文本是上月」窗口；
   `Dock.tsx` 的 `if (r.ready) { clearInterval }` 是**单次触发**，命中该窗口即弹**上个月**的
   「回合报告」并**永不再弹**「推演未成」（且回滚后 `turn` 未推进，`turn` 守卫拦不住）。
   高频采样实测：7,016,390 次采样中 **2,004,998 次**命中该状态组合。
4. **并发窗口实测可量化**：`settle_local` **16.5 ms** ＋ `finish_turn` **11–37 ms**
   （含 `save_game` **29 ms**）全部运行在 server `_lock` **之外**；`save_game` 从 daemon 线程
   序列化**被主线程同时改写的 state**。窗口与 docstring 的"~40 ms"估计一致，但**文件落盘**这一环
   未被现有注释覆盖。
5. **守恒断言两极化**：运行时仅 **2 处硬 assert**（太仓恒等 / 财政恒等）；其余 29 步的守恒
   靠测试期 `_STEPS` 逐步账本断言；`money_audit`（Step 10.9）**只读且吞异常**，只留残差记录。
   这是**有意的轻运行时设计**，但意味着"新步偷偷漏钱"在**运行时**不可见，只能靠测试回补。

## 三、必修（会破坏守恒/存档/稳定性，或错误码被伪造）

### M-1 三段式重构丢失 AI 可用性预检 → 「AI 未配置」被误报为「契约失败」

| 项 | 内容 |
|---|---|
| **位置** | `game/core/commands.py:595 advance_two_phase`（对照 `commands.py:288 settle_turn`） |
| **现象** | `settle_turn` 有预检：`if not (ai_client and getattr(ai_client,"available",False)): raise AIRuntimeError(AI_ERROR_CODES["AI_NOT_CONFIGURED"], code="AI_NOT_CONFIGURED")`；**`advance_two_phase` 无此检查**。AI 未配置时：① 首段照常返回 events＋民间情况文本（200 OK）；② daemon 内 `AIClient().economy_decide()` 返回 **`None`**（实测，不抛）→ `_ai_prelude` 的 `if not isinstance(eco, dict)` 分支抛 `code="AI_CONTRACT_FAILED"`；③ 玩家先读到一段民间故事，随后收到「推演未成：**AI_CONTRACT_FAILED**」（文义为"AI 输出不满足契约"，与实际"根本没配 AI"**不符**）；④ 该回合已 `advance_month` 的事件与民意被**回滚**，故事里描述的事情消失了。 |
| **成因** | 三段式拆分时把"AI 预检"留在了旧的同步路径 `settle_turn`，新路径未继承；`AIClient` 未配置时 `economy_decide` 静默返回 `None` 而**不是**抛 `AI_NOT_CONFIGURED`（对照 `ai/client_utils.py:1331 _ai_unavailable` 是存在该码的）。 |
| **改法** | 在 `advance_two_phase` **开头**（`snap = _snapshot_state(state)` 之前）补与 `settle_turn` 同形的预检：<br>`from content.data import AI_ERROR_CODES`<br>`if not (ai_client and getattr(ai_client, "available", False)):`<br>`    raise AIRuntimeError(AI_ERROR_CODES.get("AI_NOT_CONFIGURED", "AI 未接入"), code="AI_NOT_CONFIGURED")`<br>→ 恢复「点过回合立即 503 ＋ 精确错误码」，**不 spawn daemon、不弹会被回滚的故事**。 |
| **验收断言** | ① 新增测试：`advance_two_phase(GameState(...), None)` 与 `AIClient()`（available=False）**均抛** `AIRuntimeError` 且 `e.code == "AI_NOT_CONFIGURED"`；② 断言抛错路径下 **无新线程**（`threading.active_count()` 不变）且 `state.turn` **未推进**；③ 服务端端点测试：`/api/advance` 返回 **503**，`detail["error_code"] == "AI_NOT_CONFIGURED"`。 |

## 四、应修（机制无闭环 / 意图未落地 / UI 无法回答）｜**其中 S-1 已实证，按必修级处理**

### S-1 失败回合回滚把富化字段还原成**上一回合**的值 → 可弹**上月**「回合报告」且吞掉「推演未成」

> **已实证**（`_ming_probe/prove_stale_window.py`：7,016,390 次采样中 **2,004,998 次**命中
> 「`rich_ready=True` ＋ `settle_error=''` ＋ `rich_report='【AI月报】上月文本'`」组合）

| 项 | 内容 |
|---|---|
| **位置** | `game/core/commands.py:580-589`（`_async_settle` 失败分支）＋ `advance_two_phase:615-620`（快照早于复位）＋ `game/frontend/src/renderer/hud/Dock.tsx:87-129` |
| **现象（后端）** | `snap` 在**复位之前**拍摄，故含上一回合的 `rich_ready=True`、`rich_report`、`rich_civilian`、`_last_settle_log`。失败时 `_restore_state(state, snap)` 把这四个字段**整体还原成上月值**（随后仅 `settle_error`/`rich_ready` 被显式覆写，**三处富化字段没有**）。实测失败回合终态：`settle_error='RUNTIME:RuntimeError'`、`rich_report='【AI月报】上月文本'`、`rich_civilian='【AI民间】上月文本'`、`_last_settle_log` 仍为上月 33 行。 |
| **现象（前端·更严重的后果）** | `_restore_state` 还原 `rich_ready=True` 的那一刻到 `state.settle_error = ...` 赋值之间，形成「**ready=True ＋ 无错误 ＋ 富文本是上月**」窗口（`_restore_state` 实测 **5.63 ms**，含记忆库 `rollback_after` 截断）。`Dock.tsx:90-91` 是**单次触发**：`if (r.ready) { clearInterval(_t); ... }` —— 轮询一旦落在此窗口，会走 `:108-125` 的成功分支弹出「**回合报告**」（内容是**上个月**的月报与朝报），随后 interval 被清除，**「推演未成」永远不会再弹**；且 `:110` 的 `turn === stNow.turn` 守卫在**回滚后（turn 未推进）恒成立**，拦不住它。<br>`AdvancePanel.tsx:30-33` 独立地只判 `r.ready` 就 `setRich(r.rich_civilian)`，**不判 `settle_error`** → 把上月 AI 民间反应当作本月内容就地替换民间段。 |
| **成因** | 回滚语义＝"把 state 折回快照"，UI 语义＝"本回合失败"；两者对"本回合富化字段应为空 / `rich_ready` 应为 False"的期望不一致。快照时点早于复位，使"折回"必然带回上月的 `ready` 与富文本。 |
| **改法** | **后端单点（必做）**：失败分支在 `_restore_state` 之后、`settle_error` 赋值**之前**先清空，再置错误与 ready：<br>`state.rich_report = ""`<br>`state.rich_civilian = ""`<br>`state._last_settle_log = []`<br>`state.settle_error = (…code…) + ":" + type(e).__name__`<br>`state.rich_ready = True`<br>—— 前三条使前端的成功判据（`rich_report \|\| rich_civilian`）在**整个失败窗口内恒为假**，杜绝上月弹出。<br>**前端加固（建议同做）**：`AdvancePanel` 轮询 `if (r.settle_error) { clearInterval; return; }` 先于 `setRich`；`Dock` 的 `r.ready` 分支改为「先判 `settle_error`，否则若 `rich_report/rich_civilian` 为空则**不 clearInterval**，继续等到真值或 180s 上限」。 |
| **验收断言** | ① 单元：monkeypatch `economy_decide` 抛错 → `_wait_ready` 后断言 `rich_report == ""`、`rich_civilian == ""`、`_last_settle_log in (None, [])`、`settle_error != ""`；② 跨回合：先跑成功一回合（富文本有值），再让下一回合失败，断言富化字段**不含**首回合文本；③ 采样回归：用高频采样器（`prove_stale_window.py` 范式）复跑 200 次失败回合，断言**零**「ready=True ＋ settle_error='' ＋ rich_report 非空」样本；④ 前端：`r.ready && !r.settle_error && !r.rich_report && !r.rich_civilian` 不得清 interval。 |

### S-2 `finish_turn` 在 daemon 线程落盘，与玩家 action 无互斥（存档一致性）

| 项 | 内容 |
|---|---|
| **位置** | `game/core/commands.py:658 finish_turn`（docstring 自称"**主线程**"，实际由 daemon 调用）；`core/save_load.py:96 save_game` |
| **现象** | daemon 在 `server._lock` **之外**执行：`settle_local`（16.5 ms 写 state）→ `finish_turn`（实测 **11.14 ms 均值 / 37.05 ms 最大**，含每回合 `mg.save` 与正月 `save_game` 实测 **28.90 ms**）。此窗口内玩家 action（`/api/action` 持 `_lock`）可改同一 state；`save_game` 逐字段读取并 `json` 序列化 `prefectures`/`pops` 等**可变嵌套结构**，可能落出**半新半旧**的存档，或触发 `dictionary changed size during iteration`。`/api/advance/round2` 虽持 `_lock` 读 `_state_to_dict`，但**锁只约束了读方**，写方（daemon）不参与 → 互斥是单向的。 |
| **成因** | 三段式为了避免阻塞 HTTP 20–75 s，把整条结算链移出请求锁；文件落盘随之一并移出。 |
| **改法** | 三档，按代价递增：<br>**①（最小）**：把 `finish_turn` 拆成"纯内存收尾"（`check_game_over` / 记忆库压缩标记）与"落盘"（`mg.save` / `save_game`），**落盘段回到持锁路径**：由 `/api/advance/round2` 首次观察到 `rich_ready=True` 时（或专门的 `/api/advance/commit`）在 `with _lock` 内执行一次。需在 state 上加 `_persist_done` 幂等标记。<br>**②（中）**：daemon 写 state 时改用 `server` 提供的共享锁（把 `_lock` 下沉为 `state._lock` 或注入 `with_lock` 回调），`settle_local`+`finish_turn` 整体持锁；代价是玩家 action 在这 ~50 ms 内排队（可接受）。<br>**③（兜底）**：`save_game` 改为**先在锁内 `copy.deepcopy` 快照，再在锁外写盘**（序列化对象不再与主线程共享），仅解决"半新半旧"，不解决 state 随机读写竞争。 |
| **验收断言** | ① 并发压力测试：线程 A 循环 `_async_settle` 成功路径，线程 B 循环播放 20 种 action，跑 200 回合；断言**无异常**、每回合存档 `load_game` 成功、且 `turn`/`treasury`/`prefectures` 三者取自同一回合（在存档里加 `turn` 一致性校验或用现有守恒断言）；② `finish_turn` 的 docstring 与调用点一致（不再是"主线程"）。 |
