## 1. 模块地图

> 依赖方向总体为：`frontend` →(HTTP/IPC)→ `backend` ⇄ `commands` → `settlement*` → {`game_state`, `content`, `money`, 各机制模块}
> ；`ai` 产出**契约**→ `engine/state_applier` 落地 → 回写 `game_state` 与 `memory`。

### 1.1 回合与时序（入口层）

| 模块 | 职责 | 关键符号 | 依赖 |
|---|---|---|---|
| `core/commands.py`（1,697 行，最大） | 与 UI 无关的游戏命令层、回合时序（AI 推演→结算→叙事）、`advance_and_settle` 原子封装、结算异常**快照回滚** | `advance_and_settle`、`settle_local`、`envoy_diplomacy`、`allocate_payraise` | → `settlement`、`engine/state_applier`、`memory`、`ai` |
| `core/commands_decree.py` | 诏令/密旨/拟旨/会签族、内帑金额解析 | `parse_decree`（**0 生产调用**，见 §2.4） | → `content/data_decree` |

**结果**：快路径 `-m "not slow"` **≈ 27–33 s**（较全量省 **约 30 s / 50%+**）；
慢例 `-m slow` 单跑 ≈ 28 s。**静态守卫/哨兵（<1.2 s）刻意不标**——快路径必须始终跑它们。

**两个过程教训（都是我的操作错）**：
1. **先写盘后校验**：第一版脚本"插入 `import pytest` → 写盘 → 才 AST 校验"，而插入点用
   "最后一个以 `import`/`from` 开头的行"定位 → 落进了**多行 import 的括号内**，
   文件落盘即坏、pytest 收集报错。**改为：AST 定位插入点（取顶层 import 的 `max(end_lineno)`），
   且 AST 通过才落盘。**
2. **脚本中途崩溃导致后续步骤静默未执行**：第一版在循环里抛异常，后面的 `pytest.ini` marker
   注册从未运行 → 表现为"标记都打了但全是未知警告"。**教训：脚本要把"哪些步骤真的执行了"打清楚，
   并且崩了要能续跑（幂等）。**

**另一个坑**：`pytest.ini` 的 `addopts = -q` 与我命令行的 `-q` 叠加成 `-qq`，**会抑制摘要行**
（"1101 passed, 8 deselected" 不显示）→ 我曾误以为"没有摘要"。取摘要需 `-o addopts=` 显式覆盖。

### 13. 一条命令全量验证（2026-09-27）

**为什么是地基**：验证层已从 1 层长到 5 层（后端 pytest / 前端 vitest / tsc 双配置 / 面板截图矩阵 /
地图基准），却散落在 README 与 `cloudbase-check.ps1` 的 §8 里 —— **"我跑过了"无法被复述**。

|---|---|

### 15. F401 未用导入清理：494 → 0（2026-09-27）

**为什么不能直接用 `ruff --fix`**：ruff 的 F401 只看得见**本文件**。对 `content/data.py` 这类
**façade 模块**（外部到处 `from content.data import X`），ruff 会把 300 条再导出**全当死导入删掉** —— 一删全项目崩。

**做法（两段式）**
1. **先用 AST 全仓判定"再导出 vs 死导入"**：把 `from <模块> import <名>` 与 `alias.<名>` 的引用者建索引；
2. **把再导出名补进 `__all__`**（没有就创建）—— ruff 对 `__all__` 成员不再报 F401；
3. 再 `ruff --fix`：此时剩下的才是真死导入，删除安全。

**结果**

| 项 | 数 |
|---|---|
| F401 清理前 | 494 |
| 其中**再导出**（全仓有引用，已补进 `__all__`） | **269** |
| 真死导入（已删） | **207** |
| F401 清理后 | **0** |

涉及文件（再导出集中的 4 个）：`content/data.py`（新建 `__all__` 257 名）、`ai/client.py`（新建 `__all__` 9 名）、
`core/commands.py`（追加 2 名到既有 `__all__`）、`core/army_models.py`（新建 `__all__` 1 名）。
**全量 pytest 1175 passed / exit 0**。

**⚠️ 真实的过程失败（两次，都记下来）**

**失败 ①：作用域漏判 → 删掉测试仍在用的名字。**
第一版分类器只扫 `game/**`，而**测试与开发脚本在 `_dev_tools/**`**（在 `game/` 之外）→
`BLUEPRINT_BRANCHES` / `FINANCE_UNITS` / `imperial_distance` 被判"无人引用"删除 →
**3 个测试文件收集失败**（`ImportError: cannot import name ...`）。
- **教训：判定"无人引用"必须**全仓**（源码 + 测试 + 开发脚本 + 文档示例），作用域漏一块就是错的。**
- 处置：`git checkout -- .` 回滚本次清理，扫描范围改为整个 `sz/`（261 个 py 文件）后重做 →
  再导出数由 259 升到 **269**（多出的正是测试要用的那批），`--fix` 删除数由 217 降到 **207**。

**失败 ②：文件名/命名格式踩坑，导致分类器"全判死"。**
首版分类器输出"再导出 0 / 死导入 476"——**明显不合理**（`content/data.py` 必然是 façade）。
两个原因叠加：
1. Windows 下 `os.path.relpath` 产出**反斜杠**，模块名成了 `content\data`，与 AST 里的 `content.data` 永不匹配；
2. ruff 对**相对导入**报的名字是**限定名**（`` `.data_constants.ANNUAL_TAX_BASE` ``，带前导点与模块前缀），
   直接拿去查 `("content.data", name)` 永不命中 —— 必须**取最后一段**作为符号名。
- **教训：工具给出"全 0 / 全 1"这类极端分布时，先怀疑工具自己**（这是本项目第三次同类教训）。
