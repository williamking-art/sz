## 1. 结论摘要

1. **分层方向大体成立，反向边是"点状"而不是"面状"**：全库 **329 个模块 / 996 条模块边**，
   明确违反分层方向的只有 **37 对 / 65 条 import 语句**（占内部 import 的 4.3%）。其余是合法的向下依赖。
   也就是说**不需要重构整棵树**，只需要处理这 37 对。
2. **循环依赖 7 个强连通分量（SCC）/ 69 个模块**，其中最大一个 **37 模块**（结算链 + AI 契约 + 读档入口全在里面），
   第二大 **20 模块**（基础账本 ↔ 业务计量）。**没有一个环能靠"移动文件"拆开**——这与 2026-10-06 阶段 1 的结论一致
   （当时的 12 条反向边"无一条能靠机械改动拆出去"），现在环里**多了 2 个 application 模块**。
3. **口径单点基本成立**：money / pop / transport / literacy / decree_effect 五个口径都还有唯一的实现家，
   生产侧消费方集中（`foundation.ledger.pop_bridge` fan-in **41**、`content.data` **92**）。
   **前端 0 处复制结算算法**（只有展示格式），硬约束 §3-2 在这一侧没破。
4. **真正的问题不是"结构乱"，而是"同一份实现存在两套"**：
   `core/settlement_imperial.py`(484L) 与 `core/domains/politics/settlement_imperial.py`(257L)、
   `core/domains/population/settlement_hidden.py` 三个模块之间有 **8 个函数体逐字节相同、重复 415 行**，
   而且**活的是其中一份、死的是另一份**（§6.1）。这是"改错文件"型事故的温床，比越层边更值得先处理。
5. **可复用资产比想象中多，重复实现也比想象中密集**：`_num` 在 **31 处**各自定义、前端 `asNum` **12 份**、
   `asStr` **15 份**；同时 `core/foundation/common/numeric.py`（fan-in 17）、`utils/format.ts`（fan-in 19）
   本来就可以承接它们。⇒ 复用清单的主体是**"把散落的副本收回到已有的单点"**，不需要新建抽象层。
