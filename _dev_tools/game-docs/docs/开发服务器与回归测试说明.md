## 一、这台机器解决什么问题

本机（Windows 开发机）**已具备**三套工具链，但**全都没有加入 PATH**，
直接用 `node` / `python` / `cargo` 会提示找不到（用 `where` 或 `Get-Command` 也查不到）。
调用时需用绝对路径：

| 工具 | 本机位置 | 版本 |
|---|---|---|
| Node / npm | `D:\codebuddy\tools\nodejs\node-v20.19.5-win-x64\` | 20.19.5 / 10.8.2 |
| Python | `D:\codebuddy\.audit-venv\Scripts\python.exe` | 3.13.14（含 fastapi / pytest / shapely / rich / requests / Pillow） |
| Rust / cargo | `C:\Users\<用户名>\.cargo\bin\cargo.exe` | 1.98.1 |

> 排查提示：**不要只用 PATH 判断"有没有装"** —— 本次就因此误判过。
> 应同时检查 `D:\codebuddy\tools\`、`.audit-venv`、`~/.cargo/bin` 等位置。

因此服务器**不是"本机跑不了"的替代品**，它的独立价值在于：

| 用途 | 为什么用服务器而不是本机 |
|---|---|
| **Linux 平台验证** | 本机是 Windows。部分用例存在平台相关行为（如立绘路由用例把 Windows 路径 `D:\...` 写死，在 Linux 下解析为空串而失败），需要在目标平台上跑 |
| **Python 版本交叉验证** | 本机 3.13 vs 服务器 3.11，取整/浮点行为可能不同；两边对比可区分「环境差异」与「真实缺陷」 |
| **Linux 产物构建** | `songzuo_server` 若要部署到 Linux，应在 Linux 上 `cargo build --release` |
| **独立 CI** | 不占用本机、不依赖本机环境，push 后自动跑回归 |
| **长跑 / 压力测试** | 240 月对账等重算可后台跑，不挡本机开发 |

> 注：2 核 2GB 是偏紧的配置，编译 Rust 前已补 2GB swap（见 §3）。
> 这台机器适合**测试与构建**，不要在未评估前承载线上服务。

## 四、日常操作

### 4.1 同步代码

```bash
cd /opt/sz
git pull origin main
```

> 服务器直连 GitHub **时好时坏**：clone 时实测可达 10MB/s，但 `fetch`/`pull`
> 偶发超时（`Failed to connect to github.com port 443`、
> `Failure when receiving data from the peer`）。失败就重试；
> 若连续失败，可从本地直接 `scp` 覆盖单个文件（内容一致时不会与后续 pull 冲突）。

### 4.2 跑全量回归

```bash
cd /opt/sz/game
.venv/bin/python -m pytest           # 当前约 892 例，约 1 分钟
```

长跑建议放后台（避免 SSH 会话被切断）：

```bash
cd /opt/sz/game
nohup .venv/bin/python -m pytest > /tmp/pytest.log 2>&1 &
tail -f /tmp/pytest.log
```

> 注：`pytest.ini` 里 `testpaths = ../_dev_tools/game-dev/tests`，
> 所以**必须从 `game/` 目录**运行。

### 4.3 编译并运行 Rust 后端（已实测）

编译（**实测 1 分 07 秒，产出 3.0MB 二进制**）：

```bash
cd /opt/sz/songzuo_server
export PATH=$HOME/.cargo/bin:$PATH
nohup cargo build --release > /tmp/cargo.log 2>&1 &
tail -f /tmp/cargo.log
```

依赖走 `/root/.cargo/config.toml` 里配的 rsproxy 镜像（crates.io 在境内不稳）。

单元测试（**实测 3 passed**）：

```bash
cargo test --release
```

本地运行验证：

```bash
SONGZUO_ADDR=127.0.0.1:18080 ./target/release/songzuo_server
curl -s http://127.0.0.1:18080/healthz
curl -s -X POST -H "Content-Type: application/json" --data-binary {} \
     http://127.0.0.1:18080/api/new_game
```

**云托管就绪性（已实测）**：只设 `PORT` 时会自动绑 `0.0.0.0`（`ss` 可见 `LISTEN 0.0.0.0:<PORT>`），
正合容器探针要求；未设 `SONGZUO_SERVER_TOKEN` 时 `/api/*` 只接受回环来源。

### 4.4 构建前端（已实测）

Electron / electron-builder 的二进制默认从 GitHub 下载，在本链路会被限速卡死，
**必须先接国内镜像**：

```bash
cd /opt/sz/game/frontend
npm config set registry https://registry.npmmirror.com
export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
export ELECTRON_BUILDER_BINARIES_MIRROR=https://npmmirror.com/mirrors/electron-builder-binaries/
nohup npm install > /tmp/npminstall.log 2>&1 &      # 实测 733 包 / 31 秒 / 741MB
```

构建（**实测 11.11 秒**）：

```bash
npm run build        # electron-vite build
```

产物在 `game/frontend/out/`（126MB，已 gitignore）：`out/main`、`out/preload`、`out/renderer`。
其中 `out/renderer` 即浏览器可用的静态产物 —— 想发到 CloudBase 静态托管时用它，
但 Electron 桌面链路的 `electron` API 需另行剥离。

### 4.5 常驻运行参考后端（联调用）

```bash
cd /opt/sz/game
.venv/bin/python -m backend.server      # 默认 127.0.0.1:8080
```

### 4.6 构建并运行容器镜像（已实测）

机器上已装 Docker 29.7.0。Docker Hub 直连会被限速，先在 `/etc/docker/daemon.json`
配腾讯云内网镜像源（**已配置**）：

```json
{ "registry-mirrors": ["https://mirror.ccs.tencentyun.com"] }
```

构建（**实测：builder 镜像 1.23GB → 成品 134MB / 内容 33.3MB**）：

```bash
cd /opt/sz/songzuo_server
docker build -t songzuo_server:0.1.0 .
```

运行：

```bash
docker run -d --name sz-test -p 127.0.0.1:18090:8080 \
  -e PORT=8080 -e SONGZUO_SERVER_TOKEN=sz-dev-token \
  songzuo_server:0.1.0
curl -s http://127.0.0.1:18090/healthz
```

> ⚠️ **容器化必读两条**
>
> 1. **`SONGZUO_SERVER_TOKEN` 必须设置。** 源码在未配 token 时只放行回环来源
>    （`is_loopback`），而 Docker 端口映射后容器看到的源 IP 是网桥网关（172.17.0.1），
>    **不是回环** —— 结果是 `/healthz` 正常 200，但**所有 `/api/*` 一律 401**。
>    实测三种情形：无 token → 401、`Authorization: Bearer <正确 token>` → 200、
>    错误 token → 401。鉴权头格式为 `Authorization: Bearer <token>`。
> 2. **`SONGZUO_ADDR` 在容器里不要设。** 它优先级高于平台注入的 `PORT`，
>    一旦设置会覆盖端口，readiness probe 直接判失败。

## 五、持续集成（CI）

回归由服务器上的 `/opt/sz-ci/ci.sh` 承担，两条触发路径：

| 路径 | 触发方式 | 说明 |
|---|---|---|
| **本地直推**（推荐） | `git push server master:main` | 服务器 `post-receive` 钩子立即跑回归，**不经过 GitHub**，最可靠 |
| **定时轮询**（兜底） | cron 每 30 分钟 | `git fetch` 检查远端 main 是否有新提交；**镜像优先 + 直连回退**（各试 2 次）——服务器直连 GitHub 的 git 数据传输会被限速到 <1KB/s，必须走镜像 |

### 5.1 一次性配置

服务器侧（已完成）：

```bash
cd /opt/sz
git config receive.denyCurrentBranch updateInstead   # 允许直推并同步更新工作区
chmod +x /opt/sz-ci/ci.sh /opt/sz/.git/hooks/post-receive
```

本地侧（已完成）：

```bash
git remote add server ssh://root@<公网IP>/opt/sz
```

私钥不是默认名时，push 前指定（Windows PowerShell）：

```powershell
$env:GIT_SSH_COMMAND = "ssh -i C:/Users/<用户名>/.ssh/sz_cvm_ed25519 -o StrictHostKeyChecking=no"
```

### 5.2 日常用法

```bash
git push origin master:main     # 推 GitHub（对外）
git push server master:main     # 推服务器 → 自动触发回归
```

查看结果：

```bash
ssh -i ~/.ssh/sz_cvm_ed25519 root@<公网IP> "tail -20 /var/log/sz-ci.log"
```

日志格式：

```
[2026-09-23 10:15:58] PASS 757a68d77c  用例 892 全通过
[2026-09-23 10:12:06] 收到本地推送，开始回归
[2026-09-23 09:59:25] fetch 失败（已重试 3 次，跳过本轮）
```

失败时是 `FAIL <短SHA>  失败 M 例（用例 N）` 并附前 20 条失败用例。
每一轮的完整 pytest 输出留档在 `/var/log/sz-ci-last.log`。

> 实现备注：**完整套件跑完后 pytest 自己的汇总行会丢失**（套件内部有测试在收尾阶段
> 吞掉了 stdout，小规模子集则正常）。因此 CI 不依赖汇总行，而是：
> 收集阶段用 `--collect-only -q` 累加用例总数、正式跑用 `FAILED/ERROR` 行统计失败数，
> **最终判定以返回码为准**。

### 5.3 注意

- CI 运行前会**丢弃服务器工作区的本地修改**（`git checkout -- .`）—— 不要把服务器当开发机。
- 服务器上 `.git/hooks/post-receive` 与 `/opt/sz-ci/ci.sh` 都不入 git（前者在 .git 内，后者在仓库外），重建环境时需按 §5.1 重做。
