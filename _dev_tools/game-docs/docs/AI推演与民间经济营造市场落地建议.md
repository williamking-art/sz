# AI 推演与民间经济、营造市场落地建议（设计稿）

> **目的**：把《民间需求与营造材料市场设计.md》的既有构想，与《民间经济与营造市场统一设计.md》的官民仓储/经营/建筑模型，以及现有 AI 回合推演机制合并为一条可分批实施的路线。
> **状态**：分阶段落地指导，**部分基础能力已实现，完整市场/营造闭环尚未放行**。不取代上述设计文档或用户既有定论；分阶段实现、接线、校准和未关闭项以 `specs/market-civilian-economy/tasks.md`、`specs/unified-civilian-market/tasks.md` 与 `specs/decree-action-chain/tasks.md` 为准。涉及经济口径、参数和历史解释的分歧须先裁定，再改核心模拟。
> **游戏定位**：AI 驱动的宋代政务与社会推演游戏。规则确保因果、账物和可解释性；AI 在这些约束中自由选择策略、立场和创意，不被写成固定脚本。
> **设计基准**：1101 年开局；项目硬约束见 `AGENTS.md`，特别是 POP 挂载律、货币口径单点、缺失值不作 0/1.0、核心模拟改动先定口径再加定向回归。
> **当前实施顺序**：请以本文 §14 为最新落地路线；§9–§10 的旧阶段清单用于保留设计背景，不再直接作为排期。具体代码完成度以 `specs/market-civilian-economy/tasks.md` 和 `specs/decree-action-chain/tasks.md` 为准，不重复建设已有交易、动态蓝图、官员 Agent 与旨意能力。

## 1. 目标与不做什么

### 1.1 落地目标

1. 让民间 POP 成为持续的市场买方、生产者、投资者和持货者，而不仅是税赋与政府支出的承接方。
2. 让“需求—财富—供给—成交—库存—价格—生活状况—政治反应”构成可追踪的回合因果链。
3. 让口粮与商品粮、官仓与民仓、官营与民营、政府工程与民间营造共处于一套经济规则中。
4. 让 AI 能因不同局势提出不同方案，并可提出原始内容库没有的新科技、新商品、新蓝图和新装备。
5. 保留生成内容带来的混沌、分歧、失败与意外，不要求每回合收敛成最优解；所有实际数值变化仍须可审核、可守恒、可回放。

### 1.2 不做什么

- 不让 LLM 直接改 POP 财富、人口、库存、价格、建筑等级或回合进度。
- 不把历史事件年表扩成唯一玩法路线；历史窗口是参考与世界压力，不是阻止玩家改写历史的强制轨道。
- 不让缺货被虚拟供给、不让商品需求直接生成商品、不让科技解锁变成免费实物。
- 不为了所谓真实而把所有行为细节写成固定公式；参数只给边界、惯性和反馈，策略选择留给 AI 与玩家。
- 不同时重做全部商品、全部官仓和全部 AI 契约；按可验证的闭环分期接入。

## 2. 现状与需要补齐的结构

当前回合的主方向是“回合前 AI 推演 → 程序结算 → 回合后叙事”。经济、军事、外交等领域契约按状态、关键词或上一回合 diff 唤醒；程序负责数值与守恒。同时，游戏已有具名大臣档案、人格、派系、关系、记忆与一对一召对。**二者是两层不同的东西**：领域 Agent 是推演/分析能力，具名官员才是有身份、有立场、有记忆并能彼此冲突的行动主体。现有月度结算主要接入领域级槽位；不能因此把“大臣个人 Agent”缩减成一个经济 Agent、财政 Agent 或派系代表。这正是本设计需要补齐的核心接口。

| 现状 | 设计影响 | 落地建议 |
|---|---|---|
| `economy.md` 主要让 AI 为全国经济输出有限档位 | 有方向，无地点/行业/利益关系，许多局势结果趋同 | 保留宏观档位，新增可选的区域与市场意图 |
| `settlement_granary.py` 按财富比例扣商品消费，但消费入商品库存时没有真实卖方成交约束 | 支出、购买和供给不构成真实市场闭环 | 先完成库存撮合，再把需求篮子接入 |
| 宋方主要消费需求围绕布、绸，营造建材市场缺少动态价格发现 | 商品市场规模小，建筑材料供需与民间生活脱节 | 以最少商品起步，逐步扩建商品注册表与生产配方 |
| 月度推演以领域级 Agent 槽位为主；大臣人格/记忆已有，但个体作为行动者进入月度政策链的覆盖不足 | 若让领域 Agent 替代官员，会抹平个人目标、官职权限、派系关系和对同一局势的异见 | 以具名官员 Agent 为决策主体；经济/财政/军事等领域契约改作分析能力或专业幕僚输入 |
| 财政 Agent 停用、投资/改革尚无生产闭环 | 直接重启会产生无消费者结果，或让共享系统代理代替实际主事官员 | 先确定由哪些官员发起/会签/执行，以及每一类领域结果如何进入官员决策 |
| 局势评分 AI 只在有活跃局势时调用；部分结果是程序惯性/规则推进 | 不同系统的 AI 参与密度不一致 | 把 AI 评分用于解释与情境判断，程序仍负责合法性和实际变化 |
| 事件压力较多依靠规则和阈值，叙事以真实来源为界 | 可解释但新兴事件类型不足 | 允许因果支持的新事件提案，验证后再决定是否产生数值后果 |
| 外邦模型按接触与重要性分层，部分政权使用简单模拟 | 低交互对象计算轻，但竞争对手的策略可能缺少能动性 | 对接壤/交战/贸易对象升级策略推演，其余保持低成本摘要 |

以上列的是架构接点和设计机会，不表示所有差异都是缺陷。实现时要对照当前模块的生产调用与读档兼容，不以旧文档单句替代运行事实。

## 3. 核心架构：意图开放、执行受控、结果反馈

### 3.1 建议的回合结构

```text
玩家行动 / 事件触发
        ↓
每名相关官员以自己的身份读取有限奏报（专业、记忆、立场、关系与信息精度各异）
        ↓
官员 Agent 分别形成奏议、私下经营、支持/反对、联署、拖延或不表态
        ↓
官员之间交锋与结盟：交换信息、质疑奏议、争取预算/差遣；必要时形成多轮朝议
        ↓
皇帝亲裁或按官制/惯例运行：玩家旨意优先；无人裁决时由权限、派系力量、时限和执行条件决定去向
        ↓
具体官员与机构承办：征购、平粜、调运、营造、赈济、军需等实际执行
        ↓
程序校验并落账：权限、资金、实物、时间、前置条件、账本守恒
        ↓
结果归因：成功、部分执行、受阻、失败、意外后果及实际受益/受损者
        ↓
各官员分别更新自己的记忆、判断、关系与下一步打算；叙事只描述已发生事实
```

领域分析可批量计算或按需调用，但不能合并官员身份。每个具名官员始终有独立、持久的 Agent 状态；“被唤醒”表示本回合需要展开其认知与行动，不表示该官员此时才存在。普通月份可用低成本个体状态推进；只有职责相关、本人有利害、记忆被触发、收到圣旨/弹劾/任命，或局势重大时，才请求 LLM 生成该官员的完整行动。可把多个官员的请求装入一次模型调用以降低成本，但输出必须逐人独立，不能变成一个共享人格的“朝廷综合回答”。

### 3.2 AI 的自由空间与引擎的硬边界

| AI 可自由提出或选择 | 程序必须确定地校验/执行 |
|---|---|
| 每名官员自己的关切、政策目标、风险偏好、区域与行业重点 | 当前状态、合法范围、资源来源、货币与实物账 |
| 每名官员选择进言、沉默、反对、结盟、交易、执行、拖延或规避 | 买方购买力、卖方库存、运输容量、施工材料和工期上限 |
| 对圣旨的个人解释、对其他官员的态度、承办方式及行动优先级 | 已注册效果算子、官职权限、数值封顶、POP 与资产守恒 |
| 对新技术/商品/建筑/装备的自然语言提案及因果假设 | schema 校验、去重、前置、存档迁移、未支持效果拒绝执行 |
| 争议、误判、策略失败和临时替代方案 | 状态事务原子性、固定随机种子、完整结算与错误留痕 |

**个体 Agent 提出“我想做什么、为何如此、愿付什么代价”；皇帝/制度决定授权；引擎决定实际可做多少。**不能由一个全知协调 Agent 把不同官员的方案压成唯一最优答案。非法提案应拒绝、部分批准或挂起并说明缘由，不要静默替官员改成另一个行为。

### 3.3 官员 Agent 的身份模型

每一位进入游戏名册的官员都是独立 Actor/Agent 实例，不因同派、同职或同领域而合并。Agent 的最小状态应包含：

- **身份与时间**：人物 ID、名号、存活/在野/在朝、任官与离任、任职机构、权限、任期/历史阶段；
- **个性与能力**：已有 traits/persona、专业知识、风险倾向、表达风格与行动能力；
- **立场与利害**：政策立场、派系及利益集团关系、对具体政策的得失判断；忠诚与贪腐等隐藏字段继续遵守既有保密规则，不直接暴露给模型或玩家；
- **私人关系**：支持、反对、恩怨、师承、举荐、联署和政治承诺；
- **个人记忆**：本人参与的召对、圣旨、承诺、成败、处分、功劳和观察；不能把甲的私下谈话当成乙亲闻；
- **认知边界**：官职可见范围、奏报精度、消息来源、滞后、传闻和未知项；
- **当前意图**：本回合目标、拟议动作、执行状态、条件/风险与未竟承诺。

官员任免、升迁、贬谪、致仕、病故与复起都作用于同一人的生命周期；换职改变权限、可见信息、行动资源和同僚关系，但不换人格或抹去记忆。新官员进入名册时创建独立 Actor；离朝官员不再承办朝廷事务，但可继续以在野士人、地方势力或历史人物身份产生影响。

具名官员一人一 Agent 不等于每回合一人一条网络请求。可采用**个体状态 + 事件唤醒 + 批量推理**：每位官员都有独立输入/输出/记忆，通常由轻量程序更新；遇关键议题才让相关官员调用模型。若批量推理，须使用逐官员分隔上下文与输出 schema，防串人格、串记忆和互相污染。

**范围声明**：当前 `MINISTERS` 具名大臣体系已有 43 名现役/历史人物记录、人格/立场演化、派系关系与逐人召对记忆等组件；月度结算仍以领域级契约为主，不能据此宣称每个官员已经每月独立决策。后续“官员 Agent 化”要逐步把官职持有者和地方具名官员接入个人 Agent 状态机，而不是另造一套替代现有名册的平行人物表。无姓名的一般吏役与 POP 不自动生成海量 LLM 对话；若以后需要个体化，应先创建实体 ID 和生命周期，再由事件唤醒。

### 3.4 不确定性从哪里来

- **信息差**：朝廷、地方、商人、军队看到的奏报不同；数值区间、读数滞后与消息来源保留。
- **利益差**：不同阶层、派系、机构与地方对政策有不同得失；AI 可据此支持、拖延、规避或寻租。
- **环境变动**：灾害、战乱、航运、季节和市场冲击通过有语义的变量进入推演。
- **策略差**：相同局势可选择不同合法应对，不强制唯一最优策略。
- **模型随机性**：用于叙事和策略选择；账目结算本身保持确定，可由种子复现。

不要用不受约束的随机数扰动钱粮、人口或库存来制造混沌；也不要只靠 AI 写不同故事，却让状态每次都完全相同。

## 4. 统一经济对象与交易规则

### 4.1 五类数据必须分开

1. **需求**：主体想要什么、目标量、优先级、替代品和满足期限。
2. **商品**：可生产、储存、运输、采购、消费或作为原料的实物。
3. **库存**：商品的真实持有人、所在路府、用途/预留状态。
4. **价格/预算**：基准估价、实际成交价、预算上限、税费、运费和工钱。
5. **交易/流量**：从谁到谁、转了多少实物和货币、因何发生。

市场汇总只是对底层库存与报价的读视图，不能形成第二份商品账。预留材料可以标记为不可售，但不得复制库存。

### 4.2 消费成交规则

```text
期望量 = 人口与生活层级形成的需求
支付量 = 预算/可支配财富按当期价格能购买的数量
可售量 = 本地库存 + 已到货输入 − 已预留/不可售库存
成交量 ≤ min(期望量, 支付量, 可售量)
```

一笔 POP 购买应同时完成：买方财富减少、卖方财富增加、卖方商品库存减少、买方库存增加。供给不足时产生未满足需求；财富不足时产生被价格排挤；两者必须可区分。

AI 可改变需求篮子、储蓄/消费倾向、可替代品接受度、囤售策略和地区经营选择。阶层偏好是初始倾向而非固定清单；商品与价格变化后，AI 可以改变选择。

### 4.3 粮食：同一种粮，不同用途与所有权

- **口粮**是实际吃掉的粮，不是独立商品；仍由现有职业口粮规则计算并从真实粮库存扣除。
- **商品粮**是进入交易、采购、征收、运输或储备流程的粮；转成商品粮时必须从原持有人库存移出/锁定。
- 农户自留粮、商人待售粮、官仓储备粮、军粮预留粮要有不同所有者/用途状态。
- 先保农户口粮与必要安全垫，再计算可售粮；不能把农粮先计入卖方，再要求农户买回自己的口粮。
- 买粮、吃粮、缴粮、官府采购、官仓平粜、赈济与军需拨粮必须是不同交易类型，避免双扣款/双扣粮。

### 4.4 官仓与民仓

官仓按调价、赈济、军需/官供等目的设子用途。官仓库存默认不算民间市场供给：

- 平粜：官仓库存 → 市场买方库存；买方付钱，官仓粮减少。
- 赈济：官仓库存 → 受济 POP 粮；不伪装成市场交易。
- 军需：官仓库存 → 军队指定粮食用途。
- 籴购：官府付钱给出售者，卖方库存减少、官仓库存增加。

民仓归农户、士绅、商人等持有者。其出售/惜售/囤积由价格预期、需求压力、政策风险和 AI 策略决定。征购或强征必须记出资金/税权/强制代价和社会后果，不能当作无主供给。

首期先用用途机制区分仓储，不要求一次建完复杂仓名史制；之后可依据地区、年份和政策扩展仓制差异。

### 4.5 官营与民营

官营、专营、许可经营、官府采购和民营都是生产/流通制度属性：

- **民营**：由 POP/经营主体投入资金和原料，雇工生产，货品归经营者并承担盈亏。
- **官营**：官府支付采购、工资、维护成本，货品进入官有库存、军需或官售渠道。
- **专营/许可**：限制生产或销售资格；商人仍可参与生产、批售或运输，税利按制度分配。
- **官府采购民产**：官府成为民营生产者的买方，购买后转官有用途。

同一种商品可依政策改变经营方式。不能把“专营”简化成无成本生产，也不能假设官营天然低价、高效、无寻租。

## 5. 商品市场与生产链

### 5.1 商品类别按宋代生活与生产关系扩展

商品扩展应从宋代开局生产基础和游戏现有维度逐批做，不先建立庞大现代商品清单：

- 食物与饮用：粮、酒、茶、盐及已有畜牧/渔产；
- 衣着：布、绸及可确认的纤维制品；
- 燃料与生产资料：木、炭、铁料/铁器、农具；
- 日用和营造：陶瓷、木器、纸、木石砖；
- 地域特产与高阶商品：依据路府资源、贸易路径和技术逐步启用。

每种商品应声明名称、单位、基准价、价格带、存储/损耗、需求用途、生产配方、生产者、科技/建筑前置、可替代品、贸易制度和时代可用性。缺数据的商品先是提案，不进入已生效市场。

### 5.2 商品间配方链

生产链连接原料、岗位、建筑、技术和成品。例如：

```text
木/铁料 + 工匠岗位 → 农具 → 农业生产能力
麻/蚕丝 + 织作岗位 → 布/绸 → 衣着需求
粮 + 酒曲 + 燃料 → 酒 → 消耗品/税源/官府经营
木/石/砖 + 工匠劳动 → 民居/商铺/仓场/道路
纸料 + 工艺 + 工匠 → 纸 → 文书、教育与行政需求
```

上述仅是关系示例；每条具体配方须由现有资源/建筑/史料/玩法需求支持。原料消耗和产品产量都按已注册配方落账，停工时显示缺料或岗位不足。

### 5.3 民间库存与商人流通

本地市场可交易库存取自实际 POP/资源持有量。商人可以提供仓储、集散和跨路运输；在途货品不是目的地库存，抵达后才可售。跨路贸易扣运费、考虑距离/地形/战乱和路线能力，AI 可选择是否调货。

第一阶段先做路府内撮合；路线容量与价格发现验证后，再扩展跨路网络。避免首发就做全图复杂匹配导致结算成本和不可解释性上升。

## 6. 民间建筑、政府建筑与营造材料

### 6.1 建筑职责

| 建筑 | 主要出资/所有者 | 影响链 |
|---|---|---|
| 民间生产建筑 | POP/经营主体 | 原料采购 → 工匠就业与工钱 → 产品库存 → 市场销售/利润 |
| 民居、商铺、货栈 | 居民/商人/地产持有者 | 建材与劳工投入 → 住房/经营/仓储能力 → 维护、拥挤、商业外溢 |
| 公共设施 | 国库或地方财政 | 公共工程采购 → 交通/水利/仓储/教育服务 → 改善民间产销条件 |
| 官营作坊与行政设施 | 国库/官府 | 官府采购原料与雇工 → 官有产品/军需/官售供给；可挤占民间资源 |

公共建筑要改善、联通或规范民间经济，不直接取代民间商品供给。官营扩产能补关键供给，也可能争料争工、排挤民营。民间建筑随人口增长、拥挤、损坏、经营扩张或财富变化而产生需求，不做成“每回合每人都建一次”。

### 6.2 建材与造价

- 木、石、砖及其他适用建材要有实物来源、单位、库存、价格和可替代性。
- 水泥/钢筋等新材通过本局科技解锁配方、工艺或贸易渠道；科技不等于免费材料。
- 工程蓝图声明材料清单、劳动量、工期基线、地域要求、效果算子、维护和出资方式。
- 基准造价是预算估值，可由材料基准价、人工和运输估算；不是额外扣钱项。
- 市场采购：出资方付款给卖方，材料从卖方库存转项目/官仓。
- 使用既有仓储：仓减、项目预留增，不重复支付市场货款。
- 施工：预留材料真实扣除，工钱/运费按实付并转到对应 POP。
- 赶工预算是基准支出之外的额外劳务、运输优先权或组织成本；边际提速递减，仍受材料、劳工、季节和工程能力限制；未用余额退回出资方。
- 合同内可锁采购数量/单价；额外采购按市场成交并明示追加成本或延期，避免把预算锁价误当成市场不受影响。

## 7. 官员个体 Agent、专业分析与朝议

### 7.1 角色层次：人是主体，领域契约是能力

月度 Agent 架构分为三层：

1. **官员个体 Agent（行动主体）**：每名官员以自己的身份决定是否提出议案、支持/反对谁、是否承办、如何落实圣旨以及如何处理个人风险。
2. **领域分析能力（专业输入）**：经济、财政、军务、灾荒、仓漕、清丈等契约提供局势分析、专业判断或选项建议；它们没有独立官职、派系利益和最终政治决定权。
3. **程序执行器（现实约束）**：把获授权的个体行动翻译为交易、工程、发令、预算和状态变化，并核验账物。

因此，“finance Agent”未来若重新接线，应回答“税源、支出、市场与风险的专业分析是什么”；具体财政奏议由当值户部官员、宰执或玩家分别提出/会签。经济分析可以观察全国供需，但各官员仍可因信息、偏好和利益不同而得出不同结论。

### 7.2 每位官员的回合意图

先兼容现有领域档位，再给相关的官员 Agent 提供逐人行动契约：

- `actor_id`：提议/执行的官员；
- `action`：上疏、奏议、反对、请托、会签、承办、拖延、规避、执行或观望；
- `intent`：拟实现目标（保价、扩产、囤粮、调运、赈济、抑制奢侈消费等）；
- `targets`：可选路府、阶层、行业、商品、工程或另一位官员；
- `reason`：该官员所据奏报、本人记忆、派系利益、承诺或判断；
- `expected/risk`：本人期望的结果、代价和可能反噬；
- `sponsors/opponents`：希望联署/需要回应的官员；只记录已知关系和本回合真实提案；
- `alternatives`：关键议题可提供其他方案；不强迫每次生成；
- `urgency/duration`：议题紧迫性及意图持续期；
- `confidence/knowledge_gap`：该官员自己的判断把握和未知项。

输出必须逐官员保留署名和来源；不允许把多名官员意见合并成“朝廷认为”。领域分析字段可作为奏报材料，不能静默改写任何官员的立场。

官员不必每回合发言或行动。沉默、未获奏报、观望、表面支持而私下不办、公开反对、违诏等都是不同状态；不能用缺失输出冒充“忠诚支持”或“没有异议”。

### 7.3 圣旨、密令、中旨与口谕：权威、程序、保密和传达方式

这四个概念不应设计成四种互斥的“效果卡”。它们回答的是不同问题：

| 概念 | 主要回答的问题 | 游戏中的机制定位 |
|---|---|---|
| **圣旨/正式诏令** | 谁授权？是否形成正式政令？ | 皇帝授权的正式命令总称；可经过奏议、会签、批红和公开颁行，再由有司承办。玩家掌握最终裁决权，朝议不能投票抹销玩家已颁命令。 |
| **中旨/御笔直发** | 是否绕过常规会签？ | 皇帝直接作出决定，减少审议和协调时间；不应天然等于秘密，也不保证基层执行。它提高明确性/紧迫性，同时增加官僚抵触、程序冲突、问责压力或长期皇权信用成本。 |
| **密令/密旨** | 谁能知道命令内容？ | 信息保密属性，可与正式诏令或中旨组合。保密限制知情人和信息传播，缩小协同面；泄露风险来自实际经手人数、跨机构协办、地方执行痕迹和保密能力，不应只在随机失败时掷一次固定概率。 |
| **口谕/口宣** | 命令如何传达、是否即时？ | 御前口头传达，适合紧急、局部、可逆的小事；传达快但原文/授权边界/记载精度较弱。应表现为承办官员复述确认、误解/遗漏风险和事后补录，不应用统一打折的效果假装“较弱执行”。 |

**组合关系**：圣旨是权威/命令对象；“正式会签或中旨直发”是程序路径；“公开或密令”是可见范围；“书面诏令或口谕”是传达形式。比如可有“正式公开诏令”“密旨直达枢密院”“御笔中旨公开颁行”“口谕后补正式诏书”。中旨不自动保密，密令不自动绕过会签，口谕也不自动意味着低政治权威。UI 与存档应分别表达这些属性，避免把它们混成互斥类型。

#### 当前机制审阅：已有差异，但流程与 Agent 因果尚未统一

按当前实现，常规诏令进入 `pending_decrees`，在月度 `_settle_decrees` 中按派系立场、是否直发、机构归属、效果系数等计算执行概率；中旨通过 `is_zhongzhi`/`is_direct` 等标记进入密旨队列，并按内廷/政府/地方套不同执行率；密旨也单独排队，失败可能以固定概率泄露。口谕则在命令入口直接按固定 `0.6` 效果系数和 `30%` 档位走样规则改效果，并立即调用效果执行器。长期事务上的“督行诏/御笔中旨/密令”另有皇威成本、支持增量和密令容量。

这些代码提供了基本玩法差异，但现在存在几处会妨碍“官员都是独立 Agent”的问题：

- **概念与字段纠缠**：`is_secret`、`is_direct`、`is_zhongzhi` 等布尔字段组合出多种叫法；“御笔直发”与“御笔中旨”在 UI、密旨队列、带宽/额度上的含义容易重叠。玩家难预测究竟改变了保密、审批还是执行能力。
- **缺少官员逐人响应**：执行概率主要由派系、机构和抽象倍率决定；主办官员没有先行领旨/奏覆、请求预算、建议改办或明确承办的统一步骤，其他官员也没有围绕同一道旨意形成可见的支持/阻挠网络。
- **口谕的“即时落地”削弱因果**：它绕开月度 Agent 承办与执行推演，效果先落账后叙述；固定 0.6/30% 的档位折损不表达“谁听错、谁复述、哪里传达失真”。金额、税率等精确命令也不适合套用同一走样规则。
- **密令风险过于随机**：目前泄露检定与真实知情范围、传递路径、经手官员、地方足迹没有充分关联；秘密命令的目标和信息权限也应落实到具体人物/机构，而不只是显示“密令”。
- **倍率可能被误读为必然执行**：内廷/政府/地方固定执行率以及将来领域 Agent 的优先级加成，适合做抽象基线，但不应代替具体 Agent 的承办状态、资源条件和失败原因。
- **短命令和长期事务接缝不清**：即时效果、持续政策、专项事务、具体行动计划需要共享同一命令 ID 和来源链；“诏令已执行”不能等同于事务完成、建筑落成或效果持续生效。

#### 改良目标：四个维度、一个命令对象、逐人推演

把命令存为一个有稳定 `decree_id` 的对象，属性至少分开：

```text
authority: imperial | delegated
procedure: memorial_review | direct_zhongzhi | routine
visibility: public | restricted | secret
delivery: written | oral
urgency: routine | urgent | immediate
issuer / recipients / responsible_actor_ids / informed_actor_ids
intent / actions / location / deadline / budget_and_resource_authority
status / replies / execution_receipts / leaks / source_memory_ids
```

常规推演按如下关系运行：

1. 皇帝写命令并选择/确认授权范围；AI 可拆解目标、行动和所需资源，但不能代玩家扩大强制权、拨款或保密范围。
2. 系统依“可见范围 × 官员权限 × 事务相关性”把命令分别送达具名 Agent。每位官员独立判断自己是否知情、是否赞同、是否领旨、需要什么条件；无权知情者不得在提示和记忆中看到密令正文。
3. 正式会签路径先收集专业意见、异议与封驳，再由玩家裁决；中旨跳过会签等待并立即确立皇帝意图，但不抹去官员异议与执行阻力。公开/秘密各自独立选择。
4. 口谕先记录原话和受谕人，由受谕官员复述“所领何事、权限/期限/资源为何”；玩家确认或按既定容错规则确认后才能成为有效指令。紧急低风险口谕可先做可逆准备动作，同时生成待补录文书；涉及征税、迁民、长期建设、调兵、改变制度、精确金额等不可逆重大事项，必须确认/书面化后执行。
5. 主办官员提交承办方案，领域 AI 提供分析，协办者和地方官员按自身 Agent 状态响应；程序校验权限、预算、材料、前置与蓝图。没有执行器/蓝图时转“待支持/待补旨”，不得套成功率直接改变世界。
6. 逐月推进实际行动，分别记录承办、执行、完工和效果生效；秘密命令按知情名单/传递路线/经手节点积累泄露暴露，公开中旨则承担公开政治责任。口谕补录后沿用同一 `decree_id`，不能重复执行。
7. 将领旨、批答、执行、结果、泄露/失真、赏罚分别写入相关人物个人记忆；同一命令的主办人和反对者记到的内容可以不同。

游戏数值上，区别应主要体现在**速度、知情面、协调成本、官员支持/抵触、信息可靠性、皇威/信用代价、可追责性**，而不是给四种命令各套一个静态成功倍率。紧急命令快但准备不足；中旨快且权威明确但政治摩擦高；密令隐蔽但协同弱、暴露代价大；口谕反应快但需复述确认和补文书；常规诏令较慢但意见汇集、责任链清楚。效果仍由 Agent 行为和程序条件共同造成，保留临场变化与意外后果。

### 7.4 圣旨：从玩家意图到官员行为与世界变化

圣旨是玩家意图进入推演的**最高优先级政治指令与授权**，不是一段只供叙事引用的文本，也不是自动生效的全局数值 buff。它决定“要办什么、授权谁、允许调动什么”，官员 Agent 决定“如何理解职责、怎样响应和承办”，程序再决定“在现有资源与规则下实际办成多少”。因此，圣旨既不能被官员投票否决，也不能跳过承办、资源和现实因果直接保证成功。

每道圣旨应形成可追踪的指令对象，至少包含：

- **原旨与目标**：玩家原文、归纳后的目标、目标地区/对象、期限与优先级；原文留档，结构化理解可供玩家校正，不能让 AI 偷换旨意。
- **授权边界**：主办官员/机构、协办或会签者、可采取的行动、可调用权限；未点名时按官制与事务归属推定候选承办人，并允许官员争办或推诿。
- **资源与约束**：明确拨款、可用预算上限、官仓/民间采购渠道、劳力/差役、材料、军队或其他授权；圣旨可以授权征用或加派，但必须显示成本、合法性依据与反作用。
- **效力与状态**：已下达、待领旨/待奏覆、已承办、执行中、部分完成、受阻、逾期、完成、撤销等状态；状态由程序事实更新，不由叙事宣称。
- **结果归因**：提旨人（玩家）、领旨/承办官员、协办与反对者、执行机构、资金与物资流、受益/受损者、实际效果和失败原因。

圣旨进入回合后的因果步骤：

1. **解析并校验旨意**：提取目标、对象、期限和授权意图；不明确之处保留歧义并提示待澄清/按保守解释执行，不虚构玩家未授予的预算、强制权或蓝图。
2. **分发给相关官员**：主办者、主管部门及受影响官员分别收到符合职位权限的圣旨内容。每个人结合人格、利益、先前记忆、对皇权/政策的判断及自己掌握的信息，产生领旨、奏覆、支持、异议、请求资源、建议改办、观望、拖延或抗命等响应。
3. **形成承办方案**：主办官员把旨意转成行动步骤、预算/物资申请、责任人、蓝图/效果需求与期限；协办者可以补充、争议或提出替代执行法。旨意要求明确时，异议不自动暂停命令，但会影响执行摩擦、信息上报和政治后果。
4. **授权与资源落位**：已有执行器/蓝图/效果时直接进入程序校验；没有蓝图时，由官员提出新蓝图或临时方案，补齐材料、劳动、工期、效果、维护、产权与风险，待玩家朱批或既定授权范围批准后注册。新内容未补全时，圣旨保持待支持/待批，不凭空产生效果。
5. **执行及月度推进**：每回合根据拨款、实物、权限、官员能力/合作、地方条件、时限和外部冲击推进；允许超支申请、部分完成、绕行、迟延、寻租、抵制和意外副作用，但每种结果必须有具体状态依据及账务/关系/民心后果。
6. **奏报与后续推演**：领旨官员收到自己的执行反馈，皇帝收到带来源和可信度的奏报；下一回合相关官员据“奉旨—承办—结果—奖惩”更新个人记忆。未完成事项持续占用/释放资源并保留期限，直到完成、撤旨、失败结案或重新裁决。

圣旨可改变官员 Agent 的**可行动集合和激励条件**：明确主办权可降低争议；专款可让原本缺预算的方案可行；授权采购/调仓可开放供给路径；限期会改变优先级和风险选择；问责、奖赏、免责或调兵会影响官员对执行成本与个人风险的判断。它不能改写官员人格、抹除异议、泄露不该知道的信息，也不能让钱、粮、建材或工期越过程序约束。调兵强制施行只能在圣旨明确授权且规则允许时提供执行力，并记录军费、地方摩擦及民政资源挤出。

因此一条经济/建设事务链应能完整呈现为：**玩家下旨 → 具名官员响应并形成承办方案 → 获批预算/蓝图/资源 → 官营或民营主体实际采购与施工 → 建筑/产能/供给发生变化 → POP、市场、国库及利益关系出现后果 → 官员奏报并把结果记入个人记忆 → 后续回合调整执行**。没有可用执行器时，事务应显示“待支持/待蓝图/待裁决”，不能只累进度或由领域 Agent 代办。

### 7.5 朝议、结盟和决断

议事不是把所有官员送进同一个 AI 会话，也不是一个“朝廷总 AI”代替个人。按官制与情境组织：

1. 由事件/玩家诏旨确定议题；按任职、主管事务、既有承诺、个人关系与利益，挑选相关官员，而非全体发言。
2. 每名相关官员先独立形成意见；他们看到的消息精度与既往记忆按本人权限计算。
3. 在需要朝议时，官员收到可合法获知的他人奏议摘要，并可反驳、修订、联署或结盟；秘密记忆和隐情不会自动广播。
4. 依现有权力结构和玩家操作决定结果：御批、会签、机构承办、派系施压、时限与执行能力都影响结局。程序记录谁提出、谁赞成/反对、谁承办、谁搁置。
5. 玩家亲自下旨时，官员不能以 AI 投票取消旨意；但执行中仍可能迟延、走样、寻租或造成反作用，且要有符合人物/制度的具体原因与机制后果。
6. 没有玩家亲裁的日常事务，按规则形成暂行执行、待议、搁置、搁置至期限或因资源不足未办；不由“全知 AI 中枢”挑唯一最优方案。
7. 所有被采纳行动经程序校验财力、货源、授权、前置和效果，再进入结算。

触发朝议的情形包括：军需与赈济争粮、政府工程抢建材、政策伤及显著利益群体、多人争同一预算/任命、跨部圣旨、弹劾、重大灾荒/战事、官员违命或关键承诺将到期。普通月份可以没有朝议。

### 7.6 关系、个人记忆与适应

每名官员只读取自己的“所见—奏议—批答—执行—结果”记忆和经关系/权限可获得的信息。记录本人建议是否被采纳、承诺是否兑现、所办工程/政策是否成功、遭谁弹劾或提拔；支持与反对关系可演化，但不得让模型自行篡改关系权重或事实日志。

周期摘要逐人生成或维护，原始状态变更日志仍是事实真源。可观察官员是否坚持失败主张、转向替代政策、记恨失信、因利益变化改口或借势结党；不要求人人理性、团结或学会最优策略。人物顽固、短视、迎合、冒进、耿直或派系化应形成玩法差异。

官员的记忆与对话原文不能跨人物混用；合议时只传递本回合已经公开或合法获知的信息。忠诚度、贪腐等隐藏量继续使用姿态/状态规则，不直接以原始数值注入提示词。

## 8. 新科技、商品、蓝图、装备的内容生命周期

```text
自然语言提案
  → 识别既有内容/查重
  → 史实与玩法审议（可标未证实/架空分支）
  → 声明式注册并存入当前档
  → 研究、试制、投资、营造或装备
  → 生产/库存/效果接入
  → 回合反馈和事件后果
```

### 8.1 新内容登记要求

| 类型 | 进入推演前必填的机械信息 |
|---|---|
| 科技 | 能力标签/效果构件、研究来源与成本、前置、适用对象、确定性/不确定性 |
| 商品 | 单位、价格、供给来源、生产配方、需求用途、库存/损耗规则、贸易制度 |
| 蓝图 | 材料、岗位/劳动、工期、建设地利、效果构件、维护、产权/出资人 |
| 装备 | 实物键、生产/采购来源、适用兵种、配给量、损耗/维护及能力效果 |

AI 可先给出灵感和方案；未满足机械信息时保持“提议中/待补蓝图/待技术支持”，不立即影响结算。需要突破史实时，允许在存档中标记“架空发展/玩家诱发创新”，而不是误写成真实宋史。新内容由玩家审批、AI奏议或事件触发均可，按玩法设定。

已有动态蓝图和效果算子机制可作为落地基础；动态商品需要补足存档级注册、读取迁移、库存初始化、冲突/查重和生产链约束。模块全局注册不能直接等同于当前存档的稳定内容注册。

## 9. 建议的开发阶段与依赖

### 阶段 0：读数与基线

**目标**：先看见民间经济实际发生什么，不先调大消费比例。

- 输出逐月、逐路/府、逐 POP、逐商品的需求、支付能力、供给、成交、未满足量、价格、库存、生产、外运和损耗。
- 区分货币支出、商品转移、生产耗料、消费耗用、官府拨用与初始存量。
- 用开局及长局检查民间持钱、实际消费、物价、税收和库存变化的量级。

**验收**：读数能重建每种商品的月度库存恒等式，且能区分“没需求、没钱、没货、没运到”。

### 阶段 1：市场真实成交与口粮分界

**目标**：修正商品消费支出与实物供给脱节；明确 POP 粮、商品粮和口粮关系。

- 让 POP 成交不超过可支付量和真实库存。
- 成交双向扣/加钱与实物，统一处理整数尾差。
- 保留当前粮市/口粮顺序，加入防双买、防重复扣款断言。
- 建立民间库存和在途库存的唯一归属表示。

**验收**：无货不能买；买方持有量由成交产生；买方钱减少 = 卖方收入；口粮只扣一次。

### 阶段 2：需求层级与商品价格

**目标**：让阶层生活和地区差异进入市场。

- 引入基本需求篮子与耐用品目标库存。
- 接入财富保底、收入、价格敏感、替代品和地区权重。
- 价格依据报价/成交需求/可售供给缓动，有上下界并使用统一权威算法。
- 先加少量能由当前资源/作坊生产的日用品；无来源不启用。

**验收**：贫困、短缺、涨价分别导致不同的未满足原因；供需变化能影响成交与价格；不会发生穷 POP 因死比例持续破产。

### 阶段 3：官仓、民仓与官营/民营

**目标**：把官府粮食/商品供应和市场分清。

- 给仓库存标所有者和用途，接入采购入仓、平粜、赈济、军需和调运。
- 建立官营生产、民营生产、许可/专营、官府采购的差异化资金与产品流向。
- 政府采购加入市场需求；政策可改变供给、价格、税利、民怨及寻租风险。

**验收**：官仓未释放不算市场供给；官府买货是市场真实买方；官营/民营均可追踪工钱、原料、产品和收入。

### 阶段 4：政府建筑、民居和材料市场

**目标**：让建材真实连接市场与建筑投资。

- 木、石、砖逐步进入有来源的本地市场；缺货时项目排队、追加采购或延期。
- 工程从市场购料或官仓领料，消耗时扣实物；基准估价、采购款、工钱、运费不得双计。
- 建立民间住宅、商铺、货栈等营造触发，联系拥挤、人口、经营和损坏；民宅材料进入建筑资产。
- 让公共设施改变运输、生产稳定性、储存与可达性；允许工程抢料影响民间市场。
- 水泥/钢筋等科技新材需解锁生产或贸易路径，不以抽象加工费代替真实供给，除非玩家明确选择简化玩法模式。
- 赶工曲线结合资金、工匠、材料和运输能力；使用既有凹函数建议，具体参数经推演校准。

**验收**：建造材料有来源、有货款接收方、有实物消耗；建筑资产增加；未用赶工预算退款；缺料不会照常完工。

### 阶段 5：AI 意图、议事和自适应推演

**目标**：让具名官员 Agent 成为月度政治/经济决策主体，在较低调用成本下推动实际事务；领域契约提供专业分析，程序验证并结算。

- 建立官员 Agent 的稳定人物 ID、在任/离任生命周期、官职权限、个人记忆与信息可见边界；先覆盖实际在任并承担政策职责者，再扩展地方具名官员。
- 将经济、财政、军事等领域契约定位为专业分析工具/幕僚意见；输出须回到具体官员的上下文，由该官员形成提案，不能由领域 Agent 代替主事官员拍板。
- 每名官员按本人职责、利害、记忆与收到的奏报独立形成意图；支持沉默、异议、联署、拖延、执行等不同选择。批量模型调用必须维持逐人独立上下文和逐人结构化结果。
- 把圣旨接入官员响应、奏覆、主办/协办、资源授权、蓝图审批、机构承办与执行反馈链；授权、会签、预算、材料、权限、状态和期限均需可追踪。圣旨优先级最高，但不绕过现实资源和程序结算。
- 把密令/中旨/口谕从互相重叠的类型标签改为命令对象上的保密、会签路径、传达方式、紧迫度等独立维度；口谕补复述确认和同旨补录，密令泄露根据真实知情范围推演，中旨改变决策路径但不直接保证执行。
- 增加冲突检测和危机/重大议题下的轻量朝议；朝议汇总各方主张，不覆盖或伪造个人立场。
- 把每位官员实际执行/未执行提案及结果摘要分别写入其记忆，使其下回合能据此改变策略和关系。
- 在以上个人行动链成立后，再扩展经济意图契约并兼容旧档位字段。
- 允许 AI 提议动态科技/商品/蓝图/装备，先审定再注册和执行。
- 让事件 AI 提议新的、由本回合变化支持的事件；数值效果需注册，纯叙事与机械效果明确分层。

**验收**：相同局势可出现不同官员主张和合法政策路径；同一官员跨回合保留个人记忆，不同官员不会共享私密信息或记忆；任免改变权限而不重置人物身份；批量推理和逐人推理在身份、记忆与归因上等价；圣旨、中旨、密令、口谕的差异能在时效、知情范围、意见流程、承办条件和后果上被玩家感知，而不会仅显示为静态倍率；口谕确认/补录不会重复执行，密令未授权人员不会看到正文；每道命令及其承办结果能追溯到提议者、支持者、反对者、承办者及实际受益/受损者；失败可见原因并能进入相关官员后续判断；路线实际影响市场/POP/国库/建筑，而不是只改变月报文字。

### 阶段 6：外邦策略和多难度

**目标**：增加对手能动性而不让全世界每月都高成本调用 AI。

- 对交战、接壤、贸易或关键外交对象运行定向决策；低交互政权用低频摘要模型。
- 外邦 AI 有目标、资源约束、风险偏好和信息局限；程序执行其实际贸易、外交或军事行动。
- 难度主要改资源与 AI 行为倾向/风险承受，不简单给 AI 更多信息或直接加数值。

**验收**：敌对势力能针对玩家政策作反应，结盟/贸易/军事方向可变；不活跃对象不导致回合调用量爆炸。

## 10. 实现优先级建议

**P0：闭环正确性**

1. 商品买卖真实库存与钱双向转移。
2. 粮食口粮、商品粮、民仓/官仓的所有权和用途区分。
3. 建材估价不重复扣费，工程材料真实采购/领用/消耗。
4. 读数/日志让消费低、供给不足、价格高等原因可辨。

**P1：核心游戏性**

5. POP 需求分层、价格反应、耐用品和替代品。
6. 民间营造、商人调货、政府采购与公共建筑外溢。
7. 官员 Agent 的身份、生命周期、个人记忆与权限接入月度推演，且每项政策意图可归因到具体主事官员。
8. 领域分析结果回流给对应官员 Agent，由官员决定是否采纳并提出政策；意图与市场数据连接，按局势选择地区/行业重点。

**P2：AI 突破空间**

9. 财政/投资/改革事务由具体官员 Agent 发起、会签或承办，配套领域分析工具与消费闭环。
10. 冲突议事、逐人执行反馈与多回合策略调整。
11. 动态商品/科技/装备注册、AI 新事件与外邦策略升级；外邦具名统治者/主事者也按独立 Actor 建模，适用时再逐步接入。

不要把 P2 内容当作 P0 市场成立的前提；也不要为追求动态提案而延迟基础货物守恒。

## 11. 定向测试与模拟评估建议

经济与人口机制属于核心模拟，动代码前先锁定参数口径与预算口径。每阶段应增加定向测试，而非等全局长测暴露账本错误。

### 11.1 单元/交易断言

- POP 买货：buyer wealth `−paid`，seller wealth `+paid`；seller goods `−q`，buyer goods `+q`。
- 官府采购、官仓平粜、赈济、军需分别验证钱粮实物对手方。
- 市场供给不得重复卖出；同一商品同回合总成交不超过可售库存。
- 口粮消费、市场购买、农售粮完税互相不重复占用同一笔财富/粮食。
- 商品加工按注册配方扣原料、加成品；缺原料/缺岗位时不产出。
- 工程从市场买料、从官仓领料、民间自建三种方式均验证实物去向和资金去向。
- 赶工成本与基准预算分开；项目总材料量封顶；退款回原出资方。

### 11.2 整回合对账

- 货币：`ΔM_ALL == 外部注入 − 销毁 + 明确残差`，内部消费/采购转移不增加残差。
- 商品：`期末库存 = 期初库存 + 生产 + 输入 − 成交转出 − 消费/加工/损耗/输出`。
- 粮食：农户自留、商品粮、口粮、官仓、军粮和运输在途逐项可复原。
- 人口：阶层迁移仍符合 ΣPOP 守恒；迁徙与就业不创建额外人口。
- 建筑：投入材料与完成资产可以对应；维护支出归属一致。

### 11.3 长局与 AI 行为评估

固定种子运行基准局以发现账户漂移、库存爆仓、市场死寂和全员饥荒；再用多个 AI 随机种子/策略温度做探索局，评估路径多样性与可玩性。建议记录：

- 按阶层/路府的基本需求满足率、消费额、收入与财富分布；
- 商品供给集中度、成交量、未满足需求、价格波动和跨路输入比例；
- 官仓用途与库存变动、平粜/赈济覆盖、民间库存响应；
- 工程完成率、缺料延期、赶工收益、民间供给挤出；
- AI 提案采纳/部分执行/拒绝/失败比例及失败原因；
- 官员 Agent 的个体行动率、沉默/异议/联署分布、立场与目标变化、跨回合记忆命中及提案归因完整率；
- 同一议题下官员意见的差异度、派系/关系对支持网络的影响，以及信息边界是否被破坏；
- 批量调用与逐人调用的身份、记忆、权限和执行归因一致性；
- 多局势下的重要决策路径差异，而非只比较叙事文本是否不同。

平衡目标不是每条指标稳定在固定数值，而是避免机制退化：永远无成交、所有路持续短缺、AI 总作同一选择、项目无来源完工、市场永远不会对冲击作反应。

## 12. 待裁定参数与设计开关

架构先支持，具体值通过校准确定：

1. 各 POP 温饱线和可消费余量尺度，以及家口折算方式。
2. 基本生活需求、耐用品目标库存、替代品与地域偏好。
3. 开局商品/建材/官仓存量的历史与玩法依据。
4. 商品基准价、动态价格带、运输成本、储存损耗和市场容量。
5. 官仓各用途的初始量、容量、采购/释放权限及管理效率。
6. 各商品官营、专营、许可、民营与官府采购的初始制度和政策影响。
7. 民居的建设触发、产权表现、住房需求和维护损耗。
8. 工程材料、工钱、运费、赶工溢价和退款的准确账务口径。
9. AI 意图可影响的参数范围、触发条件、消息不确定性和调用预算。
10. 新内容注册审批：玩家朱批、官员议奏、试制成功或事件触发的适用范围。

所有待定值在文档/代码中标为可校准参数；没有史料支持的架空科技和商品明确标记为“玩家/AI 引发的架空发展”。

## 13. 设计原则总括

```text
因果链要硬：有来源、有交易、有库存、有后果。
策略空间要软：AI 可异议、试错、偏好、误判、创新和改变历史路径。
官员是主体：每个人物有独立身份、权限、信息、关系、记忆与行动归因；领域 AI 只提供专业能力。
玩家权力要明：旨意可推动世界，但资源、执行与反作用真实存在。
叙事要服从事实：先有落账结果，再由月报和事件解释。
测试分层：账务可精确断言，社会与 AI 表现用长局指标评估，不要求每局同故事。
```

## 14. 依据统一设计与 EU/Victoria 参照的当前落地路线

本节按[《民间经济与营造市场统一设计.md》](民间经济与营造市场统一设计.md) §4.13–§4.14、§8.4、§13–§14 修订，替代本文 §9–§10 原来的粗粒度阶段安排。参考 EU5 的地方人口需求与生产贸易、EU4 的战略贸易网络、Victoria 系列的 POP—岗位—收入—消费闭环，但不复制其地图/人口规模、高频市场撮合或工业时代工厂组织。宋祚的主循环仍是**玩家旨意/局势 → 官员 Agent 响应 → 月度程序结算 → 地方社会反馈**。

### 14.1 开工门：先核状态，禁止把“有代码”当“已落地”

每个实现批次开始前，先对照两份任务表与真实调用链，分别标明“定义存在、已接线、账本闭合、长局校准、玩家可观察”五种状态。任务表是完成状态的权威入口；本文不复制易过期的测试数量或版本状态。

按当前规格已能复用的地基包括：`core.market.trade_goods` 原子商品成交、需求/价格模块、官仓与口粮既有路径、动态蓝图注册和项目链、民间建筑触发、decree-action-chain、官员 Agent/命令对象/朝议，以及相关回读 UI。实现前要逐项复核这些能力的消费者和适用粒度，**不要因设计稿写了同一机制就重写一遍**。

需要优先面对的结构缺口：

- 宋境 `prefectures` 仍是路级经济容器；目标是州府级市场。没有可靠初始数据的 POP、建筑和库存不能按面积/人口比例伪拆成“真实州府值”。
- 宋侧建筑等级/岗位、政府项目、全局 `state.workshops` 配方产出并非统一实体；现有全局作坊产出和逐路工匠库存之间存在分派路径。先给出迁移依据，不允许用人口比例分派掩盖地点缺失。
- ~~B4 建材市场存在已实现但未接线的部分；规格记载的根因是建材库存/供给与 POP 持有商品容器未统一。不得绕过这个阻塞，另造"工程专用免费货源"。~~ → ✅ **该阻塞已于 2026-10-02 解除**：裁决 **C / C-c / E-1** 并接线，建材存量统一到**商人 POP `goods`**（供给与 POP 容器已统一），仓明细层已退役。**此条禁令的初衷仍然有效且继续适用**：⚠️ **不得另造"工程专用免费货源"**——建材只能来自仓供给或商人采购，缺料即 `material_short`，不得绕过。
- 财政/投资领域契约的生产调用限制和回报来源守恒仍以任务表为准；不能为了跑通展示而唤醒没有消费者或会凭空生成回报的契约。

**开工产物**：一页“模块—权威数据—调用方—粒度—未闭合流向—存档影响”台账；明确本批唯一纵向切片、要迁移的字段和不在本批做的范围。若历史落点、产权或货币口径不确定，先保留未定位/待裁状态，不自行假定。

### 14.2 P0：确定市场契约和空间可达性

先定义州府市场的数据契约，不先铺商品目录。最少确定稳定 `market_id`/`location_id`、商品、买卖主体、用途、库存持有人、成交价/估价、预算、月份、交通边、税费、在途状态、缺失原因和来源 ID。

- 市场库存是底层 POP/经营主体/仓储库存的派生可售视图；视图不得再持有同一批商品。
- 市场范围由地域 ID、政权/关税制度、实际控制、交通连通和容量共同决定。邻接不等于可达，全国总库存不等于本地供给。
- 交通边先只表达承载力、成本、时滞、季节/风险和通行条件。州府市场圈可以从这些边派生；市场圈改变只改变可交易集合，不搬迁或复制实体库存。
- 价格至少区分基准价、有效报价、实际成交价、官定/合同价。未定义价格不可静默回落到 0 或 1；同月报价/成交窗口和价格更新时点须统一。
- 月度撮合读取冻结的意向快照。先形成订单，再按已批准的优先级清算一次；清算成交不在本月变成新需求、再采购并无限循环。

**验收门**：两个相邻州府有路可达时可以调货；断路/运力耗尽时目的地不能消费未到货库存；同一货物只有一个持有人；移除市场聚合视图不改变底层账；只冲击一地不会无因同步改全图价格。

### 14.3 P1：先完成一条地方经济纵向切片

在数据盘点后选一个有可信位置、需求、投入和现有机制支撑的州府/路级试点；首轮若无法获得可靠州府拆分依据，应明确以路级兼容切片验因果，另立州府迁移门，不能把路级数据贴州府标签。

纵向切片至少覆盖（允许先用轻量经营记录做过渡，但字段需可迁移到 §14.4 的经营主体 schema）：

```text
POP 生计/持钱
→ 一种基础需求和有限替代
→ 当地真实库存成交与价格记录
→ 一个本地生产者/经营记录及投入约束
→ 工资或经营收益回到既有 POP/政府账户
→ 下一月需求、供给或 Agent 意图响应
```

优先选现有配置和稳定数据能支撑的农副、纺织或窑业，不预先指定历史上未核实的产能。每件商品在“自用、待售、储藏、在制、项目预留、在途”状态间转移时只做状态/所有者变更，不重复建货。

**验收门**：能逐月复原货币和商品库存恒等式；缺钱、缺货、缺岗位、缺料、缺运力分别可见；贫困人口有需求但买不起时不伪造成交；有库存和购买力时可成交；生产者/卖方获得的收入有来源，后续消费可由收入变化驱动。

### 14.4 P2：建筑资产与经营主体并轨

沿用现有项目、蓝图、`prefectures[*].buildings` 和岗位计算，不另外创建平行建筑账本。分清**建筑资产、经营者、生产方法、雇佣岗位、库存与订单**：建筑提供空间/设备/耐久/容量；经营者决定资金、原料、工艺、销售和盈亏。首期可将经营记录嵌在建筑实例中，但 schema 要能将经营主体独立出来。

每个试点建筑/经营记录要能确定：蓝图版本、稳定地点、等级和完工/可运营月份、所有者、经营者/管理 Agent、维护责任、经营方式（家庭兼业/民营雇工/官营/官有承包）、可选生产方法、岗位容量/实到、配方、投入/产出库存和收入去向。缺字段时标未定义，不能用默认全员就业或默认满产补齐。

月结因果固定为：

```text
可用建筑与技术
→ 经营 Agent/主体提出开工、停工、转产或采购意向
→ 程序检查资金、原料、岗位/技能、设备、维护、法规和订单
→ 扣投入并产出到本地经营库存
→ 销售/服务履约
→ 收入按产权/合同转给雇工 POP、经营者 POP、政府账户与税收
→ 经营者下月决定工资、留存、维修、扩建或退出
```

生产方法切换须有培训/改造成本或延迟。官府拥有、官府经营、官有承包、民有民营、公共设施分别建模；公共道路/水利等产生网络或服务能力，不自动产出普通商品。新建筑完工当月还是次月生效应统一规定。家庭/未就业人口仍可通过农业生计、家庭生产或季节性活动参与经济，避免“没专门建筑就无收入/无供给”。

经营资本如需留存，所有权必须继续归属 POP 或政府账户；不要增加脱离 `M_ALL` 的影子钱池。维护、工资、分红、亏损、停业和欠款均按实记账。

**验收门**：建筑不会因等级存在自动满产；缺任一必要投入/工资/许可时按规则降产或停产；产出首先入本地经营库存；成品卖出后收入正确归属；将建筑设为停业不会继续产出；官营和民营使用同一物理成交接口但钱货去向不同。

### 14.5 P3：官府旨意、Agent 与经济动作接线

复用已有 decree-action-chain 和 B5 Agent 能力，不重写命令 schema。新增市场/建筑行动时，扩展既有注册行动/效果构件：例如修路、港口扩容、官仓目标库存、某货官买优先、许可调整、支持某行业、官府采购或保护商路。

- 玩家旨意明确目标、授权范围、主办官员、可用预算/仓料、期限、公开/保密和传达方式；AI 不可替玩家加拨款、征用权或强制调兵。
- 相关官员以各自身份接收权限内信息，出现领旨、异议、请款、争办、拖延、改办或执行等可区分响应；财政/经济分析是奏报，不是代替户部/主事官员作决定。
- 没有生产 handler 的新蓝图、制度或行业命令维持“待支持/待补蓝图/待裁决”，不能只增加事务进度。
- 程序月结落实资金、货物、采购、运输、建造和效果；Agent 产生行为策略和叙事理由，不直接写结算数值。
- 将执行回执分别写入主办、协办、反对者的记忆；次月推演能基于已发生结果调整策略，而不是让 AI 读到尚未批准的闲聊就改状态。

**验收门**：同一旨意在两名不同官员承办时可以产生有依据的路径差异；未授权人员看不到密旨；拒绝/受阻原因能追到权限、资源或关系；玩家能从命令回看资金/商品/建筑/POP 后果；重试不重复执行。

### 14.6 P4：府际、边境与远方市场

按成本和历史不确定性逐步扩图，不直接搭“全世界一个市场”：

1. **府际市场**：先把可复原的州府邻接/漕运路线接入，有在途批次、运价、到达月、运力、损耗和截断原因；先不做所有路线任意互通。
2. **边境与政权市场**：接辽/西夏/大理等当前直接接触的市场与关卡/互市条件；库存继续属于其地域账本，易主改制度归属，不搬空库存。
3. **中亚陆路需求**：用有限预算、有限需求篮子和多段陆路表示河西—绿洲—中亚转运；政治控制和风险可让路线中断。
4. **印度洋—西亚转口与欧洲终端需求**：首期只用转口商圈+滞后终端需求信号；宋境在本地可接触的节点卖给具体买方，欧洲需求不能直接成为宋境买家，也不能即时改写宋境价格。

每段路线都需有限预算/库存/运力、时滞、交易成本、税费和风险；转售货物需先到货并进入中间商库存。商人 Agent 可以按预期利润扩张/收缩采购或改道，程序在月初意向快照和当月约束下确定成交。价格差只在扣除运费、税费、资金占用与风险后可能形成套利；没有实际贸易记录不得计市舶税或外销收入。

**验收门**：关路后贸易量、价格/采购意向和财政税基按逻辑逐月变化；无预算或运力时不成交；在途货未到不能使用；沿途转售不重复计收入；终端欧洲需求通过转口滞后传递而非瞬时买空宋境商品。

### 14.7 P5：玩家界面和月度推演报告

采用 Victoria 系列“可追原因”的信息层级，但保留本游地图/政务界面和月回合节奏。新增读数从后端权威派生，不在 React 里复制市场/经济公式：

- **市场地图**：市场圈、交通边、容量、在途货、边境/关税与受阻原因；可切换供给、需求、价格、连接度。
- **商品详情**：期初/产出/输入/成交/消费/损耗/期末库存、需求未满足原因、本地可达供应、价格历史和主要交易双方。
- **建筑/经营详情**：地点、产权/经营权、生产方法、雇工与岗位、投入、产量、产品去向、收入/工资/税/维护、订单和停工原因。
- **POP 经济详情**：收入构成、必要支出、消费品类、购买力/缺货原因、储蓄或经营变化及实际受益/受损来源。
- **旨意因果回看**：旨意→相关 Agent 响应→承办计划→授权资源→市场/施工动作→本月结果→下一月变化；只突出重要变化，详细账本按需展开。
- 通知分层：重大缺粮/断路/工程受阻默认提示，可设置；一般价格变化汇入市场报告，减少每月弹窗噪声。

**验收门**：每个显著读数能下钻到来源；读数缺失不显示为 0；一个用户能回答“哪里短缺、为何未运到、谁本来应供、旨意为何未办成、结果影响了谁”。

### 14.8 P6：校准、放行与不可跳过的质量门

每阶段先加定向回归，再按项目约定执行针对性校验。先跑确定性账本/交易断言，再跑固定种子短局和 60/240 月长局；最后以多 AI 策略种子检查路径差异。不能用 `M_ALL` 残差为零替代人口存活、购买力和玩法体验验收。

放行至少要求：

- 货币、商品、粮食、人口、建筑材料均可逐月对账，缺失/未定位资产不被当作零或虚拟分配。
- 无“无库存照常成交”、无同月商品循环、无建筑空转产出、无贸易无限买方/运力。
- POP 基本口粮机制、商品消费、农业收入和工程抢料分别有诊断读数；人口变化能按出生、死亡、迁移、逃荒等流量解释。
- AI 同一局势下可有不同合法选择，但没有 Agent 能绕开权限/库存/资金/蓝图写值；程序随机可按种子复现。
- 玩家可观察命令、官员承办、市场交易和建设结果之间的因果，失败也有真实状态依据。
- 存档迁移有旧档样本、往返读写及未知 schema 的拒绝/保留策略；州府数据不足时明确维持上层聚合，不伪造精度。

一个阶段未过门，只修复其内的账本/数据/解释问题，不把未验证产出扩展到更多商品、地区或 AI Agent。~~B4-1 接线等既有阻塞须先按任务表解决或重新裁定~~ → ✅ 已解除（2026-10-02，裁决 C/C-c/E-1 并接线）；原则仍有效：**不能靠新增阶段掩盖未解决问题**。

### 14.9 明确排除的首期范围

- 不创建每个家庭、商铺和远方消费者的 LLM Agent；普通活动按 POP 生计群组/经营记录聚合，具名人物和关键商团才按情势唤醒。
- 不做全图同步统一价、无损瞬移商品、全国共享仓库或无限外贸订单。
- 不一次上线全部 40–60 商品、所有服务业和所有历史势力；商品新增必须服务于已经选定的纵向切片或玩法决策。
- 不让每座建筑都独占全套微观企业账；先用轻量经营记录，只有关键设施/大商号/官营衙门才升级成独立 Agent。
- 不把市场 AI 变成一段无法审计的自由文本推演。AI 的动作最终必须可映射到命令/订单/方案对象和程序执行器。

## 15. 外部机制参照的适用边界

- **EU5**启发“地方人口需求、地区资源生产、市场接入”共同作用；不照搬其人口和地图细度。
- **EU4**启发贸易节点、海陆通道、关税与政策的战略玩家操作；抽象贸易流不能替代宋祚实际商品成交。
- **Victoria 2/3**启发 POP 生计与生产组织、建筑雇佣、工资/所有者收入、贸易盈利和清楚的商品/人口面板；19世纪工厂、阶级制度和周度交易不应直接移植到北宋。
- **宋祚的差异化**是官员 Agent 彼此有身份与信息边界，圣旨可改变行动授权；玩家治理社会而非直接控制每家店。市场机制要为诏令因果和地方回应服务。

## 16. 外邦人口数据的史料边界与落地规则

人口总量是模拟底盘，但不得把地方户口、使者自述或零散降附人口改写成一国普查。当前代码里 `EXTERNAL_REGIMES` 使用“万口”量级的人口值；`REGIME_DEMOG` 又保存州/府级人口与户数，两套数据不能因数值相近就视为同一统计口径。本节是后续人口数据整理的约束，**不等于这些数值已按本节完成代码改造**。

### 16.1 已核实的史料范围

| 政权/材料 | 可支持的结论 | 不可据此推出 |
|---|---|---|
| 西夏相关，《宋史》卷492 | 凉州旧领姑臧等五县报告户 25,693、口 128,193；是限定地域的地方数，且同段注明为龙钵自述 | 西夏全国户口；不能把凉州数外推成西夏总量 |
| 高丽使者，《宋史》卷487 | “本国……府曰开城，管六县，民不下三五千”属于高丽方面人物自述，范围、统计对象和精度不足 | 不能当作宋方核定的高丽全国人口数 |
| 《宋史》卷489 | “所统大小州三十八，不盈三万家”位于占城条，指占城（Champa） | 不能归给交趾/安南，更不能作为大理或吐蕃数据 |
| 《宋史》卷491 | 黄乜族降户、八千帐族及其他户数是具体部族/降附事件记录 | 不能拼加为吐蕃全国人口 |
| 《宋史》卷488《大理国》 | 本传可见文本未给大理全国户口总数 | 不能把游戏设定包装成史料数；“本传未载”也不等于所有史料绝无相关记录 |
| 辽人口汇总 | 现有辽道府表引用“各郡县户总计之不过五十五万有奇”的汇总性说法；原注同时指出详略不一、宫府分隶户数未明 | 不能称为完整、精确且覆盖全体人口的普查；道级拆分仍是模型分配，不是逐道史料值 |

### 16.2 建议采用的数据标签

人口字段旁应记录 `basis`、`unit`、`scope`、`source`、`reported_by`、`confidence`、`conversion_note`。至少区分：

- `historical_local_report`：有明确原文，但只覆盖某地或特定群体；保留原始户/口单位与报告者，不自动外推。
- `historical_aggregate_approximation`：史料汇总或不完整上限式数字；必须保留“约/不逾/缺项”等限定。
- `setting`：缺少可用同期全国总量时采用的玩法设定值，须说明它服务于地图规模、经济承载或外交军事实力等哪个设计目的。
- `derived_estimate`：由户数、假定户均人口、疆域或其他模型参数换算所得；必须公开换算假设，不能显示为原始史料。

现阶段推荐：辽的“五十五万有奇”标为带缺漏限定的历史汇总锚点；凉州 25,693 户 / 128,193 口只作为西夏境内一个地方样本；西夏、吐蕃、大理全国值继续用 `setting`，并保留现有玩法基线，直到完成各政权人口账本、单位和州府拆分的统一审计。不要因为凉州有地方数就自动新增/覆盖西夏全国人口，也不要把零散部族户数求和。

**当前代码基线（本节编写时核对）**：`EXTERNAL_REGIMES` 的政权级值为辽 380 万口、西夏 160 万口、吐蕃 120 万口、大理 90 万口；`REGIME_DEMOG` 的州府底盘另为辽 275 万口 / 55 万户、西夏 150 万口 / 30 万户、吐蕃河湟 20 万口 / 4 万户、大理 90 万口 / 18 万户。故不能把“33 万”当作当前代码值。辽州府户数合计对应 55 万户，但这只是依汇总锚点按模型比例分配；吐蕃的 20 万口明确只覆盖河湟，不代表全国。人口标签接线前，应先确定每种结算/展示场景究竟读取政权级还是州府级账本，禁止相加重复计人口。

### 16.3 界面与推演要求

- 人口面板同时显示数值、单位、地域范围和依据标签；例如“凉州五县：12.82 万口（地方自述；不代表西夏全国）”或“西夏：160 万口（玩法设定；同期全国总户口无可靠数据）”。
- 鼠标悬停/详情可查看原文卷次、报告者、统计范围、换算说明及置信度；缩放/切换政权后不能丢失范围限定。
- AI 推演引用人口时读取结构化标签：设定值可用于市场规模、兵力与财政模拟，但叙述中不得说成史实普查；地方史料数只约束其地域样本。
- 如州府人口由政权总量拆分，拆分值标为模型分配并保证合计守恒；不能让美观的州府明细制造“史料级精度”。
- 修改人口底盘前，对齐同一模拟路径中的 `EXTERNAL_REGIMES`（政权级）与 `REGIME_DEMOG`（州/府级）单位、总和、覆盖范围和易主后归属，再单独评估人口、粮食、市场、军力和贸易连锁影响。

**验收断言**：任何外邦人口数都能回答“多少人/户、哪一地、哪一时、谁报告、依据是什么”；史料缺失显示为“玩法设定/未有可靠总量”，不会显示为 0 或伪装成史料值；地方数不会被自动扩大为全国数；政权级与州府级人口不会重复进入同一市场或 POP 总量。
