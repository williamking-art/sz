# game-docs 全目录审校与改善建议

> 审校日期：2026-10-02。范围为本目录下 Markdown 文档（docs、analysis、specs、reviews、archive 及索引）。本次是文档一致性与时效审校，不代表对每条历史结论重新跑了代码、测试或游戏。
>
> **时间口径**：部分台账自述日期为 2026-10-11 或 2026-11，晚于本次审校日期。未核清来源前，这些日期、测试数字和状态只能视作文档中的待核陈述，不应被当作当前实测结果。

## 一、总评

文档覆盖面很广，机制设计、实施任务、历史审查和证据记录都有。但目前主要风险不是缺文档，而是**同一机制有多个状态口径**：设计稿、需求稿、任务表、历史快照分别写了“未实施 / 已接线 / 已完成 / 待裁决”，读者很难判断实际可玩到哪一步。

建议把状态拆成五个可独立判断的字段：

1. **代码存在**：数据结构或处理函数是否存在。
2. **月结接线**：是否进入实际回合结算路径。
3. **因果闭环**：输入、效果、受益者、资源账是否可追踪。
4. **玩家可见**：能否在 UI/日志/读数中理解发生了什么。
5. **验证状态**：最近一次定向/全量验证的日期、命令和结果；没跑就明确写“未验证”。

“文件写了实现”“单测通过”都不能单独等同于整个玩法闭环完成。

### P1 · 让文档更容易维护

- 每个规格目录只设一个 `tasks.md` 作为状态权威。`requirements.md` 记录需求基线，`design.md` 记录方案，均不再维护第二份进度表。
- 任务状态使用“未开始 / 进行中 / 已实现未接线 / 已接线未闭环 / 已闭环待平衡 / 已验证 / 暂缓 / 不支持”固定枚举，并在术语表解释。
- 状态行附证据链接（实现文件、测试文件、读数/API）；若只定位到实现而未验证，写“代码已存在，未在本次运行验证”。
- README 只放当前入口、权威文件和纪律，不复制易漂移的批次明细。各 README 与本次新增审校总表已加互链。
- 每份统计或“当前已完成”陈述给出查询日期/命令；不再把历史测试数写成当前基线。

### P2 · 设计内容需继续补强

- **市场与 POP**：分别记录需求形成、购买力约束、实际成交、未满足原因和 POP 收入回流；避免把“计划消费”直接当成交。
- **建筑与营造**：区分建筑资产、经营主体、所有权、生产方法、岗位到岗、库存和订单；明确建成/停工/毁损的生效月份与存档兼容。
- **圣旨与事务**：区分命令类型、授权/支持、承办 Agent、执行落点、资源消耗、效果对象和结果反馈；AI 叙事不能替代程序效果证据。
- **AI 月度推演**：文档需明确 AI 输入快照、可用行动、程序校验、随机性边界、失败/未执行原因与玩家可见日志；避免把 AI 输出当成数值结算权威。
- **地图边界**：将几何拓扑连续性、行政归属唯一性、显示裁剪和标签定位分开验收；地图看起来连续不代表州府/省域归属数据正确。
- **历史与设定数据**：史料、推定和游戏设定分层标注来源/置信度/适用年代，政权总户口缺史料时不能用单地数据冒充全国数据。

## 三、按目录审校

### `docs/`

这是当前机制说明和主要设计建议的入口。本次修正了市场、营造、AI 落地建议及货币口径文档中的旧“未实施”提示，并为开发测试说明移除了易过期的固定用例数。建议下一轮逐项把机制说明中的结论链接到具体实现与读数接口；设计草案则统一使用“设计目标/当前差距/建议阶段”，不要与现状混写。

### `specs/`

实施规格最接近代码，也最需要唯一状态源。`decree-action-chain` 的需求稿旧状态已澄清，任务表中长期事务 handler 的过期结论已更正。市场两套规格的任务台账仍需要收敛重复快照，特别是未来日期记录、B4/B5 的“已实现但未接线/建模阻塞”边界，以及州府数据层与完整市场玩法的区别。

### `analysis/`

内容属于研究/诊断材料，不宜直接视作运行时机制或已确认设计。索引已补充时效与证据边界。建议各分析结论增加“样本版本、日期、口径、是否复跑”，涉及经济长局的结果同时给存档种子、月份和关键读数。

### `reviews/`

审查报告是当时的快照，正文保留是正确做法。索引已说明其时效边界。建议报告首页注明被审查的代码版本/日期，并在目录索引中标“已复核/待复核”，不直接改写旧审查结论。

### `archive/`

归档证据不应参与当前状态汇总。本次新增 `archive/README.md`，说明归档规则和当前权威入口。建议每次归档都保留原始日期、来源、提交/快照标识；如需更新结论，应新建复核记录，而不是覆盖旧文档。

## 四、变更与未做事项

- 已更新根目录、docs、specs、analysis、reviews 索引并增加 archive 索引。
- 已修正若干设计/需求文档的过时实施状态提示；已更正一次性命令链规格中的 handler 状态。
- 未改游戏代码；未运行测试。本文件不宣称本次验证任何游戏功能。
- 仍需人工/代码复核：市场任务台账的未来日期与互相矛盾状态、州府市场的实际接线范围，以及每个机制的当前 UI 可见度和存档迁移状态。

## 五、建议执行顺序

1. 先核对未来日期来源与市场任务表版本，将冲突汇总到唯一状态表。
2. 按“代码存在→月结接线→因果闭环→玩家可见→验证状态”逐规格补齐证据链接。
3. 更新权威机制文档及相关目录 README，再把审查/分析结论标成已复核或历史快照。
4. 下次涉及代码时，仅在按项目门禁验证后更新验证数字；没有跑的项目明确标注未验证。
