# 《宋祚》游戏审查整改实施指南

> 用途：交给其他 AI 或开发者，按优先级审查并实施 `sz/game` 的后续整改。
> 本文是执行任务书，不授权大规模重构、改写游戏设计或擅自改变经济数值。

## 目标

围绕玩家可见的问题完善游戏，重点保证：

1. **长期事务由圣旨推动**：事务需要相关官员、机构或派系支持，圣旨影响支持与阻力，最终结果由这些因素和执行过程决定。
2. **地图政区连续、边界层级清楚**：确认黔中与湖南、湖北交界的缺口已消失，并让玩家能辨认预期层级的政区边界。
3. **界面能引导玩家采取行动**：地图主界面与事务面板在信息密度、空状态和操作线索上更清晰。
4. **关键问题有证据、有回归保护**：实施前复现并记录，实施后验证玩家可见结果。

## 执行规则

- 开始前检查工作区改动和相关 `AGENTS.md`，保留已有未提交改动；不要执行 `git checkout -- .`、`git clean` 等清理命令。
- 先读相关机制、状态、API、面板和地图生成代码，追清完整数据流，再改动。保持已有项目架构和代码风格。
- 每项先描述“现象、根因、影响范围、拟修改文件”，再实施；不要仅按搜索命中批量替换。
- 不得把以下事项误报为已验证：仅访问后端接口、仅构建成功、仅地图数据生成成功，都不能代替玩家界面验证。
- 经济、人口、税收、随机数与长期结算属于核心模拟。任何会改变这些结果的修改，都要先说明口径和影响，并增加有针对性的回归保护。
- AI 应用于文案或推演时，不能让模型输出未经校验地直接改写核心状态；核心规则由确定性代码执行，AI 输出须经过现有契约校验。
- 不得擅自删除内容、旧实现或资源；确认没有生产消费者后再处理，并说明依据。
- 结束时给出修改文件、行为变化、验证证据和未解决项。测试/构建结果必须如实记录，不得虚构实机试玩。

## P1：长期事务与圣旨支持机制

### 已知现状

`core/settlement_decree.py::_settle_longterm_decrees` 当前主要按月数与难度增长进度，写入通用随机日志，并在进度到 100% 时结案。现有路径没有充分体现“哪些人支持、哪些人反对、圣旨如何改变支持，以及支持如何影响达成”。事务数据与命令入口位于 `core/commands_decree.py`；前端事务展示位于 `frontend/src/renderer/panels/TodoPanel.tsx`。

### 执行要求

1. 先盘点长期事务的创建、存档、快照/API、圣旨下达、人物/派系态度、月度结算和 UI 展示的端到端链路；列出当前有哪些可复用的支持度、忠诚、派系关系和圣旨效果字段。
2. 设计最小可行的事务状态模型，至少表达：事务目标/成功条件、相关支持者或阻力方、支持状态、当前阻碍、进度/阶段、最近一次有因果关系的变化、结案结果。
3. 明确圣旨对事务的作用：针对对象、获得/损失支持、执行资源或政治代价；不可只将“颁旨”直接等同于自动成功。
4. 月度结算应根据支持、阻力、执行能力及已有规则推进；成功或失败应有可解释的条件和日志。禁止继续使用无因果关系的固定进度条作为唯一成功机制。
5. UI 至少让玩家看到：事务要达成什么、需要谁支持、当前阻力/缺口、哪道圣旨产生了什么变化、下月可能如何推进。空状态需给出合适的下一步入口或说明。
6. 确保存档兼容旧事务对象；旧存档缺字段时应有安全默认值或迁移，不得导致读档崩溃。

### 验收条件

- 一项事务的进展可以追溯到相关支持变化或执行结果，不再只随时间自动完成。
- 对同一事务颁布针对不同对象/内容的圣旨，至少能在支持、成本或推进结果上产生有解释的差异。
- 无支持、支持增加、支持流失、结案、旧存档读取等路径都有针对性回归检查。
- 前端可以清楚呈现事务状态变化；失败、延迟或受阻时不伪报成功。

## P1：黔中—湖南—湖北地图与政区边界

### 已知现状

此前发现府州按路筛选时先选最近治所、再检查所属路，可能把不符合条件的府直接丢弃；生成器已调整为先筛选候选治所再匹配。此前核对显示怀化市归荆湖北路、秀山归夔州路，大面积空白基本消失。地图当前渲染路级和境外政权边界；`MapView.tsx` 的数据装载与 `map/layers.ts` 的图层中尚未看到府级边界接入。

### 执行要求

1. 先检查地图源数据、生成器、生成产物、拓扑构建清单和运行时加载链，确认当前本地资源、安装版资源分别是什么版本。
2. 对黔中、荆湖北路、夔州路及相邻区域做几何连续性核对；区分真实边界、海岸/湖泊空白、无数据区域，避免用填色掩盖错误几何。
3. 若设计要求玩家看到府级边界，将府级边界从权威源数据一路接入：生成 → 拓扑/资源构建 → `MapView` 加载 → 图层渲染；不能只在生成目录中产出文件而不接入前端。
4. 明确缩放层级和线宽/颜色层级，避免府界与路界竞争；地图命中测试、政区详情和颜色填充不得被新图层破坏。
5. 当前山影资源目录 `frontend/public/map/tiles/hill` 被检查为空，但 `mapController.ts` 仍请求该路径。选择可复现的方案：恢复项目预期瓦片，或在无瓦片时禁用该图层并避免重复 404；不得随意访问或下载未经项目许可的数据源。
6. 如果地图资源需要重建，更新正式的构建产物，并说明安装包是否已重打。不要把“源码生成成功”说成“玩家安装版已更新”。

### 验收条件

- 重点区域不存在意外空洞、重叠或异常飞线；抽查的相邻府/路归属正确。
- 目标政区边界在游戏实际地图上可辨认，且缩放、点击、标签和既有路界正常。
- 缺失瓦片不再造成持续 404，或对应图层按预期关闭。
- 提供更新前后同范围、同缩放级别的截图或其他可复查证据，并注明截图来自开发版还是安装版。

## P2：主界面与事务区的信息层级

### 执行要求

- 以现有地图截图为基线，审查底部横向功能栏、右侧纵向入口、顶部资源状态和左上事务面板在常见窗口尺寸下的占位、可读性、遮挡与操作密度。
- 保持地图为主视图；考虑按使用频率收拢低频入口、改善图标文字辨识度和间距，避免同时压缩主要地图区域。
- 事务区空状态要能说明当前无事务的含义，并提供与玩法一致的行动线索；不能只堆文字或强迫玩家执行无关按钮。
- 检查边缘政权/岛屿标签是否被窗口边界裁切，小窗口下是否重叠；决定采用动态避让、缩放显隐或可交互提示，并保持地图清爽。
- 仅做能由截图/交互验证的改动；不要只调整颜色后宣称 UI 问题已解决。

### 验收条件

- 至少检查主界面、事务有内容、事务空状态及较小窗口四种场景。
- 关键按钮文字/图标可辨认、不互相遮挡；地图标签不被窗口裁掉或有明确的替代查看方式。
- 提供修改前后截图并说明观察到的改善。

## P2：会计指标口径核对（先调查，后决定是否改）

已有走查记录中显示“到账率 128.2%”，名义岁入与月实收年化值不一致。该现象尚不能直接判为计算错误。

执行者应追踪该指标 UI、API/派生读数和财政结算的数据来源，写清分子、分母、统计周期、收入类别及年化方式。若口径不同，优先让标签/说明准确表达；若数据确实重复计入或单位错误，再修正公式。改动前后用可解释的样例对账，不得通过硬编码压到 100%。

验收条件：能从代码和一组实际数值复算该指标；界面名称与口径一致；相关计算有回归保护。

## P2：关键路径错误可观测性

核心、API、AI 和资源加载代码中可见多处宽泛异常捕获。逐项检查长期事务结算、存档/API、地图加载和 AI 契约等路径：

- 预期可恢复错误应记录足以定位问题的上下文，并给玩家或开发者合适反馈。
- 静默回退只保留在明确无害且有注释的场景；不得把数据写入失败、状态不一致或资源缺失伪装成成功。
- 避免日志泄漏密钥、完整提示词、玩家敏感状态或不应显示的隐藏数值。
- 不做全库批量替换 `except Exception`；一次处理一条调用链并核对其契约。

验收条件：关键故障能从日志/界面区分定位；正常运行不产生无意义噪声；失败路径不污染游戏状态。

## 建议执行顺序

1. 输出事务机制现状图和事务支持模型，确认旧存档兼容策略。
2. 实施并验证事务—圣旨闭环。
3. 核对地图源数据，完成府界接入（若符合游戏地图设计），处理山影缺失资源，并检查黔中交界。
4. 走查主界面与事务空/非空状态，完成低风险 UI 调整。
5. 独立核对财政指标口径，再决定是否改公式或说明。
6. 对关键静默错误逐条治理，不开展无差别异常捕获重构。
7. 运行与改动范围匹配的测试、类型检查、资源构建；如交付安装版，再重打包并实际启动检查。

## 每阶段交付格式

每一阶段结束时报告：

1. 发现的问题与证据（文件/函数/界面现象）。
2. 修改的文件及玩家能观察到的变化。
3. 执行过的验证及结果；未执行的验证明确标出。
4. 旧存档、经济平衡、地图资源或安装包方面的风险。
5. 尚未解决的问题和下一步建议。
